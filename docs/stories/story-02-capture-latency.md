# Story 02. 촬영 응답 지연 — 구간 실측과 사진 업로드 비동기 전환

| 항목 | 내용 |
| --- | --- |
| 작성일 | 2026-09-15 |
| 대상 저장소 | backend (Spring Boot 4.1, Java 25), ai (FastAPI + ONNX Runtime, Lambda 컨테이너) |
| 작업 브랜치 | `feat/async-image-store` |
| 선행 단계 | 2026-08 시연 버전 |

## 1. 배경

촬영 1회의 처리 순서는 사진 3장 읽기, Lambda 추론 호출, 세션 커밋과 사진 3장 저장, 응답이다. 추론 계약의 타임아웃은 8초다. 이 값은 GPU 개발 파드 서빙을 전제로 잡은 것이고, 당시 CPU 실측은 V3 5.87초, V2 17.47초였다. 시연 환경에 GPU가 없어 CPU Lambda 컨테이너로 옮기고 ONNX Runtime으로 바꾸면서 추론 자체는 로컬 185ms까지 내려왔지만, 계약은 8초 그대로 남았다.

없는 것은 두 가지다. 하나는 작업자 대기 시간의 목표값이다. 8초는 실패 판정 기준이지 촬영 버튼을 누른 작업자가 기다릴 수 있는 시간이 아니다. 다른 하나는 구간별 측정값이다. 시연 기간 CloudWatch에 남은 Lambda 호출 332건은 웜 p50 325ms, p95 611ms인데, 이 값은 Lambda 핸들러 안의 시간이다. 백엔드가 사진을 읽고 이벤트를 조립하고 응답을 저장하는 구간은 측정한 적이 없다.

E2E 표본은 2026-08-26 한 건뿐이었다. 2.6초였고 초기화 1.2초를 포함한 값이다. 이 단계의 목표는 응답 시간 목표를 새로 정하고, 구간 실측으로 가장 큰 구간을 찾아 응답 경로에서 빼는 것이다.

## 2. 문제 정의

**시나리오 1. 촬영 버튼을 누른 뒤의 대기**

- 상황: 입고 작업자가 고정 카메라 아래 상품을 올리고 입고 등록 화면에서 촬영 버튼을 누른다
- 처리 경로: 백엔드가 사진 3장을 읽어 Lambda를 동기로 호출하고, 응답이 올 때까지 계약 타임아웃 8초 안에서 기다린다
- 원인: 계약에 있는 숫자는 실패 판정용 타임아웃 하나뿐이고, 응답 시간 목표가 정의돼 있지 않다
- 결과: 응답이 몇 초가 걸려도 계약 위반으로 잡히지 않는다. 화면 대기 시간을 판정할 기준이 문서에 없다

**시나리오 2. 표본 한 건에 근거한 병목 추정**

- 상황: 2026-08-26 E2E 표본 1건(2.6초, 초기화 1.2초 포함)을 놓고 어느 구간을 줄일지 검토한다
- 처리 경로: CloudWatch 지표는 Lambda 핸들러 안의 시간만 기록한다
- 원인: 백엔드의 사진 읽기·이벤트 조립·응답 파싱·저장 구간에 구간 로그가 없다
- 결과: 백엔드 경로가 0.9초처럼 보였고, 개선 대상을 표본 한 건의 추정으로 정하게 됐다

**시나리오 3. 트랜잭션 안에 있는 사진 업로드**

- 상황: 작업자가 촬영 결과를 확정하면 측정 세션이 커밋된다
- 처리 경로: 커밋과 같은 트랜잭션 안에서 사진 3장을 저장한다. 운영 경로에서는 이 자리에 S3 put 3회가 들어 있다
- 원인: 업로드 호출이 응답 경로와 트랜잭션 양쪽에 함께 들어 있다
- 결과: 업로드에 걸린 시간이 그대로 응답 시간에 더해지고, 그동안 DB 커넥션을 점유한다

## 4. 구현 범위

1. 구간 로그 — 사진 읽기, 이벤트 조립, Invoke 왕복, 응답 파싱, 저장의 5구간을 백엔드 로그로 기록
2. 로컬 재현 스택 — Lambda 컨테이너 이미지를 Runtime Interface Emulator로 띄우고, 백엔드 SDK 클라이언트의 엔드포인트만 교체
3. 측정용 저장소 — MinIO를 S3 대역으로 띄워 같은 저장 코드 경로로 측정
4. 커밋 후 업로드 — 세션은 사진 키를 미리 정해 커밋하고, `AFTER_COMMIT` 이벤트 리스너가 전용 executor에서 사진 3장을 업로드
5. 업로드 실패 기록 — 재시도 3회 후에도 실패하면 WARN 로그와 함께 `upload_status = FAILED`
6. 사진 조회(1-6) — `STORED`인 사진만 반환. 없는 객체의 임시 주소는 발급하지 않음
7. 로컬 저장소 — 같은 비동기 경로 사용

Invoke 경로는 로컬에서도 운영과 같은 순서를 거친다. multipart 수신, base64 인코딩, API Gateway 이벤트 조립, Mangum 처리다.

## 5. 설계 결정

### 5.1 응답 시간 계약 (확정: p95 1초 SLO)

- 쟁점: 계약에 적힌 8초는 GPU 서빙 전제의 타임아웃이고, 작업자가 화면에서 기다리는 시간의 목표로 쓸 수 없다
- 결정: 응답 시간 한계를 Nielsen의 1초로 두고 p95 1초 이하를 SLO로 정했다. 상용 정적 치수 측정기와 같은 급이다. 타임아웃은 실패 판정 기준으로 분리해 유지한다
- 기각 안: 8초 단일 계약 유지 — 타임아웃과 응답 목표가 한 숫자에 묶여 있어 지연을 판정할 수 없다

### 5.2 응답 경로에서 줄일 구간 (확정: 4안)

- 쟁점: 백엔드 몫 중 저장 구간이 절반 이상이고, 운영 경로에서는 그 자리에 S3 put 3회가 트랜잭션 안에 들어 있다
- 결정: 4안. 사진 업로드를 커밋 후 비동기로 옮겼다. 세션은 사진 키만 확정한 상태로 먼저 커밋하고, 응답은 업로드를 기다리지 않는다. 업로드 실패 처리와 조회 시점 정합성은 5.3에서 따로 설계했다
- 기각 안: 1안 Lambda 메모리 상향(3,008 → 10,240MB) — 코드 변경 없이 vCPU가 3배가 되지만 계정 쿼터가 3,008MB에서 막혀 승인 대기 상태이고, 핸들러 p95 611ms는 이미 1초 안이다. 2안 페이로드 축소(백엔드 리사이즈) — 실측 이득이 조립 10ms와 전송 20~80ms에 그쳐 2순위. 3안 저장을 트랜잭션 밖 동기 호출로 — 커넥션 점유는 풀리지만 응답 시간은 그대로다. 5안 메시지 큐와 업로드 워커 — 재시도와 격리를 브로커가 담당하지만 시연 규모에 인프라를 추가한다

### 5.3 업로드 실패와 조회 정합성

- 쟁점: 업로드가 응답 밖으로 나가면 응답이 성공한 뒤에 업로드가 실패할 수 있다
- 결정: 재시도 3회 뒤에도 실패하면 WARN 로그와 함께 `upload_status = FAILED`로 남긴다. 사진 조회(1-6)는 `STORED`인 사진만 돌려준다
- 기각 안: 실패를 로그로만 남기고 상태 컬럼을 두지 않는 방식 — 아직 올라가지 않은 객체에도 임시 주소를 발급하게 된다

기타 확정 사항: 로컬 저장소와 S3 저장소가 같은 비동기 코드 경로를 쓴다. 두 저장소의 동작이 갈리지 않게 하기 위해서다. 핸들러 시간은 로컬 측정값 대신 CloudWatch 332건을 정본으로 쓴다. 전후 비교 측정은 MinIO를 S3 대역으로 두고 진행했다.

## 6. 검증 결과

구간 실측은 AWS를 다시 만들지 않고 로컬에서 진행했다. Lambda 컨테이너 이미지를 Runtime Interface Emulator로 띄우고 백엔드 SDK 클라이언트의 엔드포인트만 바꿔 같은 Invoke 경로를 재현했다. 사진 490KB와 57KB 두 프로파일로 55회씩 쟀다.

| 구간 | p50 | p95 | 비고 |
| --- | --- | --- | --- |
| 사진 읽기 | 6~15ms | 26~40ms | 로컬 파일 |
| 이벤트 조립 | 12~21ms | 73~105ms | base64 1.34배 팽창. 페이로드 비례 |
| Invoke 왕복에서 핸들러를 뺀 값 | 40~94ms | 240~248ms | 전송·에뮬레이터 |
| 응답 파싱 | 1~8ms | 26~33ms | |
| 저장(세션 커밋 + 사진 3장 동기 업로드) | 32~81ms | 144~227ms | 백엔드 구간 중 최대 |

백엔드 경로 전체는 p50 90~220ms다. 표본 1건에서 추정했던 0.9초는 초기화와 첫 호출 효과였다. 저장 구간이 백엔드 몫의 절반 이상을 차지했고, 운영 경로에서는 이 자리에 S3 put 3회가 트랜잭션 안에 있다.

전후 비교는 MinIO를 S3 대역으로 두고 같은 조건(11상품 × 5회, 단일 스레드)으로 측정했다.

| 지표 (사진 490KB) | 변경 전 p50 / p95 | 변경 후 p50 / p95 |
| --- | --- | --- |
| 저장 구간 | 22 / 36ms | 7 / 12ms |
| 백엔드 총 시간 | 185 / 243ms | 157 / 192ms |
| 클라이언트 E2E | 191 / 250ms | 162 / 198ms |
| 업로드(응답 밖) | — | 18 / 32ms |

저장 구간이 p95 기준 3분의 1로 줄었고, 그만큼이 응답 경로에서 빠졌다. 로컬 MinIO 기준이므로 실제 S3에서는 리전 왕복 시간이 업로드 쪽에 더해지고, 응답 경로에서 빠지는 시간은 더 커진다. 운영 E2E 추정은 CloudWatch 핸들러 p95 611ms에 백엔드 경로 p95 약 200ms를 더한 0.8초 안팎으로 1초 SLO 안에 들어온다.

측정의 한계는 세 가지다. 로컬 측정은 같은 머신의 다른 컨테이너 부하로 핸들러 절대치가 흔들렸다. 같은 조건을 두 번 실행한 결과가 p50 258ms와 597ms다. 동시 촬영은 에뮬레이터가 호출 1건만 받아 측정하지 못했다. 운영 경로의 S3 GET과 put은 로컬 재현 대상이 아니어서 측정값이 없다.
