# Story 03. 모델 교체 시 정확도 보증 — 배포 전 고정셋 평가 게이트

| 항목 | 내용 |
| --- | --- |
| 작성일 | 2026-09-15 |
| 대상 저장소 | ai (FastAPI + ONNX Runtime, Lambda 컨테이너) |
| 작업 브랜치 | `feat/eval-gate` |
| 선행 단계 | 2026-08 시연 버전 |

## 1. 배경

치수 추정 모델은 AI팀이 학습해 Hugging Face에 safetensors로 올리고, 배포 파이프라인이 ONNX로 변환해 Lambda에 싣는다. 변환 단계에는 게이트가 하나 있다. torch 출력과 ONNX 출력을 대조해 `max diff`가 1e-4를 넘으면 빌드를 멈춘다.

이 게이트가 검사하는 것은 변환의 정확성이고, 모델의 품질은 어느 단계에서도 검사하지 않는다. 학습 리포트의 검증 MAE는 length 1.31cm였는데, 서빙 코드로 검증셋 2,024품목을 다시 돌리면 2.06cm가 나왔다. 평가 프로토콜, 즉 분할과 촬영 슬롯 고정 여부가 달라서 생긴 차이다. 학습 쪽 숫자를 배포 판정에 그대로 쓸 수 없다.

정확도 계약도 없었다. MVP 문서의 목표 MAE는 "미확정"으로 남아 있었다. 응답 계약을 1초로 조이면서 INT8 양자화처럼 더 빠른 변형을 올릴 동기가 생긴 상태였다. 이 단계의 목표는 배포 전에 모든 후보를 같은 프로토콜로 평가하고, 임계를 통과한 모델만 승격하는 게이트를 만드는 것이다.

## 2. 문제 정의

**시나리오 1. 학습 리포트 수치로 하는 배포 판정**

- 상황: AI팀이 학습한 모델을 Hugging Face에 올리고 배포 파이프라인이 실행된다
- 처리 경로: 변환 단계가 torch 출력과 ONNX 출력의 `max diff`만 확인하고 Lambda 이미지를 만든다
- 원인: 검증셋을 서빙 코드로 다시 평가하는 단계가 파이프라인에 없다
- 결과: 학습 리포트의 1.31cm와 서빙 측 2.06cm 차이가 배포 전에 확인되지 않는다

**시나리오 2. 배포 승인 기준의 부재**

- 상황: 모델 후보를 배포할지 판단해야 하는 시점
- 처리 경로: 승인 절차의 조건은 변환 대조 하나뿐이다
- 원인: MVP 문서의 목표 MAE가 "미확정"이고, 상용 정적 치수 측정기 급과의 격차도 문서에 없다
- 결과: 어떤 모델을 막아야 하는지 판정할 기준이 없다

**시나리오 3. 속도를 위한 변형 교체**

- 상황: 응답 계약을 1초로 조인 뒤 INT8 양자화 변형을 배포 후보로 올린다
- 처리 경로: 변환 대조를 통과하고, 이미지 크기와 지연이 줄어든 수치만 확인된다
- 원인: 변형이 정확도를 얼마나 떨어뜨리는지 확인하는 자동 경로가 없다
- 결과: 정확도가 떨어진 변형이 그대로 배포되고, 오차가 큰 값이 측정 결과로 나온다

프로젝트가 관행과 다른 지점은 기준의 성격이다. 이 모델의 MAE는 약 2cm이고, 상용 계량 등급에 못 미치는 내부 측정 용도다. 상용 0.5cm 기준은 통과 임계가 아니라 한계로 문서에 둔다.

## 4. 구현 범위

1. 평가 프로토콜 — 검증셋 2,024품목, 품목당 shot1의 카메라 1·2·3, 정답은 데이터셋의 실측 CSV
2. 전처리 — 서빙 코드(`dimension.py`)를 그대로 호출해 학습·서빙 불일치를 제거
3. 기준선 재현 — 현행 FP32가 2026-08-26 평가값(2.06 / 2.17 / 1.62cm)을 재현하는지 먼저 확인
4. 판정 기준 — 현행 대비 비열화와 절대 상한 두 겹
5. 평가 대상 — FP16, INT8 정적 PTQ 2종, INT8 동적, FP32 OpenVINO 실행기
6. 정적 양자화 보정 — 학습셋 가공식품 100품목
7. 지연 기록 — p50·p95를 결과 표에 기록. 판정에는 반영하지 않음
8. 승격 — 임계를 통과한 후보만 Lambda 별칭으로 승격

판정 기준의 두 겹은 다음과 같다. 비열화는 축별 MAE 악화 0.2cm 이하, 3축 ±3cm 정답률 하락 2%p 이하다. 절대 상한은 축별 MAE 3cm 이하다.

## 5. 설계 결정

### 5.1 정확도 검사 시점 (확정: 3안)

- 쟁점: 모델 품질을 배포 전에 검사할 것인지 배포 후 현장 데이터로 확인할 것인지에 따라, 정확도가 떨어진 모델이 운영에 올라가는지가 갈린다
- 결정: 3안. 배포 전에 고정셋으로 자동 평가하고, 임계를 통과한 후보만 별칭으로 승격한다. 서빙 코드로 평가하므로 학습 측과 서빙 측 수치가 갈라지지 않는다
- 기각 안: 1안 학습 리포트 신뢰 — 추가 작업은 없지만 학습 측 1.31cm와 서빙 측 2.06cm가 이미 어긋나 있어 프로토콜 차이를 걸러내지 못한다. 2안 배포 후 작업자 보정률로 사후 감지 — 현장 데이터를 그대로 쓰지만 나쁜 모델이 배포된 뒤에 알게 되고, 표본이 쌓일 때까지 며칠이 걸린다. 4안 카나리(별칭 가중치)·섀도우 호출 — 운영 트래픽으로 검증하지만 입고 등록이 간헐적이라 표본이 느리게 쌓인다

3안은 평가 데이터(검증셋 2,024품목 × 3장)와 x86 평가 환경을 파이프라인이 갖춰야 성립한다. 4안은 3안의 보완책으로만 남긴다.

### 5.2 판정 기준의 구성

- 쟁점: 축별 평균 MAE 하나로 판정하면 오차가 특정 품목에 몰린 후보를 걸러내지 못한다
- 결정: 현행 대비 비열화와 절대 상한을 함께 본다. 비열화 조건에 3축 ±3cm 정답률을 넣어 품목 단위의 악화를 검사한다
- 기각 안: 축별 MAE 단일 기준 — §6의 INT8 정적 PTQ 후보를 통과시키게 된다. 상용 계량 등급 0.5cm를 임계로 — 현행 모델의 MAE가 약 2cm라 후보가 전부 막힌다

### 5.3 정적 양자화 보정 데이터 출처

- 쟁점: 보정 데이터를 어디서 가져오느냐에 따라 평가 결과의 신뢰도가 달라진다
- 결정: 학습셋 가공식품 100품목으로 보정한다
- 기각 안: 검증셋으로 보정 — 보정에 쓴 데이터로 평가하게 돼 평가가 오염된다

기타 확정 사항: 판정은 정확도 지표로만 한다. 지연은 결과 표에 기록해 빨라졌지만 정확도가 떨어진 후보를 함께 보이게 한다. 평가 환경은 x86(Xeon Sapphire Rapids, 2 vCPU, ONNX Runtime CPU)으로 고정한다.

## 6. 검증 결과

후보 전부를 같은 프로토콜로 평가했다. 환경은 x86(Xeon Sapphire Rapids, 2 vCPU, ONNX Runtime CPU)이다.

| 변형 | 크기 | MAE L/W/H (cm) | 3축 ±3cm | p50 / p95 | 판정 |
| --- | --- | --- | --- | --- | --- |
| FP32 (현행) | 52.7MB | 2.06 / 2.17 / 1.62 | 62.5% | 243 / 250ms | 기준선 |
| FP16 | 26.4MB | 2.06 / 2.17 / 1.62 | 62.5% | 243 / 249ms | 통과 — 이득 없음 |
| INT8 정적 PTQ (MinMax, 보정 100) | 14.8MB | 3.57 / 3.24 / 2.89 | 22.6% | 164 / 167ms | 차단 |
| INT8 정적 PTQ (첫 conv·헤드 FP32 유지) | 22.3MB | 3.71 / 3.42 / 2.66 | 20.5% | 167 / 171ms | 차단 |
| INT8 동적 (300품목) | 13.8MB | 11.45 / 8.22 / 7.72 | 6.7% | 1,828 / 1,871ms | 차단 |
| FP32 OpenVINO 실행기 (500품목) | 52.7MB | 현행과 동일 | 61.2% | 244 / 253ms | 통과 — 이득 없음 |

게이트는 INT8 정적 양자화 후보를 차단했다. 이 후보는 1.48배 빨라지고 축별 MAE는 1.5cm 나빠지는 데 그치지만, 3축이 모두 ±3cm 안에 드는 비율은 62.5%에서 22.6%로 내려간다. 품목별로 보면 FP32와의 최대 축 차이가 중앙값 3.2cm, p95 7.5cm로 오차가 편향으로 실려 있다. 평균 MAE만 보는 기준이었다면 통과시킬 후보다.

첫 conv와 회귀 헤드를 FP32로 남기는 표준 처방도 결과를 바꾸지 못했다. 백분위·엔트로피 보정은 4GB 평가 환경에서 메모리를 넘겨 시도하지 못했다. EfficientNet의 depthwise conv 본체가 양자화에 민감한 구조이므로, 재학습(QAT) 없이 INT8을 올릴 수 없다는 것이 이 모델의 결론이다.

나머지 두 후보는 속도 이득이 없었다. FP16은 CPU에 fp16 연산기가 없어 지연이 그대로이고, OpenVINO 실행기는 최신 ONNX Runtime CPU 실행기와 같은 수준이다. 재학습 없이 남는 속도 레버는 vCPU 수 하나이며(2 → 4스레드에서 1.6배, 로컬 실측), 이는 모델이 아니라 인프라 결정이다.
