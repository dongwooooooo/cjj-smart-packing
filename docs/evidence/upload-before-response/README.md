# 촬영 사진 업로드 A/C 실측 (2026-09-26)

설계안 `docs/superpowers/specs/2026-09-26-upload-before-response-design.md` 5절 M1~M4 의 결과다. 계획과 측정 전 예측은 `PLAN.md`, 시각별 기록은 `progress.md` 에 있다.

단일 클라이언트(M1)와 작업자 10·30명(M2)에서 C 의 응답 시간은 A 와 판정 기준(+30ms) 안에서 같았다. 사진 유실은 작업자 60명 포화(M4)에서만 A 에 생겼다. 종료 직후 2,116장이 보관소에 없었고, 120초 뒤에도 18장(6세션)이 거절돼 남았다. C 는 모든 조건에서 유실이 0이었다. 대신 코어 3 설정에서는 60명 부하에 응답 p95 가 946ms 로 올랐다. 업로드 풀 코어를 6으로 올린 보조 조건(C6)에서는 A 와 같은 540ms 였다.

| C 30명 | 3,738 | 0 | 419 | 544 | 607 | 0 · 20 | STORED 11,214 | STORED 11,214 | 3 · 27 |

응답 시간은 k6 `measure_duration`(ms)이다. 양쪽 모두 PENDING·FAILED 가 0이었다. A 10명은 정착 대기가 60초가 아니라 10초로 돌았다(`progress.md` 18:41). 종료 12초 뒤 집계에서 이미 PENDING 0 이었다. 업로드 풀은 두 이미지 모두 활성 3을 넘지 않았다. `ThreadPoolExecutor` 는 큐가 가득 차야 코어(3) 위로 스레드를 늘리기 때문이다.

A 30명에서 업로드 작업 하나가 9,918ms 걸렸다(`upload.timing` max). A 에서는 응답 밖이라 영향이 없다. C 에서 같은 지연이 나면 대기 상한 8초를 넘겨 그 촬영이 `IMAGE_STORE_FAILED` 가 된다.

## M3 재시작 — 부하 중 60초 시점

| 조건 | 방식 | 요청 | 실패 응답 | 사진 60초 뒤 | PENDING |
| --- | --- | ---: | ---: | --- | ---: |
| A | `docker compose restart backend`(SIGTERM), 작업자 10명 | 1,262 | 130 (전부 연결 실패) | STORED 3,396 | 0 |
| C | 같음 | 1,270 | 120 (전부 연결 실패) | STORED 3,450 | 0 |
| A | `docker compose kill -s SIGKILL` 뒤 `start`, 작업자 30명 (보조) | 3,803 | 390 (전부 연결 실패) | STORED 10,239 | 0 |
| C | 같음 (보조) | 3,801 | 413 (전부 연결 실패) | STORED 10,164 | 0 |

재시작으로는 A 에서도 유실이 재현되지 않았다. SIGTERM 에서는 Spring Boot 정상 종료가 A 2ms, C 356ms 만에 진행 중 요청을 마쳤다. 그 사이 업로드 큐(최대 4·13)도 비었다. SIGKILL 시행에서 A 는 kill 직전 0.7초 동안 새 촬영 완료 없이 대기 중이던 업로드 15세션(32082~32096)을 마저 올린 뒤 종료됐다. 두 방식 모두 1회 시행이다. kill 시점에 커밋 뒤 업로드 전인 세션이 있으면 A 에 PENDING 이 남을 수 있지만, 이번 시행에서는 생기지 않았다. 실패 응답은 모두 재기동 13초 동안의 연결 실패(k6 `http_0`)다.

## M4 포화 — 작업자 60명, 3분

| 조건 | 요청 | p50 | p95 | p99 | max | 서버 upload.wait p50·p95 | 사진 종료 직후 | 사진 120초 뒤 | 풀 활성·큐 최대 | 거절 | CallerRuns |
| --- | ---: | ---: | ---: | ---: | ---: | --- | --- | --- | --- | ---: | ---: |
| A | 7,529 | 417 | 540 | 575 | 806 | - | PENDING 2,116 / STORED 20,471 | PENDING 18 / STORED 22,569 | 6 · 1,974 | 6건 | - |
| C | 6,032 | 788 | 946 | 1,052 | 1,976 | 340 · 512 | STORED 18,096 | STORED 18,096 | 3 · 75 | 0 | 0 |
| C6 | 7,540 | 414 | 540 | 571 | 1,059 | 0 · 0 | STORED 22,620 | STORED 22,620 | 6 · 53 | 0 | 0 |

A 는 큐가 1,974까지 자랐다. 그 사이 6건이 거절돼(`TaskRejectedException`, 로그 12줄 = 예외와 원인) 18장이 PENDING 으로 남았다. 종료 직후에는 2,116장(약 705세션분)이 보관소에 없었다. 촬영 응답은 성공이었고, 응답에 실린 사진 주소는 그 시점에 없는 객체를 가리켰다.

C 는 유실이 없었다. 대신 업로드 풀이 병목이 됐다. 큐가 최대 75로 용량 200에 닿지 않아 스레드가 코어 3에서 늘지 않았고, CallerRuns 도 한 번도 발동하지 않았다. 3개 스레드가 사진 put 을 차례로 처리하는 동안 요청 스레드는 추론 뒤 평균 340ms 를 더 기다렸다. 작업자가 응답을 기다리는 만큼 요청 수도 줄었다(7,529 → 6,032). 코어만 6으로 올린 C6 는 upload.wait p95 0ms, 응답 p95 540ms 로 A 와 같았다.

## 미확인

- S3 고아 객체: C 의 SIGKILL·실패 경로에서 세션 없이 남은 객체 수를 세지 않았다. 측정 뒤 버킷의 `measurements/` 객체는 186,936개(C 형식 80,964, A 형식 105,972)로, 이전 측정분을 포함한다. 삭제하지 않았다.
- C 의 업로드 실패·상한 초과(`IMAGE_STORE_FAILED`)는 운영에서 한 번도 발생하지 않았다. 동작은 통합 테스트로만 확인했다.
- 재시작·강제 종료는 각 1회 시행이다. A 에서 유실이 나는 kill 시점의 확률은 재지 않았다.
