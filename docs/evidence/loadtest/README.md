환경: 백엔드 EC2 c7i-flex.large(2 vCPU, 3.8GB), RDS db.t4g.micro, Lambda 3,008MB(계정 동시 실행 한도 400), 부하 발생기 c7i-flex.large(같은 VPC). 수집 5초, k6 → Prometheus remote write. 대시보드 `tools/loadtest/monitoring/grafana/dashboards/cjj-loadtest.json`.

## 실행 3 — 출고지시 배치 접수, 배치 100·1,000·5,000주문 (2026-09-22 18:58~19:22 KST)

시나리오: 상위 시스템이 N주문 배치를 `POST /api/v1/admin/orders/import`로 보낸다. 서버는 검증 → 재고 선별 → 주문·배송단위 저장 → 라인 배정 → 유휴 토트 배정을 한 트랜잭션으로 처리한다. 배치 100주문은 분당 4건 4분, 1,000주문은 분당 1건 4분, 5,000주문은 1건. 판정 기준은 응답 시간이 주문 수에 선형인가, 동시 배치에서 커넥션·락 대기가 생기는가.

앞선 체인 3건(18:29~18:48 KST)은 무효로 처리했다. 시험 전 넣은 재고 +100,000이 `inventory_tx` 원장에만 기록되고 `product.stock_qty`는 약 120으로 남아 있었다. 가용 재고는 `stock_qty − 미포장 배정 수량`으로 계산하므로 149주문을 받은 뒤 전 주문이 `INSUFFICIENT_STOCK`으로 거절됐고, 1,000주문 배치가 70ms에 끝난 수치는 거절 경로의 측정치였다. `stock_qty`를 원장과 맞춘 뒤 재실행했다.

| 배치 크기 | 배치 수 | k6 응답 p50 / p95 / max | 주문당 | 서버 측 |
| ---: | ---: | --- | ---: | --- |
| 100 | 17 | 5.40 / 5.78 / 5.81초 | 54ms | DB `created_at` 간격 5.0~5.7초 |
| 1,000 | 5 | 52.5 / 54.0 / 54.3초 (k6 4건, 1건은 30초 gracefulStop 에 중단) | 53ms | 중단된 1건도 서버가 끝까지 처리, 50.9초 |
| 5,000 | 2 동시 | k6 측정 없음(90초에 2건 모두 중단) | 54ms | A: 5,000건 커밋 272.4초. B: 락 대기 3.5분 뒤 유니크 위반으로 전체 롤백 |

실패 0(k6 기준). 서버 `http_server_requests` 5,000배치 max 272.4초. HikariCP active 1(배치당 커넥션 1), pending 0. EC2 CPU 18~26%, JVM 힙 최대 435MB, GC 일시정지 합계 1.3초/4분. RDS 연결 10, 락 대기 세션 최대 1.

판독(표 `20260922-101510-orders_import/import-window-table.md`, 그래프 `20260922-101510-orders_import/grafana-import-run3.png`):

- **증상 1(선형)**: 응답 시간은 주문 수에 정확히 비례한다. 100주문 5.4초, 1,000주문 52.5초, 5,000주문 272초로 주문당 53~54ms가 배치 크기와 무관하게 일정하다. 배치 하나가 커넥션 1개를 잡고 순차 처리하므로 처리량은 배치 크기와 상관없이 초당 약 19주문이다.
- **원인 1(주문당 53ms의 출처)**: `ToteAllocator.allocate`가 배송단위마다 `findByStatusOrderByIdAsc(IDLE)`로 유휴 토트 전체를 읽고 첫 행만 쓴다. 토트 테이블 40,100행 중 IDLE 33,226행을 배송단위마다 JPA 엔티티로 적재한다. `pg_stat_user_tables` 기준 1,000주문 배치 1건에 tote 인덱스 행 읽기 약 4,370만 건(배송단위당 약 43,700행), 5,000배치는 약 2.4억 건이다. 같은 쿼리를 DB에서 직접 실행하면 12ms(`EXPLAIN ANALYZE`, PK 인덱스 스캔 + status 필터, 버퍼 3,738)이고 `LIMIT 1`이면 2.3ms다. 나머지 약 40ms는 33,226행을 JDBC로 옮겨 Hibernate 엔티티로 만들고, 커밋까지 영속성 컨텍스트에 쌓인 엔티티를 flush 때마다 dirty check 하는 애플리케이션 쪽 비용이다. `pg_stat_activity`에서 배치 트랜잭션이 대부분 시간을 `idle in transaction`(클라이언트 대기)으로 보낸 것이 근거다. 이 비용은 유휴 토트 수에 비례하므로 시연 규모(토트 수백 개)에서는 드러나지 않았다.
- **증상 2(동시 배치)**: 5,000주문 배치 2건이 60초 간격으로 들어왔다. 두 번째 배치는 첫 토트 배정 INSERT에서 `Lock` 대기에 들어가 첫 배치가 커밋한 19:21:56까지 3분 32초를 기다렸고, 커밋 직후 `duplicate key value violates unique constraint "ux_tote_assignment_active_tote"`(tote_id 6875)로 5,000주문 전체가 롤백됐다.
- **원인 2(같은 토트 선택)**: 유휴 토트 조회가 READ COMMITTED 스냅샷으로 첫 배치의 미커밋 배정을 보지 못해 같은 토트 id 를 고른다. 부분 유니크 인덱스 `ux_tote_assignment_active_tote (tote_id) WHERE released_at IS NULL`가 두 번째 INSERT를 첫 트랜잭션 종료까지 막고, 커밋되면 위반으로 끝낸다. 데이터는 지켰지만 배치 단위 실패다. 배치가 겹치는 시간이 길수록(큰 배치) 확률이 1에 가깝다.
- **대응 방향**: 토트 선택을 `SELECT ... WHERE status='IDLE' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED`로 바꾸면 행 읽기가 40,100행에서 1행으로 줄고 동시 배치가 서로 다른 토트를 잡는다. 배치 트랜잭션은 주문 단위 청크(예: 500)로 나눠 커밋 간격과 영속성 컨텍스트 크기를 제한한다. 이 두 가지가 실행 3의 수정 대상이다.

한계: 5,000배치의 k6 측정은 gracefulStop 30초 때문에 없다(서버 측 지표와 DB `created_at`으로 대체). 2건 동시 배치는 의도한 시나리오가 아니라 arrival-rate 실행기가 1분 duration 에 2회 시작한 결과다. 시험 전에 넣은 토트 40,000개는 시연 데이터(수백 개)보다 많아 주문당 비용을 키웠다.

### 실행 3 추가 관찰 (2026-09-23)

가설 "영속성 컨텍스트가 커질수록 배치 후반 주문이 느려진다"를 DB `created_at` 간격으로 검증했다.

| 5,000주문 배치 내 위치 | 주문당 평균 간격 | p50 |
| ---: | ---: | ---: |
| 1~500 | 50.3ms | 49.0ms |
| 2,001~2,500 | 52.6ms | 52.1ms |
| 4,501~5,000 | 59.1ms | 57.9ms |

후반이 앞보다 17% 느리다. 1,000주문 배치 5건도 앞 100건 51~54ms, 뒤 100건 53~57ms로 같은 방향이다. 컨텍스트 성장 효과는 있지만 부차적이고, 100주문 배치(53.4ms)와 5,000주문 배치 초반(50.3ms)이 같으므로 주문당 약 50ms는 배치 크기와 무관한 고정 비용이다. 이 고정 비용이 유휴 토트 전체 읽기다.

JVM 지표(5,000배치 272초 구간): 할당률 211MB/s, 합계 약 57GB, 배송단위당 약 11MB. 토트 40,100행 × 행당 약 280바이트로 계산이 맞는다. GC 195회, 일시정지 합계 1.8초, 최대 21ms라 GC 자체는 응답에 영향이 없고 비용은 할당과 행 처리 CPU다. 커넥션 점유 시간 최대 272초(배치 1건 = 커넥션 1개 전유).

미측정: JFR 프로파일로 50ms 안에서 JDBC 수신·ResultSet 처리·Hibernate 식별자 조회의 비중. 수정 전 한 번 찍어 둔다.


## 실행 4 — 동시 포장 완료, 포장 작업자 10명·50명 (2026-09-22 19:26~19:43 KST)

시나리오: 포장 작업자 N명이 각자 토트를 스캔하고(`POST /api/v1/totes/scan`), 배송단위 상세를 보고(`GET /api/v1/shipments/{id}`), 포장 완료를 누른다(`POST /api/v1/shipments/{id}/complete`, 사이 생각 시간 1초). 완료는 한 트랜잭션에서 상품별 재고 차감(상품 행 `SELECT FOR UPDATE`) → 박스 재고 차감(박스 행 `FOR UPDATE`) → 토트 해제 → 상태 변경을 한다. 토트는 시연용 피더 대신 DB에서 뽑은 배정 목록(11,874건)을 작업자별로 나눠 썼다. 판정 기준은 완료 p95 500ms, 실패 1% 미만.

50명 실행은 세 번 돌렸다. 앞의 두 번(19:30, 19:36)은 토트 목록 시작 위치(OFFSET)가 스크립트에 반영되지 않아 10명 실행이 이미 포장한 토트를 다시 스캔했고(`404 TOTE_NOT_ASSIGNED` 811건·1,486건), 무효로 처리했다. 아래 50명 수치는 미사용 토트로 돌린 세 번째(19:40)다.

| 항목 | 10명 | 50명 |
| --- | ---: | ---: |
| 완료 시도 | 1,109 | 864 |
| 완료 성공 / 실패(500) | 975 / 134 (12.1%) | 515 / 349 (40.4%) |
| 완료 처리량 | 5.4건/s | 2.9건/s |
| k6 완료 p50 / p95 / max | 50ms / 3.03초 / 7.06초 | 4.41초 / 10.07초 / 18.81초 |

실패 500은 전부 `CannotAcquireLockException: deadlock detected`다(백엔드 로그 466건 + 356건, `OUT_OF_STOCK`·`INVALID_STATE` 0). 데드락 대기 대상은 로그 1,060건 전부 `relation "product"`다.

판독(표 `20260922-104007-packing/packing-window-table.md`, 그래프 `20260922-103015-packing/grafana-packing-run4.png`(10명), `20260922-104007-packing/grafana-packing-run6.png`(50명)):

- **증상**: 10명에서 완료 p50은 50ms인데 p95는 3.0초, 12%가 500이다. 50명에서는 p50이 4.4초, 40%가 500이고 완료 처리량이 10명 때의 절반으로 떨어진다. 작업자를 늘리면 처리량이 줄었다. CPU는 10% 아래다.
- **원인 1(상품 행 락 순서)**: 완료 트랜잭션이 배송단위의 상품마다 `findByGtinForUpdate`로 상품 행을 잠근다. 잠그는 순서는 `shipment_item` id 순, 즉 주문에 적힌 상품 순서라서 배송단위마다 다르다. 시험 상품이 8종뿐이라 두 작업자가 같은 두 상품을 반대 순서로 잠그는 일이 잦고, PostgreSQL이 `deadlock_timeout`(1초) 뒤 한쪽을 끊는다. 로그의 대기 사슬은 3~4개 트랜잭션이 서로를 기다리는 형태다. 데드락으로 끊긴 트랜잭션은 500으로 끝나고 배송단위는 `PACKING`에 남는다(시험 뒤 644건).
- **원인 2(포화)**: 락을 잡은 채 다른 락을 기다리는 트랜잭션이 커넥션을 점유한다. 50명에서 HikariCP active 10(최대), pending 39, Tomcat busy 50이다. 커넥션을 못 받은 스캔·상세 조회까지 p95 5~6초로 밀린다. 락 대기가 커넥션 풀을 채워 읽기 요청까지 느려지는 구조다.
- 생존 응답 시간: 10명에서 성공한 완료의 서버 p95는 2.1초, 실패한 완료의 p50은 2.0초다. 성공도 락 대기를 거친 뒤 끝난다.
- **대응 방향**: 상품 행을 잠그기 전에 상품 id 순으로 정렬하면 순환 대기가 사라진다(락 순서 고정). 재고 차감은 `UPDATE product SET stock_qty = stock_qty - ? WHERE id = ?`로 바꿔 엔티티 로드 없이 한 문장으로 끝내고, 박스 행도 같은 방식으로 줄인다. 데드락이 남으면 `CannotAcquireLockException`에 한해 한 번 재시도한다. 이 세 가지가 실행 4의 수정 대상이며, 수정 뒤 같은 목록으로 50명을 다시 돌려 500 비율과 p95를 비교한다.

한계: 상품이 8종이라 실제 SKU 수천 종보다 충돌 확률이 훨씬 높다. 다만 물류센터에서는 같은 시간대에 같은 인기 상품이 몰리므로 상품 수가 많아도 상위 상품에서 같은 충돌이 난다. 시험 뒤 `PACKING` 644건은 재스캔 없이 완료할 수 없는 상태라 정리가 필요하다.

품목 1개인 배송단위도 13.8% 실패한다. 상품 행 하나를 잡은 채 박스 행(`box_type FOR UPDATE`)을 기다리고, 박스 행을 잡은 쪽이 그 상품 행을 기다리는 2자 순환이다. 즉 순환에는 상품 행끼리뿐 아니라 상품 행과 박스 행 사이도 포함된다. 락 순서를 고정할 때 박스 행까지 한 순서에 넣어야 한다.

같은 목록 870건 안에서 같은 두 상품을 반대 순서로 담은 배송단위 쌍은 48,090쌍이고, 상품 8종의 모든 조합(28쌍)에서 역순이 존재한다. 첫 번째로 잠그는 상품의 분포는 8종에 고르게 퍼져 있어(실패 29~63건) 특정 상품이 뜨거운 것이 아니라 순서 자체가 원인이다.

데드락 로그의 tuple ctid는 UPDATE마다 바뀌어 현재 ctid와 대응하지 않으므로 상품 쌍을 로그에서 직접 복원하지는 못했다. 위 품목 수 분석이 그 대체 근거다.
