# 부하 테스트 실행 기록

환경: 백엔드 EC2 c7i-flex.large(2 vCPU, 3.8GB), RDS db.t4g.micro, Lambda 3,008MB(계정 동시 실행 한도 400), 부하 발생기 c7i-flex.large(같은 VPC). 수집 5초, k6 → Prometheus remote write. 대시보드 `tools/loadtest/monitoring/grafana/dashboards/cjj-loadtest.json`.

## 실행 1 — 동시 촬영, 작업자 1→20명 (2026-09-22 17:53~18:02 KST)

시나리오: 입고 작업자 N명이 각자 상품을 스캔하고 촬영 버튼을 누른다(사이 생각 시간 1초). 서버는 사진 3장 읽기 → Lambda Invoke → 세션 커밋 → 비동기 S3 업로드. 판정 기준은 촬영 응답 p95 1초, 실패 1% 미만.

| 항목 | 값 |
| --- | ---: |
| 촬영 요청 | 2,496건, 실패 0 |
| k6 촬영 응답 | avg 459ms, p95 558ms, max 4,013ms |
| 최대 처리량 | 13 req/s (작업자 18~20명) |
| Lambda 핸들러(CloudWatch) | p50 309 / p95 430 / p99 445 / max 714ms |
| 콜드 스타트 | 8건, 초기화 p50 1.3초, 최대 2.5초 |
| Lambda 최대 메모리 | 674MB |

판독(그래프 `20260922-085104-capture/grafana-capture-run1.png`):

- **증상**: 작업자 2명에서 20명까지 늘려도 p95는 0.56~0.60초로 평평했다. 서버 p95와 k6 p95가 같아서 앞단 큐잉이 없다. max 4.0초는 시험 시작 직후 첫 콜드 호출 1건이다.
- **원인 1(구간)**: 응답의 대부분이 Invoke 구간이다(p95 0.42~0.51초). 사진 읽기 p95 0.09초, 저장 p95 0.03초. 업로드는 응답 밖에서 p95 0.13~0.19초.
- **원인 2(포화도)**: HikariCP active 최대 2, pending 0. 업로드 executor 큐 최대 1. EC2 CPU 최대 13%, JVM 힙 20% 미만, RDS 락 대기 0. **어느 자원도 차지 않았다.** 이 구간의 처리량 한계는 서버가 아니라 작업자 수다.
- 타임아웃 예산: 1초 = Invoke p95 0.45 + 백엔드 구간 p95 0.15 + 여유 0.4. 예산의 절반이 Lambda다.

한계: 촬영본은 상품별 고정 사진 3장이고, 20명 구간이 2분뿐이다. 자원이 차기 시작하는 지점은 실행 2(최대 100명)에서 찾는다.
