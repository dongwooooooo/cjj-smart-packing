# 부하 테스트 실행 기록

환경: 백엔드 EC2 c7i-flex.large(2 vCPU, 3.8GB), RDS db.t4g.micro, Lambda 3,008MB(계정 동시 실행 한도 400), 부하 발생기 c7i-flex.large(같은 VPC). 수집 5초, k6 → Prometheus remote write. 대시보드 `tools/loadtest/monitoring/grafana/dashboards/cjj-loadtest.json`.

## 실행 1 — 동시 촬영, 작업자 1→20명 (2026-09-22 17:53~18:02 KST)

시나리오: 입고 작업자 N명이 각자 상품을 스캔하고 촬영 버튼을 누른다(사이 생각 시간 1초). 서버는 사진 3장 읽기 → Lambda Invoke → 세션 커밋 → 비동기 S3 업로드. 판정 기준은 촬영 응답 p95 1초, 실패 1% 미만.

| 항목 | 값 |
| --- | ---: |
| 촬영 요청 | 2,496건, 실패 0 |
| k6 촬영 응답 | avg 459ms, p95 558ms, max 4,013ms |
| 최대 처리량 | 13 req/s (작업자 18~20명) |
| Lambda 핸들러(CloudWatch) | p50 309 / p95 430 / p99 445 / max 714ms |
| 콜드 스타트 | 8건, 초기화 p50 1.3초, 최대 2.5초 |
| Lambda 최대 메모리 | 674MB |

판독(그래프 `20260922-085104-capture/grafana-capture-run1.png`):

- **증상**: 작업자 2명에서 20명까지 늘려도 p95는 0.56~0.60초로 평평했다. 서버 p95와 k6 p95가 같아서 앞단 큐잉이 없다. max 4.0초는 시험 시작 직후 첫 콜드 호출 1건이다.
- **원인 1(구간)**: 응답의 대부분이 Invoke 구간이다(p95 0.42~0.51초). 사진 읽기 p95 0.09초, 저장 p95 0.03초. 업로드는 응답 밖에서 p95 0.13~0.19초.
- **원인 2(포화도)**: HikariCP active 최대 2, pending 0. 업로드 executor 큐 최대 1. EC2 CPU 최대 13%, JVM 힙 20% 미만, RDS 락 대기 0. **어느 자원도 차지 않았다.** 이 구간의 처리량 한계는 서버가 아니라 작업자 수다.
- 타임아웃 예산: 1초 = Invoke p95 0.45 + 백엔드 구간 p95 0.15 + 여유 0.4. 예산의 절반이 Lambda다.

한계: 촬영본은 상품별 고정 사진 3장이고, 20명 구간이 2분뿐이다. 자원이 차기 시작하는 지점은 실행 2(최대 100명)에서 찾는다.

## 실행 2 — 동시 촬영, 작업자 1→100명 (2026-09-22 18:11~18:20 KST)

같은 시나리오, 최대 100명. 18:09~18:10 배포와 겹쳐 시험 시작이 2분 밀렸고, 그 구간은 판독에서 제외했다.

| 항목 | 값 |
| --- | ---: |
| 촬영 요청 | 13,038건, 실패 0, 전부 INFERRED |
| k6 촬영 응답 | avg 443ms, p95 542ms, max 2,115ms |
| 최대 처리량 | 66 req/s (작업자 90~100명) |
| Lambda 핸들러(CloudWatch) | p50 309 / p95 428 / p99 442 / max 706ms |
| Lambda 동시 실행 최대 | 35 (한도 400), 스로틀 0 |
| 콜드 스타트 | 33건, 초기화 p50 1.24초, 최대 1.38초 |
| HikariCP active 최대 | 4 / 10 |
| EC2 CPU 최대 | 48% |
| 업로드 executor 큐 최대 | **2,000 (큐 용량)** |
| 업로드 완료 | 12,693건 = 촬영 13,038건 − 345건 |
| DB `measurement_image` PENDING | **1,155장 (385세션 × 3장)** |

판독(그래프 `20260922-090934-capture/grafana-capture-run2.png`):

- **증상**: 100명까지 올려도 촬영 응답 p95는 0.54초로 움직이지 않았다. 실패 0. 응답만 보면 아무 문제가 없다.
- **원인 2(포화도)**: 작업자 45명(약 30 req/s)부터 업로드 executor 큐가 쌓이기 시작해 18:17 228, 18:18 1,304, 18:18:30 2,000에 닿았다. 큐 용량이 2,000이고, 차면 작업을 거절한다. 거절된 업로드는 로그 한 줄로 끝나고 사진은 `PENDING`으로 남는다. 시험 뒤 DB에 PENDING 1,155장이 남았다. **응답 시간은 지켰지만 데이터가 빠졌다.** 촬영 화면의 사진 주소는 발급됐으나 객체가 없는 상태다.
- 업로드 처리량 계산: 작업 하나(사진 3장 순차 put)가 p50 104ms, 스레드 6개면 이론상 초당 58건인데 실측 소화량은 초당 약 30건에서 큐가 자라기 시작했다. S3 put 지연이 동시 요청에서 늘어난 것으로 보이며, 스레드별 처리 시간은 재지 않았다.
- **원인 1(구간)**: Invoke p95 0.42~0.44초로 실행 1과 같다. Lambda는 동시 35까지 콜드 33건을 만들었지만 초기화가 1.2~1.4초라 p99에만 보인다(18:12:30 p99 2.0초).
- Tomcat 스레드·RDS 락은 여전히 여유. CPU 48%는 업로드 스레드와 GC다.

**결론**: 이 시스템의 첫 병목은 요청 경로가 아니라 응답 뒤로 넘긴 업로드다. 비동기화가 응답 시간을 지키는 대신 실패를 숨겼다. 거절 시 PENDING 을 재처리하는 경로(Outbox 테이블 + 스케줄러, 또는 CallerRuns 로 역압)와 큐 깊이 알람이 필요하다. 다음 실행 전에 PENDING 1,155장은 재처리해야 한다.
