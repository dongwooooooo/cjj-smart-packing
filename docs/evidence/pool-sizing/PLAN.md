# 커넥션 풀·서버 설정 실험 계획

작성 2026-09-25. 실험 전에 커밋하고, 결과를 보고 판정 규칙을 바꾸지 않는다. 바꿔야 하면 바꾼 이유와 함께 이 문서 끝 "변경 기록"에 남긴다.

## 0. 목적과 방식

HikariCP 설정이 기본값(`maximumPoolSize` 10, `connectionTimeout` 30,000ms)이고 Tomcat 스레드도 기본값(200)이다. 부하 테스트 실행 4에서 락 대기가 커넥션을 붙잡아 락과 무관한 상세 조회까지 커넥션 획득에 최대 10.5초를 기다렸고, 실행 5에서는 50명이 동시에 들어온 첫 30초에 pending 38이 찍혔다(`docs/evidence/loadtest/README.md`). 설정값을 비즈니스 트래픽에서 산정하고, 부하를 고정한 채 설정 하나만 바꿔 재서 정한다.

방식은 Oracle Real World Performance Group 영상(https://www.youtube.com/watch?v=_C77sBcAtSQ)을 따른다. 영상은 스레드 9,600·생각 시간 550ms를 고정하고 JDBC 풀 크기만 2048 → 1024 → 96으로 줄이며 TPS, 커넥션 대기(Queue-ms), 실행 시간(Run-ms), DB 대기 이벤트를 같은 화면에 놓는다. 여기서는 작업자 수(k6 VU)와 사이클 길이(pacing)를 고정하고 `maximumPoolSize` 만 바꾼다. 도구는 `tools/loadtest/pool-sweep.sh`(사용법 `tools/loadtest/README.md`).

## 1. 비즈니스 트래픽 산정

### 1-1. 사용 주체와 요청

| 주체 | 행동 | 서버 요청 | 커넥션 점유 |
| --- | --- | --- | --- |
| 포장 작업자 | 토트 스캔 → 화면에서 주문 내역 확인 → 상자 포장 → 포장 완료 | 스캔·상세·완료 3건 / 사이클 | 요청마다 짧게 1개 |
| 관리자·상위 시스템 | 출고지시 배치 접수 | 배치당 1건 | 배치 전체 동안 1개(500주문 약 20~29초, 이 실험의 묶음 접수 실측) |
| 서버 내부 | 재고 원장 집계(5초), 대조(60초) | 주기 작업 | 주기마다 짧게 1개 |

입고 촬영은 Lambda 호출 동안 커넥션을 잡지 않도록 이미 나뉘어 있고(실행 1·2에서 HikariCP active 최대 4), 이 실험 범위 밖이다.

| 요청당 커넥션 점유 시간 | 평균 22.3ms, p95 44.4ms | smoke 실행(`20260925-161551`, 작업자 20명, 풀 10)의 `hikaricp_connections_usage` |

### 1-3. 필요 커넥션 (Little's law)

동시에 쓰이는 커넥션 수 = 요청 도착률 × 요청당 점유 시간.

| 부하 | 사이클/초 | 요청/초 | 평균 동시 커넥션 | 3개 이상 동시일 확률(포아송) |
| --- | ---: | ---: | ---: | ---: |
| 피크 1배(100명) | 1.67 | 5.0 | 0.11 | 0.02% |
| 피크 3배(300명) | 5.0 | 15.0 | 0.33 | 0.45% |

여기에 배치 접수 1개(배치가 커넥션 하나를 전유)와 주기 작업 1개를 더하면 피크 3배에서 상시 필요한 커넥션은 약 2.3개, 포장 요청이 4개 이상 겹칠 확률이 0.04% 수준이므로 1 + 1 + 4 = 6개면 모자라지 않는다는 것이 산정값이다. 여유 배수는 따로 두지 않고 실험(2절)의 획득 대기로 확인한다. 이 산정에서 나오는 예측은 다음과 같고, 틀리면 산정이 틀린 것이다.

- 예측 A: 피크 1배·3배에서는 풀 크기 2~40 사이에 처리량 차이가 없다(처리량은 작업자 수가 정한다).
- 예측 B: 피크 1배·3배에서 풀 5 이상이면 커넥션 획득 대기 p95 가 1ms 아래다.

### 1-4. 부하 프로파일(k6)

| 이름 | VU | PACING_MS | THINK_MS | 의미 |
| --- | ---: | ---: | ---: | --- |
| `peak1x` | 100 | 60,000 | 50,000 | 작업자가 스캔·확인 뒤 50초 동안 상자를 싸고 완료를 누르며, 한 사이클이 60초 |
| `peak3x` | 300 | 60,000 | 50,000 | 같은 작업자 300명 |
| `sat` | 3-1 절에서 결정 | 0 | 0 | 작업자가 쉬지 않고 누르는 포화 부하. 영상의 9,600 스레드처럼 DB가 감당할 수 있는 양보다 많은 요청을 넣는다 |

영상의 "thinking time 550ms" 에 해당하는 값이 `THINK_MS`(상자를 싸는 시간)와 `PACING_MS`(사이클 길이)다. 첫 사이클의 시작을 0~60초 사이로 흩어 모든 작업자가 같은 순간에 누르지 않게 하고, 흩어진 첫 사이클이 다 돈 60초 뒤부터 판독한다.

## 2. 실험 매트릭스

| 단계 | 고정 | 변수 | 부하 | 반복 | 판독 |
| --- | --- | --- | --- | --- | --- |
| 2-1 포화 수준 탐색 | 풀 40, timeout 30s, threads 200 | VU 50·100·200·400 (think 0) | 탐색 | 1 | 45초 |
| 2-2 풀 스윕(비즈니스) | timeout 30s, threads 200 | 풀 2·5·10·20·40 | peak1x, peak3x | 1 | 240초 |
| 2-3 풀 스윕(포화) | timeout 30s, threads 200 | 풀 2·5·10·20·40 | sat | 2 | 데이터 양이 허용하는 최대(4분 목표) |
| 3 connectionTimeout | 풀 = 2단계 결정값, threads 200 | timeout 30,000·3,000·1,000ms | peak3x + 박스 행 락 20초 주입, 클라이언트 10초 | 1 | 240초 |
| 4 Tomcat 스레드(선택) | 풀 = 결정값 | threads 200·50·20 | sat | 1 | 240초 |
| 5 재검증 | — | 기본값(풀 10) vs 결정값 | peak3x, sat | 2 | 240초 |

조건마다 절차는 같다: 설정 반영·컨테이너 재생성 → 헬스 UP → 실험 묶음 원복(배송단위 20,000건 이상을 포장 전 상태로, 박스 재고 50,000, VACUUM ANALYZE) → 10초 대기 → 대기 이벤트 채집 시작 → k6. 워밍업(기본 30초, 사이클이 있으면 사이클 길이)은 판독에서 뺀다. 포화 부하에서 실험 묶음이 판독 구간 안에 바닥나면(`packing_exhausted` > 0) 그 조건은 무효로 하고 묶음을 늘려 다시 잰다.

## 3. 측정 항목

조건마다 한 행: k6 포장 완료 처리량(판독 구간 성공 건수 / 초)·p50/p95/max·실패율, 서버 `http_server_requests` 완료·스캔·상세 p95, HikariCP active/pending max, 획득 시간 p95·평균·max(Queue-ms), 점유 시간 p95·평균(Run-ms), 획득 타임아웃 수, Tomcat busy max, RDS 연결 수 max, RDS CPU(CloudWatch 1분 평균), EC2 CPU, DB 대기 이벤트 상위 3개(1초 표본의 평균 세션 수), 커밋/초, 데드락 수.

RDS `max_connections` 는 79(`SHOW max_connections`, 2026-09-25). 평시 연결 20개(앱 10 + 모니터링·관리 연결)라 풀 40 까지는 한도 안이다.

## 4. 판정 규칙(사전 기록)

부하 수준별로 풀 크기를 작은 순서로 본다.

1. **처리량 규칙**: 최고 처리량의 98% 이상을 내는 가장 작은 풀. 이보다 크게 해도 처리량이 오르지 않는다.
2. **획득 대기 규칙**: 커넥션 획득 p95 가 1ms 이하가 되는 가장 작은 풀. 이보다 작으면 요청이 풀 앞에서 줄을 선다.
3. **DB 대기 규칙**: DB 에서 일하는 앱 세션 중 CPU 가 아닌 대기(Lock·LWLock·IO) 비중이 앞 크기보다 5%p 넘게 늘기 시작하는 풀. 이보다 크게 하면 대기가 풀에서 DB 로 옮겨 간다.
4. **p95 악화 규칙**: 처리량이 오르지 않으면서 서버 완료 p95 가 앞 크기보다 20% 넘게 나빠지는 가장 작은 풀. 이 크기 이상은 쓰지 않는다.

결정: 피크 3배에서 규칙 2를 만족하고, 포화 부하에서 규칙 1을 만족하며, 규칙 3·4 에 걸리지 않는 가장 작은 풀 크기. 두 조건이 충돌하면 포화 부하 결과를 우선한다(피크를 넘는 순간에 커넥션이 DB를 과부하시키지 않는 쪽).

connectionTimeout 결정: 락 주입 동안 락과 무관한 요청(스캔·상세)이 클라이언트 타임아웃(10초)보다 먼저 서버에서 실패로 끝나고, 락이 없는 구간에서는 획득 타임아웃이 0 인 가장 작은 값. 클라이언트보다 긴 서버 상한은 작업자 화면이 먼저 포기한 요청을 서버가 계속 붙잡게 만든다.

## 5. 복원

실험이 끝나면 백엔드 컨테이너를 실험 전 이미지와 설정(환경변수 `SPRING_APPLICATION_JSON` 없음)으로 되돌린다. 도구가 trap 으로 하고, 결과를 `progress.md` 에 적는다. 결정값은 backend 브랜치 `feat/hikari-pool-sizing` 의 `application.yml` 에만 넣고 main 에 병합하지 않는다.

## 변경 기록

- 2026-09-25 17:5x, 2-1 결과 반영(판정 규칙은 그대로). 풀 40·think 0 에서 VU 50 이 완료 135.8건/s, VU 100 이 131.8건/s 로 50명에서 이미 포화했다. 처리량이 늘지 않으므로 VU 200·400 탐색은 생략하고, `sat` 부하를 VU 100(포화점의 2배, 모든 작업자가 쉬지 않고 누름)으로 정했다.
- 같은 때, 포화 부하의 판독 구간을 240초에서 180초로 줄였다. 포화 부하는 초당 약 135건을 포장해 조건 하나(워밍업 30초 + 판독)에 묶음을 다 쓴다. IDLE 토트가 바닥나(`유휴 토트가 없어 출고지시를 접수하지 못했습니다`, 배치 73) 묶음은 36,000건(원복 대상 35,092건)이 상한이고, 240초 판독이면 270초 × 135건 ≈ 36,500건이 필요해 모자란다. 풀 크기에 따라 처리량이 오르면 더 모자라므로 여유를 두었다. 피크 1배·3배는 240초 그대로다.
