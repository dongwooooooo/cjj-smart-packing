## 1. 피크 부하: 풀 크기와 무관

작업자 100명(1배)·300명(3배)이 1분에 1건씩 포장하는 부하에서 처리량은 풀 크기와 상관없이 1.7건/s, 5.0건/s 였다. 예측 A(처리량 동일)가 맞았다.

| 부하 | 풀 | 완료/s | Queue-ms p95 | pending max | Run-ms p95 | 서버 완료 p95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 피크 1배 | 2 | 1.7 | 1.7 | 0 | 60.8 | 54.8 |
| 피크 1배 | 5·10·20·40 | 1.7 | 1.7 | 0 | 50.4~64.0 | 53.5~60.9 |
| 피크 3배 | 2 | 5.0 | **15.4** | **1** | 45.8 | 61.7 |
| 피크 3배 | 5·10·20·40 | 5.0 | 1.6 | 0 | 44.8~45.9 | 49.7~52.2 |

피크 3배에서 풀 2 만 줄을 섰다(pending max 1). 예측 B 의 사전 문구 "풀 5 이상이면 커넥션 획득 대기 p95 가 1ms 아래"는 실측 1.6~1.7ms 로 틀렸다. 원인(아래 생존 확인 왕복)을 확인한 뒤 "pending 0 이고 획득 p95 가 풀 40 과 같은 수준"으로 해석을 바꿨고, 이 해석은 결과를 본 뒤의 사후 변경이다(`PLAN.md` 변경 기록).

Queue-ms p95 1.6~1.7ms 는 줄 선 시간이 아니다. HikariCP 는 500ms 넘게 쉰 커넥션을 내주기 전에 살아 있는지 DB에 한 번 물어본다(`aliveBypassWindowMs`, 기본 500ms). 1분에 한 번 누르는 부하에서는 대부분의 커넥션이 500ms 넘게 쉬므로 이 왕복이 획득 시간에 들어간다. 확인 창을 600초로 늘린 JVM 옵션(`-Dcom.zaxxer.hikari.aliveBypassWindowMs=600000`)으로 같은 부하(풀 10·피크 3배, 1회)를 돌리자 p95 가 버킷 하한인 0.1ms 이하, 평균 0.003ms 로 내려갔다(`hypothesis-alive-bypass/`). p95 를 1.6ms 로 올리려면 획득의 5% 이상이 500ms 넘게 쉰 커넥션이면 되고, 그 비율 자체는 재지 않았다. 확인 로직은 HikariCP `HikariPool.getConnection`(https://github.com/brettwooldridge/HikariCP/blob/dev/src/main/java/com/zaxxer/hikari/pool/HikariPool.java) 에 있다.

## 3. connectionTimeout: 락 20초 동안 누가 얼마나 기다리나

풀 10, 피크 3배, 판독 60초 뒤 psql 세션이 박스 행 6개를 20초 잠갔다. k6 타임아웃 10초(작업자 화면). 스캔 p50·p95, 완료 p50, 클라이언트 타임아웃(전체), 서버 500 은 락 구간에 시작한 요청만 센 k6 요약 값이고, 클라이언트 타임아웃(전체)에는 완료 요청도 들어 있다. "스캔 타임아웃 / 스캔 500" 은 k6 원격 기록(`k6_http_reqs_total`, name·status 별)에서 락 시작부터 해제 뒤 12초까지 끝난 스캔을 센 값이라 구간 정의가 다르다(`timeout/lockwin-by-status.json`).

| connectionTimeout | 회 | 스캔 p50 / p95 | 스캔 결과 | 스캔 타임아웃 / 스캔 500 | 완료 p50 | 클라이언트 타임아웃(전체) | 서버 500 | pending max | Tomcat busy max |
| ---: | ---: | --- | --- | --- | ---: | ---: | ---: | ---: | ---: |
| 30,000 | 2 | 6.1~6.7초 / 10.0초 | 절반은 6~7초에 성공, 나머지 일부는 10초에 화면이 포기 | 46·59 / 0 | 10.0초 | 95, 95 | 0, 0 | 174, 190 | 184, **200** |
| 3,000 | 1 | 3.0초 / 3.0초 | 3초에 500 | 0 / 201 | 3.0초 | 9 | 243 | 65 | 76 |
| 1,000 | 2 | 1.0초 / 1.0초 | 1초에 500 | 0 / 487·496 | 1.0초 | 10, 10 | 518, 530 | 51, 55 | 62, 65 |

- 기본값 30초에서는 락과 무관한 스캔이 커넥션을 기다리다 작업자 화면의 10초 한도에 걸렸다. 서버는 화면이 포기한 스캔을 최대 18초, 완료를 최대 20초 뒤 200 으로 끝냈다. 2회차에는 Tomcat 스레드 200개가 다 찼다.
- 3초·1초에서는 서버가 먼저 500 을 돌려줬고, Tomcat busy 가 62~76 에서 멈췄다. 락 구간 밖의 획득 타임아웃은 두 값 모두 0 이었다.
- 세 값 모두 박스 행 락을 이미 기다리던 완료 요청은 락이 풀릴 때까지(최대 20초) 커넥션을 쥐었다. 이 대기는 connectionTimeout 이 아니라 DB 락 대기라 이 설정으로 줄지 않는다.

## 6. 한계와 미확인

- **시간에 따른 표류(원인 확인)**: 원복 없이 조건을 거듭하면 재고 원장이 포화 풀 10·20 조건마다 약 5.4만~6.2만 행씩 늘어(47만 → 105만 행, 계산식 `drift-query/README.md`), 같은 풀 10 포화 처리량이 기본값끼리 113.4(20:40) → 66.4건/s(23:53)로 3시간 13분 동안 41% 내려갔다. DB 전체 버퍼 접근량을 완료 건수로 나눈 값도 약 6.2천 → 11.8천 블록으로 늘었고(캐시 적중 100%), 원장을 되돌린 뒤에는 약 1.8천 블록이었다(`drift-query/buffers-per-complete.json`). 조건마다 원장을 되돌린 5-3 에서는 하락이 없었다. 원장 크기에 비례해 느려진 쿼리는 재고 집계기(5초 주기)의 ADVANCE 다(`drift-query/`). 정착 경계를 찾는 `MIN(y.id)` 와 정착한 마지막 id 를 찾는 `MAX(t.id)` 두 서브쿼리가 모두 `inventory_tx_pkey` 를 id 범위로 훑고 product_id·created_at 을 필터로 버리며(로컬 105만 행에서 둘 다 루프당 약 55.7만 행), 원장이 없는 상품 9개는 커서가 0 이라 원장 전체를 훑는다. 로컬 docker PostgreSQL 18.6(Apple M2 Pro, 합성 원장)에서 ADVANCE 는 2만 행 27.2ms, 105만 행 1,425ms 였다(대조기 MISMATCHES 는 5.7 → 281.7ms, 60초에 한 번). RDS 실행 시간을 로컬의 2배(2만 행 비율 54.1/27.2 를 그대로 외삽, 큰 원장에서는 미확인)로 두면 105만 행에서 2.85초 → 2.85/7.85 = 코어 1개의 36%, 2 vCPU 의 약 18%, 약 90만 행에서 약 16% 다. 부하 없는 구간의 RDS CPU 최솟값은 원장 약 90만 행일 때(23:05~23:35) 29%, 원복 뒤 6% 였다. 차이 23%p 중 16~18%p 가 ADVANCE 추정치이고 나머지 5~7%p 는 미확인이다. 원장 설계(글 F)의 남은 과제로 넘긴다. 5-2·5-1 과 2절 포화 스윕은 원장 원복 전 결과다. 2절의 풀 크기 순위는 순서를 뒤집은 2회차에서도 같았다.
