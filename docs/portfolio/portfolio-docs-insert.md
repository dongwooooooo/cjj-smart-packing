## 시스템 아키텍처

![시스템 아키텍처](images/01-architecture.png)

**아키텍처 설계 이유**

- 학습(PyTorch)과 서비스(ONNX Runtime)의 출력이 어긋나면 배포 뒤에야 드러납니다. 그래서 빌드 단계에서 변환과 출력 대조를 마친 이미지만 ECR에 올립니다.
- 치수 추론은 입고가 있을 때만 호출되고, CPU로도 응답 목표 1초를 맞출 수 있습니다. 그래서 GPU 서버를 상시 띄우지 않고 호출한 만큼 과금되는 Lambda에서 실행합니다(문제 2).
- Lambda는 공개 URL 없이 EC2의 IAM 역할로만 호출할 수 있어, API 서버를 거치지 않은 추론 요청은 들어올 수 없습니다.

## 문제 1. 동시 포장 데드락과 재고 원장 전환

### 성능 테스트

**테스트 목적**

팀 기간의 시연은 작업자 1명으로 진행해, 여러 작업자가 동시에 포장할 때의 동작은 확인하지 못했습니다. 개인 고도화 기간에 창고 규모의 동시 포장을 재현해 가장 먼저 병목이 생기는 곳을 찾았습니다.

**테스트 환경**

| 구성 | 사양 |
| :-: | :-: |
| API 서버 | EC2 2 vCPU, Spring Boot 1대 (Tomcat 스레드 200, 커넥션 풀 10) |
| DB | RDS PostgreSQL 2 vCPU, 메모리 1GB |
| 부하·관측 | 같은 VPC의 EC2에서 k6, Prometheus와 Grafana로 서버·커넥션 풀·DB 지표 수집 |

**테스트 시나리오**

포장 작업자는 상품이 담긴 운반함(토트)의 바코드를 스캔하고, 박스 하나로 나갈 주문 묶음(배송단위)의 상세를 확인한 뒤 포장 완료를 누릅니다. 1초 쉬고 다음 운반함으로 넘어갑니다. 이 작업자를 10명과 50명으로 두고 각각 3분씩 측정했습니다.

판정 기준은 포장 완료 p95 500ms 이하, 실패율 1% 미만입니다.

**테스트 결과**

| 항목 | 작업자 10명 | 작업자 50명 |
| :-: | :-: | :-: |
| 포장 완료 실패율 | 12.1% | **40.4%** |
| 포장 완료 p95 | 3.0초 | **10.1초** |
| 초당 포장 완료 | 5.4건 | 2.9건 |
| 스캔·상세 조회 p95 | 0.1초 | 5~6초 |
| EC2 CPU | 10% | 6% |
| 커넥션 풀 사용 / 대기 | 8 / 0 | 10 / 39 |
| DB 락 대기 세션 | 6 | 10 |

![개선 전, 작업자 50명](images/02-packing-before.png)

- 작업자를 5배로 늘리자 처리량은 절반으로 줄었고, 락과 무관한 조회까지 5초 넘게 걸렸습니다. 특정 API가 아니라 모든 요청이 함께 쓰는 자원에서 막힌 것입니다.
- CPU는 한가한데 커넥션 풀과 DB는 가득 차 있었습니다. 커넥션 10개가 모두 DB 안에서 행 락을 기다렸고, 나머지 요청은 풀 앞에서 커넥션을 기다렸습니다.
- 락 대기에 시간 제한을 두지 않았는데도 실패가 난 것은 DB가 트랜잭션을 강제로 끊었다는 뜻입니다. 서버 로그와 PostgreSQL 통계에서 데드락 356건을 확인했습니다.

### 문제 배경

- 포장 완료는 배송단위에 담긴 상품의 재고 행을 하나씩 잠그고 수량을 줄였습니다. 잠그는 순서가 주문에 적힌 상품 순서라, 두 작업자가 같은 두 상품을 반대 순서로 잠그면 서로를 기다리다 데드락이 났습니다.
- DB가 데드락을 끊기 전까지 트랜잭션이 커넥션을 반환하지 않아, 다른 요청은 커넥션을 받지 못했습니다. 커넥션 풀을 늘려도 DB 안의 락 대기 줄만 길어질 뿐이었습니다.

### 해결 과정

재고는 실물과 어긋나면 어느 포장에서 틀렸는지 거슬러 찾아야 합니다. 그래서 데드락을 없애면서 변동 이력도 남기는 방식을 기준으로 골랐습니다.

| 해결 방안 | 장점 | 단점 및 기각 사유 |
| :-: | :-: | :-: |
| 1. 상품 ID 순으로 잠그기 | • 순환 대기 제거 | • 상품마다 행 락과 대기는 그대로<br>• 재고 변동 이력이 없어 불일치 추적 불가 |
| 2. 낙관적 락(버전 컬럼) | • 행 락 없이 충돌 감지 | • 동시 요청이 많을수록 재시도 급증<br>• 변동 이력 없음 |
| 3. 데드락 시 재시도 | • 코드 변경 최소 | • 원인이 남아 부하가 커지면 재발 |
| **4. 재고 원장 (최종 채택)** | **• 잠그는 상품 행이 없어 데드락 불가<br>• 모든 변동이 기록돼 불일치 추적 가능** | **• 현재 수량을 계산하는 집계 필요** |

**핵심 설계 결정**

- **수량을 고치지 않고 변동만 기록**: 포장 완료는 상품 행을 수정하지 않고, 재고 변동을 쌓는 테이블(원장)에 "−1" 행만 추가합니다. 잠그는 상품 행이 없으니 서로 기다릴 일도 없습니다.
- **현재 수량은 집계표와 최근 변동의 합**: 5초마다 원장을 상품별로 합산한 집계표에, 그 뒤 쌓인 원장 행을 더해 현재 수량을 계산합니다. 집계에서 빠진 행은 60초마다 전체를 다시 맞춰 보정합니다.

### 결론

같은 시나리오(작업자 50명, 3분)로 다시 측정했습니다.

| 항목 | 개선 전 | 개선 후 |
| :-: | :-: | :-: |
| 포장 완료 실패율 | 40.4% | **0%** |
| 포장 완료 p95 | 10.1초 | **73ms** |
| 초당 포장 완료 | 2.9건 | **32.6건** |
| 스캔·상세 조회 p95 | 5~6초 | 41ms 이하 |
| 데드락 | 356건 | 0건 |
| 커넥션 풀 대기 / DB 락 대기 세션 | 39 / 10 | 0 / 2 |

![개선 후, 같은 부하](images/03-packing-after.png)

모든 요청을 막던 락 대기가 사라져 조회 지연과 커넥션 대기도 함께 없어졌습니다.

원장으로 옮기면서 기존 재고 수량과 포장 기록을 맞춰 보니, 재고가 포장 건수의 절반만 줄어 있었습니다. JPA가 잠금 전에 읽어 둔 상품 객체를 그대로 돌려줘서, 락을 잡은 뒤에도 옛 수량으로 저장하고 있었습니다(갱신 손실). 원장에 남은 변동 기록으로 올바른 수량을 다시 계산했습니다.

## 문제 2. 치수 추론 서빙과 모델 배포 판정

### 문제 배경

- 팀 기간에는 학습용 GPU 개발 환경에서 추론을 돌리는 것을 전제로 했지만, 학습 환경은 서비스 가용성을 보장하지 않았습니다. 서비스용 GPU를 따로 상시 띄우면 입고가 없는 시간에도 비용이 나갑니다(g4dn.xlarge 기준 월 약 380달러).
- 모델을 바꿀 때 나아졌는지 판정할 기준이 없었습니다. 학습 리포트의 정확도는 검증 데이터와 전처리가 서비스와 달라 그대로 쓸 수 없었습니다.

### 해결 과정

**서빙 위치**

| 해결 방안 | 장점 | 단점 및 기각 사유 |
| :-: | :-: | :-: |
| 1. GPU 인스턴스 상시 가동 | • 추론이 가장 빠름 | • 입고가 없는 시간에도 비용 발생 |
| 2. API 서버 안에서 CPU 추론 | • 인프라 추가 없음 | • 2 vCPU에서 포장 요청과 CPU 경합<br>• Python 전처리를 Java로 재작성 |
| **3. Lambda 컨테이너 + ONNX Runtime (최종 채택)** | **• ONNX 변환으로 CPU 추론을 1.07초에서 185ms로 단축(로컬 측정)<br>• 호출한 만큼만 과금** | **• 콜드스타트 최대 9.5초** |

콜드스타트는 시연 시간대에만 실행 환경 1개를 미리 띄워 두는 Provisioned Concurrency로 막았습니다. 비용은 하루 8시간 기준 약 0.4달러입니다.

**배포 판정**

GitHub Actions에서 고정 검증셋 2,024품목을 서비스와 같은 전처리로 평가합니다. 아래 조건을 모두 통과한 모델만 서비스가 호출하는 Lambda 버전으로 전환합니다.

- 가로·세로·높이별 평균 오차가 직전 모델보다 0.2cm 넘게 늘지 않을 것
- ±3cm 이내 적중률이 직전 모델보다 2%p 넘게 떨어지지 않을 것
- 가로·세로·높이별 평균 오차가 3cm 이하일 것

![모델 파이프라인. 빌드, 고정 검증셋 평가, Lambda 버전 전환](images/08-model-gate-actions.png)

### 결론

GPU 없이 서빙했고, 시연 기간 Lambda 처리 시간 p95는 609ms로 목표 1초 안이었습니다(콜드스타트 제외 246건).

속도만 보면 INT8 양자화 모델(164ms)이 가장 빨랐지만, ±3cm 적중률이 62.5%에서 22.6%로 떨어져 판정에서 자동으로 걸러졌습니다. 재학습 없이 통과한 경량화 모델이 없어 양자화하지 않은 ONNX 모델을 배포했습니다.
