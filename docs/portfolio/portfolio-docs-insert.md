## 시스템 아키텍처

![시스템 아키텍처](images/01-architecture.png)

**아키텍처 설계 이유**

- 학습 환경(OneFlow AI)과 서비스 환경(AWS)을 분리하고, 연결은 Hugging Face 비공개 저장소의 가중치 파일뿐입니다. 학습 환경의 자격 증명과 데이터가 서비스 쪽에 들어가지 않고, AI 담당과 서비스 담당이 서로의 환경을 만지지 않습니다.
- GitHub Actions는 이미지 빌드 안에서 PyTorch 가중치를 ONNX로 변환하고 출력을 대조한 뒤 ECR로 보냅니다. 변환과 정확도 검증을 서비스와 같은 컨테이너 환경에서 하기 위해서입니다(성과 2).
- 치수 추론은 GPU 인스턴스 대신 AWS Lambda 컨테이너에서 실행합니다. 입고 시각이 불규칙해 상시 가동(월 약 380달러)은 유휴 비용이 컸고, ONNX 변환으로 CPU 추론이 185ms라 호출량 과금으로 충분했습니다(성과 2).
- Lambda는 공개 URL을 두지 않고 EC2의 IAM 역할로만 호출합니다. 추론 경로가 API 서버 밖으로 열리지 않습니다.

## 성과 1. 재고 원장 전환으로 동시 포장 데드락 제거

### 문제 배경

- 포장 완료는 박스에 담긴 상품의 재고 행을 하나씩 잠그고 수량을 줄이는 구조였습니다. 박스마다 잠그는 순서가 달라 동시 포장에서 데드락이 발생했습니다.
- 잠금 전에 읽어 둔 수량을 기준으로 저장해 갱신 손실도 함께 생겼습니다. 재고 감소분이 포장 건수의 절반만 반영됐습니다.
- 락을 기다리는 요청이 커넥션 풀(10개)을 점유해, 락과 무관한 조회까지 최대 10.5초를 기다렸습니다.
- 포장 작업자 50명 동시 부하(k6, 3분)에서 에러율은 40.4%, 데드락은 356건이었습니다. 포장 완료 p95는 10초 이상(프론트엔드 요청 타임아웃)이었습니다.

![개선 전 포장 50명 부하. 포장 완료 p95 10초, 에러율 40.4%, 커넥션 대기 스레드 39개](images/02-packing-before.png)

### 해결 과정

| 해결 방안 | 장점 | 단점 |
| :-: | :-: | :-: |
| 원자적 갱신과 상품 ID 순 락 획득 | 데드락과 갱신 손실을 제거합니다. | 상품 수만큼 락은 그대로 남고, 변동 이력이 없습니다. |
| 낙관적 락 | 락 없이 버전 비교로 충돌을 감지합니다. | 동시 요청이 많을수록 재시도가 늘고, 변동 이력이 없습니다. |
| **재고 원장** | **수량을 고치지 않고 변동 행만 추가해 잠글 대상 자체가 없습니다. 모든 변동이 한 곳에 남습니다.** | **현재 수량을 읽는 집계 구조가 필요합니다.** |

- 원자적 갱신과 상품 ID 순 락 획득은 데드락은 막지만 상품 락 대기가 처리량 상한으로 남습니다. 재고 불일치가 생겼을 때 추적할 이력도 없어 제외했습니다.
- 현재 수량은 5초마다 갱신하는 스냅샷에 아직 집계되지 않은 원장 행을 더해 읽습니다. 커밋 순서가 어긋나 건너뛴 행은 60초마다 전체 대조로 잡습니다.
- 재고 부족 판정은 주문 접수 단계에서만 합니다. 포장대에 온 상품은 이미 꺼낸 실물이기 때문입니다.

### 결론

재고 행을 갱신하지 않으므로 데드락과 갱신 손실이 구조적으로 발생하지 않습니다. 원장이 105만 행까지 쌓이자 집계 쿼리가 상품마다 원장을 풀 스캔했습니다. 인덱스 범위 스캔으로 바꿔 3.39초를 0.66ms로 줄였습니다. 커넥션 풀은 실측 결과에 따라 10개를 유지했습니다. 커넥션 획득 타임아웃만 30초에서 3초로 내려 락 대기가 화면 멈춤으로 번지지 않게 했습니다.

그 결과 같은 부하(포장 작업자 50명, 3분)에서 에러율은 40.4%에서 0%로, 포장 완료 p95는 10초 이상에서 73ms로 줄었습니다. 처리량은 초당 2.9건에서 32.6건으로 늘었습니다.

![개선 후 포장 50명 부하. 포장 완료 p95 73ms, 에러율 0%, 커넥션 대기 스레드 0개](images/03-packing-after.png)

## 성과 2. 치수 추론을 Lambda로 옮기고 정확도 게이트로 배포

### 문제 배경

- 팀 초기 설계는 GPU 인스턴스(g4dn.xlarge) 상시 가동이었습니다. 입고 시각이 불규칙해 대부분의 시간이 유휴인데도 월 약 380달러가 나가는 구성이었습니다.
- 모델을 바꿀 때 나아졌는지 판정할 기준이 없었습니다. 학습 리포트의 수치는 검증 분할과 전처리가 서비스와 달라 그대로 쓸 수 없었습니다.
- 학습은 격리된 OneFlow AI 환경에서 하고 서비스는 AWS에 있었습니다. 두 환경을 직접 연결하지 않고 모델을 전달할 경로가 필요했습니다.

### 해결 과정

| 해결 방안 | 장점 | 단점 |
| :-: | :-: | :-: |
| GPU 인스턴스 상시 가동 | 추론 시간이 가장 짧습니다. | 월 약 380달러. 입고가 없는 시간에도 비용이 나갑니다. |
| API 서버 안에서 CPU 추론 | 인프라가 단순합니다. | 2 vCPU에서 포장 요청과 CPU를 두고 경합하고, Python 전처리를 Java로 다시 써야 합니다. |
| **Lambda 컨테이너(ONNX Runtime)** | **PyTorch 모델을 ONNX로 변환해 CPU 추론 1.07초를 185ms로 줄였습니다. 호출한 만큼만 과금되고 동시 촬영 수만큼 확장됩니다.** | **콜드스타트가 최대 9.5초입니다.** |

- 콜드스타트는 시연 시간대에만 Provisioned Concurrency로 실행 환경 1개를 미리 초기화해 두어 막았습니다. 8시간 설정에 하루 약 0.4달러입니다.
- 학습 환경과 서비스는 Hugging Face 비공개 저장소의 가중치 파일로만 연결했습니다. GitHub Actions가 이미지 빌드 안에서 ONNX로 변환하고 PyTorch 출력과 대조(최대 오차 1e-4)한 뒤 ECR로 보냅니다.
- 배포 여부는 고정 검증셋 2,024품목을 서비스 전처리 그대로 평가해 판정합니다. 축별 평균 절대 오차는 직전 모델보다 0.2cm 넘게 늘지 않고 3cm 이하이며, ±3cm 적중률은 2%p 넘게 떨어지지 않을 때만 Lambda 별칭을 옮깁니다.

![모델 파이프라인. 빌드, 고정 검증셋 정확도 검증, Lambda 별칭 전환 3단계 통과](images/08-model-gate-actions.png)

### 결론

GPU 없이 CPU 추론 185ms로 서빙해 상시 가동 비용을 없앴습니다. 시연 기간 Lambda 핸들러 p95는 609ms로 목표 1초 안이었습니다(319건 중 배포 검증·콜드스타트를 뺀 246건 기준).

속도만 보면 INT8 양자화 후보(164ms)가 가장 빨랐습니다. 하지만 ±3cm 적중률이 62.5%에서 22.6%로 떨어져 정확도 게이트에서 자동 차단됐습니다. 재학습 없이 통과하는 경량화 후보가 없어 양자화하지 않은 ONNX 모델을 배포했습니다.

GPU 상시 비용 제거, 배포 전 정확도 자동 판정
