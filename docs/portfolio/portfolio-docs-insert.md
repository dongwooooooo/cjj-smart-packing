## 시스템 아키텍처

![시스템 아키텍처](images/01-architecture.png)

**아키텍처 설계 이유**

- 추론 모델은 이미지 빌드 안에서 ONNX로 변환하고 PyTorch 출력과 대조한 뒤 ECR로 올려, 변환·검증·실행 환경을 하나로 맞췄습니다(성과 2).
- 치수 추론은 GPU가 더 빠르지만, ONNX 변환 후 CPU 추론 185ms로 요구사항(1초)을 만족하고 비용이 적어 Lambda 컨테이너에서 실행합니다. GPU 상시 가동은 월 약 380달러, 입고가 없는 시간에도 나갑니다(성과 2).
- Lambda는 공개 URL 없이 EC2의 IAM 역할로만 호출해 추론 경로를 API 서버 밖으로 열지 않았습니다.

## 문제 1. 서버 부하 테스트 후 장애 문제 해결

### 성능 테스트

**테스트 목적**

시연은 작업자 1명이었습니다. 창고 규모의 동시 작업에서 어디서 먼저 병목이 생기는지, 추론 요청과 DB 쓰기가 몰릴 때 어떤 문제가 나는지 찾기 위해 부하 테스트를 진행했습니다.

**테스트 환경**

| 구성 | 사양 |
| :-: | :-: |
| API 서버 | EC2 2 vCPU, Spring Boot 1대 (Tomcat 스레드 200, HikariCP 커넥션 10) |
| DB | RDS PostgreSQL 2 vCPU, 1GB |
| 부하 발생 | 같은 VPC의 EC2에서 k6 |
| 관측 | Prometheus 5초 수집, Grafana (k6·서버·JVM·커넥션 풀·EC2·RDS) |

**테스트 시나리오**

작업자 행동 단위로 만들었습니다. 포장 작업자 1명이 토트 스캔 → 배송단위 상세 조회 → 포장 완료를 1초 간격으로 반복하고, 끝나면 다음 토트를 잡습니다. 작업자 수를 10명에서 50명까지 늘리며 3분씩 측정했습니다. 현장 속도(작업자당 분당 1~2건)의 20배 이상 부하입니다. 판정 기준은 포장 완료 p95 500ms, 실패율 1% 미만입니다.

**테스트 결과**

| 항목 | 10명 | 50명 |
| :-: | :-: | :-: |
| 포장 완료 실패율 | 12.1% | **40.4%** |
| 포장 완료 p95 | 3.0초 | **10.1초** |
| 처리량 | 초당 5.4건 | 초당 2.9건 |
| 토트 스캔·상세 조회 p95 | 0.1초 | 5~6초 |
| EC2 CPU | 10% | 6% |
| HikariCP 사용 / 대기 | 8 / 0 | 10 / 39 |
| RDS 락 대기 세션 | 6 | 10 |

![개선 전, 포장 50명. 위: 완료 p95 10초 이상, 실패율 40.4%. 아래: CPU 6%로 한가한데 커넥션 풀 10개 전부 사용·대기 39, DB 세션 10개 전부 락 대기](images/02-packing-before.png)

작업자를 늘리면 처리량이 오히려 줄었습니다. 판독 순서는 다음과 같습니다.

- 지연과 실패율이 함께 올랐고, 락과 무관한 조회까지 느려졌습니다. 특정 API가 아니라 공용 자원의 대기 문제입니다.
- CPU는 6%로 한가했습니다. 연산 부족이나 트래픽 초과가 아니라 I/O 대기입니다.
- 대기가 계층별로 쌓여 있었습니다. Tomcat 스레드 50개 전부 처리 중, 커넥션 10개 전부 사용 중에 대기 39, DB에 들어간 세션 10개 전부 락 대기. 커넥션 점유 시간이 최대 14초라 풀이 마른 원인은 반납이 느린 것이었습니다.
- 락 타임아웃이 없는데 실패가 나는 것은 DB가 트랜잭션을 끊고 있다는 뜻입니다. 서버 로그의 `deadlock detected` 예외와 `pg_stat_database.deadlocks`에서 356건을 확인했습니다.

### 문제 배경

- 포장 완료 트랜잭션이 박스에 담긴 상품의 재고 행을 하나씩 `SELECT FOR UPDATE`로 잠그고 수량을 줄였습니다. 잠그는 순서가 주문에 적힌 상품 순서라 배송단위마다 달랐고, 두 작업자가 같은 상품 두 개를 반대 순서로 잠그면 순환 대기가 됐습니다.
- 데드락 대기가 커넥션을 점유해 커넥션 풀이 말랐고, 락과 무관한 조회까지 커넥션을 기다렸습니다. 풀을 늘려도 락 대기 줄만 길어지는 구조였습니다.
- 잠금 전에 읽어 둔 수량으로 저장해 갱신 손실도 있었습니다. 실제 재고 감소분이 포장 건수의 절반만 반영됐습니다.

### 해결 과정

| 해결 방안 | 장점 | 단점 및 기각 사유 |
| :-: | :-: | :-: |
| 1. 원자적 갱신과 상품 ID 순 락 획득 | • 데드락과 갱신 손실 제거 | • 상품 수만큼 락이 남아 처리량 상한이 그대로<br>• 재고 불일치를 추적할 이력 없음 |
| 2. 낙관적 락(버전 컬럼) | • 락 없이 충돌 감지 | • 동시 요청이 많을수록 재시도 폭증<br>• 이력 없음 |
| 3. 데드락 시 재시도 | • 구현 최소 | • 원인이 남아 부하가 커지면 재발 |
| **4. 재고 원장(append-only ledger) (최종 채택)** | **• 수량을 고치지 않고 변동 행만 추가해 잠글 대상 자체가 없음<br>• 모든 변동이 한 곳에 남아 불일치 추적 가능** | **• 현재 수량을 읽는 집계 구조 필요** |

**핵심 설계 결정**

- **재고 갱신 제거 (행 락 → 원장 추가)**: 포장 완료는 상품 행을 건드리지 않고 원장에 "−1" 변동 행만 추가합니다. 잠글 대상이 없으니 데드락과 갱신 손실이 구조적으로 발생하지 않습니다.
- **현재 수량은 스냅샷 + 미집계 원장**: 5초마다 갱신하는 스냅샷에 아직 집계되지 않은 원장 행을 더해 읽습니다. 커밋 순서가 어긋나 건너뛴 행은 60초마다 전체 대조로 잡습니다. 원장이 105만 행까지 쌓이자 집계 쿼리가 3.39초 걸린 문제는 인덱스 범위 스캔으로 0.66ms로 줄였습니다.
- **커넥션 획득 타임아웃 30초 → 3초**: 풀 크기는 실측으로 10개를 유지하고, 락 대기가 화면 멈춤으로 번지지 않도록 프론트엔드 타임아웃(10초) 전에 실패하게 했습니다.

### 결론

같은 시나리오(포장 작업자 50명, 3분)로 다시 측정했습니다.

| 지표 | 개선 전 | 개선 후 |
| :-: | :-: | :-: |
| 포장 완료 실패율 | 40.4% | **0%** |
| 포장 완료 p95 | 10.1초 | **73ms** |
| 처리량 | 초당 2.9건 | 초당 32.6건 |
| 토트 스캔·상세 조회 p95 | 5~6초 | 31~41ms |
| 데드락 | 356건 | 0건 |
| HikariCP 대기 | 39 | 0 (시작 30초 제외) |
| RDS 락 대기 세션 | 10 | 2 |
| EC2 CPU (워밍업 뒤) | 6% (요청 초당 14) | 12% (요청 초당 139) |

![개선 후, 같은 부하. 위: 완료 p95 73ms, 실패 0. 아래: CPU는 시작 시 JIT 워밍업으로 50%까지 올랐다가 12%로 안정, 커넥션 대기 0, RDS 커밋 초당 100건 이상, 락 대기 0](images/03-packing-after.png)

잠글 대상을 없애 데드락이 0건이 됐고, 같은 부하에서 실패율 40.4%가 0%로, 포장 완료 p95가 10초에서 73ms로 내려갔습니다. 처리량 10배에 CPU는 2배라 요청당 CPU도 줄었습니다. 남은 락은 박스 자재 재고 1행뿐이며, 이것이 포화 처리량의 상한입니다.

## 성과 2. 치수 추론을 Lambda로 옮기고 정확도 게이트로 배포

### 문제 배경

- 팀 초기 설계는 GPU 인스턴스(g4dn.xlarge) 상시 가동이었습니다. 입고 시각이 불규칙해 대부분 유휴인데도 월 약 380달러가 나갔습니다.
- 모델을 바꿀 때 나아졌는지 판정할 기준이 없었습니다. 학습 리포트의 수치는 검증 분할과 전처리가 서비스와 달라 쓸 수 없었습니다.

### 해결 과정

| 해결 방안 | 장점 | 단점 |
| :-: | :-: | :-: |
| GPU 인스턴스 상시 가동 | 추론 시간이 가장 짧습니다. | 입고가 없는 시간에도 월 약 380달러가 나갑니다. |
| API 서버 안에서 CPU 추론 | 인프라가 단순합니다. | 2 vCPU에서 포장 요청과 CPU를 경합하고, Python 전처리를 Java로 다시 써야 합니다. |
| **Lambda 컨테이너(ONNX Runtime)** | **ONNX 변환으로 CPU 추론 1.07초를 185ms로 줄였습니다. 호출한 만큼만 과금되고 동시 촬영 수만큼 확장됩니다.** | **콜드스타트가 최대 9.5초입니다.** |

- 콜드스타트는 시연 시간대에만 Provisioned Concurrency로 실행 환경 1개를 미리 초기화해 막았습니다. 8시간에 하루 약 0.4달러입니다.
- 배포 여부는 GitHub Actions에서 고정 검증셋 2,024품목을 서비스 전처리 그대로 평가해 판정합니다. 축별 평균 절대 오차가 직전 모델보다 0.2cm 넘게 늘지 않고 3cm 이하이며, ±3cm 적중률이 2%p 넘게 떨어지지 않을 때만 Lambda 별칭을 옮깁니다.

![모델 파이프라인. 빌드, 고정 검증셋 정확도 검증, Lambda 별칭 전환 3단계 통과](images/08-model-gate-actions.png)

### 결론

GPU 없이 CPU 추론 185ms로 서빙해 상시 가동 비용을 없앴습니다. 시연 기간 Lambda 핸들러 p95는 609ms로 목표 1초 안이었습니다(콜드스타트를 뺀 246건 기준).

속도만 보면 INT8 양자화 후보(164ms)가 가장 빨랐지만 ±3cm 적중률이 62.5%에서 22.6%로 떨어져 게이트에서 자동 차단됐습니다. 재학습 없이 통과하는 경량화 후보가 없어 양자화하지 않은 ONNX 모델을 배포했습니다.

GPU 상시 비용 제거, 배포 전 정확도 자동 판정
