## 문제 1. 치수와 무게를 함께 보는 박스 판정

### 문제 배경

- **박스 추천**: 포장 단계에서 주문 상품을 담을 박스와 개수를 정해 작업자에게 추천해야 했습니다. 작업자가 추천대로 바로 포장하려면, 추천한 박스에 상품이 들어가고 택배 접수 한도(무게 20kg, 세 변 합 160cm, 최장변 100cm)도 넘지 않아야 합니다.

### 해결 과정

- **부피·무게 합으로 비교 (기각)**
  - 방식: 상품 부피 합이 박스 안쪽 부피보다 작고 무게 합이 20kg 이하이면 담을 수 있다고 판정합니다.
  - 장점: 구현이 단순합니다.
  - 단점: 상품이 들어가지 않는 박스도 추천합니다.
  - 예시: 25×25×20cm 상품 두 개는 부피 합이 30×30×30cm 박스보다 작지만, 나란히 놓으면 한 변이 40cm가 되어 들어가지 않습니다.
- **상품을 배치해 치수만 판정 (기각)**
  - 방식: 상품을 박스 안에 하나씩 놓고, 모든 상품이 놓이면 담을 수 있다고 판정합니다. 박스 수가 가장 적도록 나눠 담습니다.
  - 장점: 상품이 들어가는 박스만 추천합니다.
  - 단점: 무게를 보지 않아, 무거운 상품이 한 박스에 몰리면 20kg을 넘습니다.
- **배치 판정에 무게·접수 한도 검사 추가 (채택)**
  - 방식: 상품이 모두 놓인 박스 중 무게 합 20kg, 세 변 합 160cm, 최장변 100cm를 넘지 않는 박스만 후보로 둡니다.
  - 장점: 상품이 들어가고 택배로 접수되는 박스만 추천합니다.
  - 단점: 나눠 담는 주문이 늘어 박스 수가 증가합니다. 모든 배치를 시험하지 않아 담을 수 있는 박스를 놓치는 경우도 있습니다.

**핵심 설계 결정**

- **배치 판정**: 이미 놓인 상품의 모서리가 만드는 지점을 바닥부터, 안쪽부터 확인합니다. 상품을 6방향으로 돌려 처음 맞는 지점에 놓고, 한 번 놓은 상품은 다시 옮기지 않습니다.
- **여러 박스로 나누기**: 치수나 무게 때문에 한 박스에 다 담을 수 없으면 부피 큰 상품부터 들어갈 수 있는 첫 박스에 넣고, 들어갈 박스가 없으면 새 박스를 엽니다.

### 결론

| 항목 (다품목 주문 5,000건) | 치수만 판정 | 치수·무게 판정 |
| :-: | :-: | :-: |
| 20kg 넘는 박스가 나온 주문 | 689건 (13.8%) | **0건** |
| 박스 수 | 5,551개 | 6,036개 |

- **박스 수 증가**: 20kg을 넘던 박스(최대 45.7kg)를 나눠 담아 박스 수가 8.7% 늘었습니다.
- **계산 시간**: 주문 하나의 박스를 정하는 데 p95 13.8ms가 걸렸습니다(단일 스레드).

## 문제 2. 치수 추론 서빙과 모델 배포 판정

### 문제 배경

- 치수 추론 모델을 서빙할 인프라 구성이 필요했습니다.
- 추가 학습한 모델이 기존 모델보다 추론 정확도가 떨어지지 않는지 확인할 수 있어야 했습니다.

### 해결 과정

**서빙 인프라**

| 해결 방안 | 장점 | 단점 |
| :-: | :-: | :-: |
| GPU 인스턴스 상시 가동 | 추론 시간이 가장 짧습니다. | 치수 추론이 없는 시간에도 과금됩니다. |
| **Lambda 컨테이너 (채택)** | **호출한 만큼만 과금됩니다.** | **일정 시간 호출이 없으면 다음 호출에서 콜드스타트가 발생합니다.** |

- **응답 목표**: 작업자가 촬영한 뒤 화면에서 결과를 기다리므로, 추론 요청에 p95 1초 안에 응답해야 했습니다.
- **Lambda 선택 이유**: 모델을 ONNX로 변환해 Lambda에서 CPU로 추론한 결과, 웜 호출 p95는 609ms로 응답 목표를 충족했습니다. 입고는 작업 시간대에만 진행되므로, 이 시간대에 실행 환경을 미리 띄워 두면 콜드스타트(최대 9.5초)를 피할 수 있습니다. 따라서 상시 과금되는 GPU 인스턴스보다 비용이 적은 Lambda를 선택했습니다.

**배포 판정**

- **변환 대조**: ONNX 모델의 출력을 PyTorch 모델 출력과 비교해, 차이가 허용 오차를 넘으면 이미지 빌드를 멈춥니다.
- **정확도 평가**: 전처리가 다르면 같은 모델도 정확도가 달라지므로, GitHub Actions에서 고정 검증셋 2,024품목을 서비스와 같은 전처리로 평가합니다. 직전 모델보다 정확도가 떨어지면 서비스가 호출하는 Lambda 버전을 바꾸지 않습니다.

![모델 파이프라인. 빌드, 고정 검증셋 평가, Lambda 버전 전환](images/08-model-gate-actions.png)

### 결론

- **INT8 차단**: 가장 빠른 INT8 양자화 모델(164ms)은 오차 3cm 안에 드는 품목 비율이 62.5%에서 22.6%로 떨어져 배포되지 않았습니다.
- **배포 모델**: 정확도 평가를 통과한 경량화 모델이 없어, 양자화하지 않은 ONNX 모델을 배포했습니다.
