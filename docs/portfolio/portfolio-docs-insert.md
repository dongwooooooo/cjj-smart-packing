## 문제 1. 치수와 무게를 함께 보는 박스 판정

### 문제 배경

- **박스 추천 기능**: 포장 단계에서 주문 상품을 어떤 박스 몇 개에 나눠 담을지(이하 편성) 정해 작업자에게 추천해야 했습니다. 추천한 박스는 상품이 실제로 들어가고, 택배 접수 한도(무게 20kg, 세 변 합 160cm, 최장변 100cm)를 넘지 않아야 합니다.
- **부피 비교의 한계**: 부피 합만 비교하면 들어가지 않는 박스를 추천합니다. 안쪽 치수 30×30×30cm 박스에 25×25×20cm 상품 두 개는 부피로는 들어가지만, 어느 방향으로 놓아도 함께 들어가지 않습니다.
- **무게 한도 초과**: 치수만 보고 박스 수를 줄이면 무거운 상품이 한 박스에 몰립니다. 20kg을 넘는 박스는 택배로 접수되지 않아 현장에서 다시 나눠 담아야 합니다.

### 해결 과정

상품을 박스에 실제로 배치해 보고, 같은 판정에서 무게와 접수 한도도 검사합니다. 고른 기준은 두 가지였습니다. 추천한 박스에 상품이 실제로 들어가야 하고, 택배 접수 한도를 넘지 않아야 했습니다.

| 해결 방안 | 장점 | 단점 및 기각 사유 |
| :-: | :-: | :-: |
| 1. 부피·무게 합산 비교 | • 구현이 단순함 | • 부피로는 맞아도 실제로 들어가지 않는 박스를 추천함 |
| 2. 실제 배치로 치수만 판정 | • 들어가는 박스만 추천함 | • 박스 수를 줄이는 과정에서 20kg을 넘는 박스가 나옴 |
| **3. 실제 배치에 무게·접수 한도까지 판정 (최종 채택)** | **• 담기고 택배로 접수되는 박스만 추천함** | **• 나눠 담는 주문이 늘어 박스 수가 증가함<br>• 배치를 탐색으로 찾으므로 실제로는 담기는 조합을 놓칠 수 있음** |

**핵심 설계 결정**

- **배치로 치수 판정**: 상품을 6방향으로 돌려 가며 이미 놓인 상품 옆에 놓아 봅니다. 모든 상품이 놓인 박스만 후보로 남깁니다.
- **무게를 편성에 반영**: 담긴 무게가 20kg을 넘는 박스는 후보에서 뺍니다. 한 박스에 담기지 않으면 상품을 새 박스로 옮기는 편성까지 비교해, 총 택배 요금이 가장 적은 편성을 고릅니다. 박스 요금은 세 변 합 구간과 무게 구간 중 높은 쪽으로 매깁니다.

### 결론

무게를 판정에 넣어, 택배로 접수되지 않는 박스를 추천하지 않게 되었습니다.

| 항목 (다품목 주문 5,000건) | 치수만 판정 | 치수·무게 판정 |
| :-: | :-: | :-: |
| 20kg 넘는 박스가 나온 주문 | 689건 (13.8%) | **0건** |
| 박스 수 | 5,551개 | 6,036개 |

- **박스 수 증가**: 치수만 판정하면 최대 45.7kg 박스까지 나왔습니다. 이런 박스를 나눠 담으면서 박스 수가 8.7% 늘었습니다.
- **편성 시간**: 주문당 p95 13.8ms였습니다(단일 스레드).

## 문제 2. 치수 추론 서빙과 모델 배포 판정

### 문제 배경

- **GPU 상시 비용**: 치수 추론은 입고가 있을 때만 호출됩니다. GPU 서버를 상시 띄우면 호출이 없는 시간에도 비용이 나갑니다(g4dn.xlarge 기준 월 약 380달러).
- **정확도 판정 기준 부재**: 모델을 바꿀 때 서비스 환경에서 정확도가 떨어졌는지 판정할 기준이 없었습니다. 그래서 더 빠른 경량화 모델이 나와도 배포 여부를 정할 수 없었습니다.

### 해결 과정

**서빙 위치**

치수 추론은 Lambda 컨테이너에서 ONNX Runtime으로 CPU 추론합니다. 고른 기준은 두 가지였습니다. 응답 목표 1초 안에 들어와야 하고, 호출이 없는 시간에는 비용이 나가지 않아야 했습니다.

| 해결 방안 | 장점 | 단점 및 기각 사유 |
| :-: | :-: | :-: |
| 1. GPU 인스턴스 상시 가동 | • 추론이 가장 빠름 | • 입고가 없는 시간에도 비용 발생 |
| 2. API 서버 안에서 CPU 추론 | • 인프라 추가 없음 | • 2 vCPU에서 포장 요청과 CPU 경합<br>• Python 전처리를 Java로 재작성 |
| **3. Lambda 컨테이너 + ONNX Runtime (최종 채택)** | **• ONNX 변환으로 CPU 추론을 1.07초에서 185ms로 단축(로컬 측정)<br>• 호출한 만큼만 과금** | **• 콜드스타트 최대 9.5초** |

- **콜드스타트**: 실행 환경을 새로 띄우는 첫 호출은 최대 9.5초가 걸려 목표 1초를 넘습니다. Provisioned Concurrency로 사용 시간대에만 실행 환경 1개를 미리 띄워 두어 막았습니다.

**배포 판정**

고정 검증셋 평가를 통과한 모델만 서비스에 배포합니다.

- **평가 방식**: 전처리가 다르면 같은 모델도 정확도가 달라집니다. 그래서 GitHub Actions에서 검증셋 2,024품목을 서비스와 같은 전처리로 평가합니다.
- **통과 조건**: 아래 세 조건을 모두 만족하면 서비스가 호출하는 Lambda 버전을 새 모델로 전환합니다.
  - 가로·세로·높이별 평균 오차가 직전 모델보다 0.2cm 넘게 늘지 않을 것
  - ±3cm 이내 적중률이 직전 모델보다 2%p 넘게 떨어지지 않을 것
  - 가로·세로·높이별 평균 오차가 3cm 이하일 것

![모델 파이프라인. 빌드, 고정 검증셋 평가, Lambda 버전 전환](images/08-model-gate-actions.png)

### 결론

GPU 없이 추론을 서빙했고, 배포 판정이 정확도가 떨어진 모델을 자동으로 걸러냈습니다.

- **서빙 결과**: 웜 호출 246건의 Lambda 실행 시간 p95는 609ms였습니다.
- **INT8 차단**: 가장 빠른 INT8 양자화 모델(164ms)은 ±3cm 적중률이 62.5%에서 22.6%로 떨어져 판정에서 걸러졌습니다.
- **배포 모델**: 재학습 없이 통과한 경량화 모델이 없어, 양자화하지 않은 ONNX 모델을 배포했습니다.
