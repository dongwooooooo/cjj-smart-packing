## 시스템 아키텍처

![시스템 아키텍처](images/01-architecture.png)

**아키텍처 설계 이유**

- 입고 시각이 불규칙해 GPU 서버를 상시 가동하면(월 약 380달러) 유휴 비용이 컸습니다. PyTorch 모델을 ONNX로 변환해 CPU 추론을 1.07초에서 185ms로 줄였습니다. 치수 추론은 호출한 만큼만 과금되는 AWS Lambda 컨테이너에서 실행합니다(성과 2).
- 모델을 바꿀 때 나아졌는지 판정할 기준이 없었습니다. 그래서 GitHub Actions 빌드 안에서 고정 검증셋 2,024품목을 서비스 전처리 그대로 평가하고, 기준 안일 때만 Lambda 별칭을 옮기도록 했습니다. INT8 양자화 후보(164ms)는 ±3cm 적중률이 62.5%에서 22.6%로 떨어져 자동 차단됐습니다(성과 2).
- 학습 환경(OneFlow AI)과 서비스 환경(AWS)은 직접 연결하지 않고 Hugging Face의 가중치 파일만 주고받습니다. AI 담당은 서비스 코드를, 서비스 담당은 학습 환경 자격 증명을 다루지 않습니다.
- 배포는 GitHub Actions가 OIDC로 IAM 역할을 수임해 액세스 키 없이 하고, EC2 교체는 SSH 대신 SSM Run Command로 합니다. 헬스 체크 실패 시 이전 이미지로 자동 롤백합니다.
- 작업자 수십 명 규모라 API 서버는 EC2 1대에 Spring Boot 서버 하나로 두고, 동시 처리 한계는 부하 테스트로 확인했습니다(성과 1).
- 동시 포장에서 재고 행을 갱신하다 데드락이 발생했습니다. RDS(PostgreSQL)의 재고는 수량을 갱신하지 않고 변동 행만 추가하는 원장(append-only ledger)으로 바꿔 잠글 대상을 없앴습니다(성과 1).
- 촬영 사진은 S3에 저장합니다. 커밋 뒤 비동기로 올리던 사진이 부하 중에 유실돼, 추론과 병렬로 올리고 둘 다 끝나야 응답하도록 바꿨습니다. 같은 부하에서 저장되지 않은 사진이 27장에서 0장으로 줄었습니다.
- 개인 고도화에서 Prometheus·Grafana·k6를 추가해 커넥션 풀, Tomcat 스레드, DB 대기 이벤트를 보며 부하 테스트를 반복했습니다.

## 성과 1. 재고 원장 전환으로 동시 포장 데드락 제거

### 문제 배경

- 포장 완료는 박스에 담긴 상품 행을 하나씩 잠그고 재고 수량을 줄이는 구조였습니다. 박스마다 잠그는 순서가 달라 동시 포장에서 데드락이 발생했습니다.
- 잠금 전에 읽어 둔 수량을 기준으로 저장해 갱신 손실도 함께 생겼습니다. 재고 감소분이 포장 건수의 절반만 반영됐습니다.
- 락을 기다리는 요청이 커넥션 풀(10개)을 점유해, 락과 무관한 조회까지 최대 10.5초를 기다렸습니다.
- 포장 작업자 50명 동시 부하(k6, 3분)에서 에러율 40.4%, 포장 완료 p95 10초 이상(프론트엔드 요청 타임아웃), 데드락 356건이 측정됐습니다.

![개선 전 포장 50명 부하. 포장 완료 p95 10초, 에러율 40.4%, 커넥션 대기 39](images/02-packing-before.png)

### 해결 과정

| 해결 방안 | 장점 | 단점 |
| :-: | :-: | :-: |
| 원자적 갱신과 상품 ID 순 잠금 | 데드락과 갱신 손실을 제거합니다. | 상품 수만큼 락은 그대로 남고, 변동 이력이 없습니다. |
| 낙관적 락 | 락 없이 버전 비교로 충돌을 감지합니다. | 동시 요청이 많을수록 재시도가 늘고, 변동 이력이 없습니다. |
| **재고 원장** | **수량을 고치지 않고 변동 행만 추가해 잠글 대상 자체가 없습니다. 모든 변동이 한 곳에 남습니다.** | **현재 수량을 읽는 집계 구조가 필요합니다.** |

- 원자적 갱신과 상품 ID 순 잠금은 데드락은 막지만 상품 락 대기가 처리량 상한으로 남습니다. 재고 불일치가 생겼을 때 추적할 이력도 없어 제외했습니다.
- 현재 수량은 5초마다 갱신하는 스냅샷에 아직 집계되지 않은 원장 행을 더해 읽습니다. 커밋 순서가 어긋나 건너뛴 행은 60초마다 전체 대조로 잡습니다.
- 재고 부족 판정은 주문 접수 단계에서만 합니다. 포장대에 온 상품은 이미 꺼낸 실물이라 포장 완료에서는 판정하지 않습니다.

### 결론

재고 행을 갱신하지 않으므로 데드락과 갱신 손실이 구조적으로 발생하지 않습니다. 원장이 105만 행까지 쌓이자 집계 쿼리가 상품마다 원장을 풀 스캔했습니다. 인덱스 범위 스캔으로 바꿔 3.39초를 0.66ms로 줄였습니다. 커넥션 풀은 실측 결과에 따라 10개를 유지했습니다. 커넥션 획득 타임아웃만 30초에서 3초로 내려 락 대기가 화면 멈춤으로 번지지 않게 했습니다.

그 결과 같은 부하(포장 작업자 50명, 3분)에서 에러율 40.4%에서 0%, 포장 완료 p95 10초 이상에서 73ms, 처리량 초당 2.9건에서 32.6건으로 개선했습니다.

![개선 후 포장 50명 부하. 포장 완료 p95 73ms, 에러율 0%, 커넥션 대기 0](images/03-packing-after.png)

## 성과 2. 치수 추론을 Lambda로 옮기고 정확도 게이트로 배포

### 문제 배경

- 팀 초기 설계는 GPU 서버(g4dn.xlarge) 상시 가동이었습니다. 입고 시각이 불규칙해 대부분의 시간이 유휴인데도 월 약 380달러가 드는 설계였습니다.
- 모델을 바꿀 때 나아졌는지 판정할 기준이 없었습니다. 학습 리포트의 수치는 검증 분할과 전처리가 서비스와 달라 그대로 쓸 수 없었습니다.
- 학습은 격리된 OneFlow AI 환경에서 하고 서비스는 AWS에 있었습니다. 두 환경을 직접 연결하지 않고 모델을 전달할 경로가 필요했습니다.

### 해결 과정

| 해결 방안 | 장점 | 단점 |
| :-: | :-: | :-: |
| GPU 인스턴스 상시 가동 | 추론 시간이 가장 짧습니다. | 월 약 380달러. 입고가 없는 시간에도 비용이 나갑니다. |
| API 서버 안에서 CPU 추론 | 인프라가 단순합니다. | 2 vCPU에서 포장 요청과 CPU를 두고 경합하고, Python 전처리를 Java로 다시 써야 합니다. |
| **Lambda 컨테이너(ONNX Runtime)** | **PyTorch 모델을 ONNX로 변환해 CPU 추론 1.07초를 185ms로 줄였습니다. 호출한 만큼만 과금되고 동시 촬영 수만큼 확장됩니다.** | **콜드스타트가 최대 9.5초입니다.** |

- 콜드스타트는 시연 시간대에만 실행 환경 1개를 예약(Provisioned Concurrency)해 막았습니다. 8시간 예약에 하루 약 0.4달러입니다.
- 학습 환경과 서비스는 Hugging Face 비공개 저장소의 가중치 파일로만 연결했습니다. GitHub Actions가 이미지 빌드 안에서 ONNX로 변환하고 PyTorch 출력과 대조(최대 오차 1e-4)한 뒤 ECR로 보냅니다.
- 배포 여부는 고정 검증셋 2,024품목을 서비스 전처리 그대로 평가해 판정합니다. 직전 모델 대비 평균 절대 오차 +0.2cm, ±3cm 적중률 −2%p 안(절대 상한 3cm)일 때만 Lambda 별칭을 옮깁니다.

![모델 파이프라인. 빌드, 고정 검증셋 정확도 검증, Lambda 갱신 3단계 통과](images/08-model-gate-actions.png)

### 결론

GPU 없이 CPU 추론 185ms로 서빙해 상시 가동 비용을 없앴습니다. 시연 기간 Lambda 핸들러 p95는 609ms(319건 중 배포 검증·콜드스타트를 뺀 246건, 목표 1초)였습니다.

속도만 보면 INT8 양자화 후보(164ms)가 가장 빨랐지만, ±3cm 적중률이 62.5%에서 22.6%로 떨어져 정확도 게이트에서 자동 차단됐습니다. 재학습 없이 통과하는 경량화 후보가 없어 기준 모델을 배포했습니다.

GPU 상시 비용 제거, 배포 전 정확도 자동 판정
