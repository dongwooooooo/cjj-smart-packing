## 문제 1. 치수와 무게를 함께 보는 박스 판정

### 문제 배경

- **박스 추천 기능**: 포장 단계에서 주문 상품을 담을 박스와 개수를 정해 작업자에게 추천해야 했습니다. 추천한 박스에는 상품이 들어가야 하고, 택배 접수 한도(무게 20kg, 세 변 합 160cm, 최장변 100cm)를 넘지 않아야 합니다.
- **부피 비교의 한계**: 부피 합만 비교하면 상품이 들어가지 않는 박스를 추천합니다. 25×25×20cm 상품 두 개의 부피 합은 30×30×30cm 박스보다 작습니다. 그런데 두 상품을 나란히 놓으려면 한 변이 40cm 이상 필요해 박스에 들어가지 않습니다.
- **무게 한도 초과**: 치수만 보고 박스 수를 줄이면 무거운 상품이 한 박스에 몰립니다. 20kg을 넘는 박스는 택배로 접수되지 않아 현장에서 다시 나눠 담아야 합니다.

### 해결 과정

상품을 박스 안에 하나씩 배치하고, 같은 판정에서 무게와 택배 접수 한도도 검사합니다.

| 해결 방안 | 장점 | 단점 및 기각 사유 |
| :-: | :-: | :-: |
| 1. 부피·무게 합산 비교 | • 구현이 단순함 | • 상품이 들어가지 않는 박스를 추천함 |
| 2. 배치로 치수만 판정 | • 상품이 들어가는 박스만 추천함 | • 20kg을 넘는 박스를 추천함 |
| **3. 배치로 치수를 판정하고 무게·접수 한도도 검사 (최종 채택)** | **• 상품이 들어가고 택배로 접수되는 박스만 추천함** | **• 나눠 담는 주문이 늘어 박스 수가 증가함<br>• 모든 배치를 시험하지 않아, 담을 수 있는 박스를 놓치는 경우가 있음** |

**핵심 설계 결정**

- **배치로 치수 판정**: 상품을 하나씩 6방향으로 돌려 빈 자리에 놓습니다. 모든 상품이 들어간 박스만 후보로 둡니다.
- **무게와 요금으로 박스 선택**: 담긴 무게가 20kg을 넘는 박스는 후보에서 뺍니다. 한 박스에 다 담을 수 없으면 여러 박스로 나누는 경우도 비교해, 택배 요금 합이 가장 적은 조합을 고릅니다. 박스 요금은 세 변 합 구간과 무게 구간 중 높은 쪽으로 계산합니다.

### 결론

20kg을 넘는 박스를 추천하던 주문이 13.8%에서 0건이 되었습니다.

| 항목 (다품목 주문 5,000건) | 치수만 판정 | 치수·무게 판정 |
| :-: | :-: | :-: |
| 20kg 넘는 박스가 나온 주문 | 689건 (13.8%) | **0건** |
| 박스 수 | 5,551개 | 6,036개 |

- **박스 수 증가**: 20kg을 넘던 박스(최대 45.7kg)를 나눠 담아 박스 수가 8.7% 늘었습니다.
- **계산 시간**: 주문 하나의 박스를 정하는 데 p95 13.8ms가 걸렸습니다(단일 스레드).

## 문제 2. 치수 추론 서빙과 모델 배포 판정

### 문제 배경

- **GPU 상시 비용**: 치수 추론은 입고가 있을 때만 호출됩니다. GPU 서버를 상시 띄우면 호출이 없는 시간에도 비용이 나갑니다(g4dn.xlarge 기준 월 약 380달러).
- **배포 기준 없음**: 모델을 바꿀 때 서비스 환경에서 정확도가 떨어졌는지 판정할 기준이 없었습니다. 그래서 더 빠른 경량화 모델이 나와도 배포 여부를 정할 수 없었습니다.

### 해결 과정

**서빙 위치**

추론 응답은 1초 안에 와야 했고, 호출이 없는 시간에는 비용이 나가지 않아야 했습니다. 그래서 Lambda 컨테이너에서 ONNX Runtime으로 CPU 추론합니다.

| 해결 방안 | 장점 | 단점 및 기각 사유 |
| :-: | :-: | :-: |
| 1. GPU 인스턴스 상시 가동 | • 추론이 가장 빠름 | • 입고가 없는 시간에도 비용 발생 |
| 2. API 서버 안에서 CPU 추론 | • 인프라 추가 없음 | • 2 vCPU에서 포장 요청과 CPU 경합<br>• Python 전처리를 Java로 재작성 |
| **3. Lambda 컨테이너 + ONNX Runtime (최종 채택)** | **• ONNX 변환으로 CPU 추론을 1.07초에서 185ms로 단축(로컬 측정)<br>• 호출한 만큼만 과금** | **• 콜드스타트 최대 9.5초** |

- **콜드스타트**: 실행 환경을 새로 띄우는 첫 호출은 최대 9.5초가 걸려 목표 1초를 넘습니다. Provisioned Concurrency로 사용 시간대에만 실행 환경 1개를 미리 띄워 두어 막았습니다.

**배포 판정**

고정 검증셋 평가를 통과한 모델만 서비스에 배포합니다.

- **평가 방식**: 전처리가 다르면 같은 모델도 정확도가 달라집니다. 그래서 GitHub Actions에서 검증셋 2,024품목을 서비스와 같은 전처리로 평가합니다.
- **통과 조건**: 아래 세 조건을 모두 만족하면 서비스가 호출하는 Lambda 버전을 새 모델로 전환합니다.
  - 가로·세로·높이별 평균 오차가 직전 모델보다 0.2cm 넘게 늘지 않을 것
  - ±3cm 이내 적중률이 직전 모델보다 2%p 넘게 떨어지지 않을 것
  - 가로·세로·높이별 평균 오차가 3cm 이하일 것

![모델 파이프라인. 빌드, 고정 검증셋 평가, Lambda 버전 전환](images/08-model-gate-actions.png)

### 결론

GPU 없이 추론을 서빙했고, 정확도가 떨어진 모델은 배포 전에 자동으로 걸렀습니다.

- **서빙 결과**: 웜 호출 246건의 Lambda 실행 시간 p95는 609ms였습니다.
- **INT8 차단**: 가장 빠른 INT8 양자화 모델(164ms)은 ±3cm 적중률이 62.5%에서 22.6%로 떨어져 배포되지 않았습니다.
- **배포 모델**: 재학습 없이 통과한 경량화 모델이 없어, 양자화하지 않은 ONNX 모델을 배포했습니다.
