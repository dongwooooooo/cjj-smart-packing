## 시스템 아키텍처

![시스템 아키텍처](images/01-architecture.png)

**아키텍처 설계 이유**

- 빌드 단계에서 ONNX 변환과 출력 대조를 마친 이미지만 ECR에 올립니다. 학습(PyTorch)과 서비스(ONNX Runtime)의 출력이 어긋나면 배포 뒤에야 드러나기 때문입니다.
- 치수 추론은 GPU 서버 대신 호출한 만큼 과금되는 Lambda에서 실행합니다. 입고가 있을 때만 호출되고, CPU로도 응답 목표 1초를 맞출 수 있습니다(문제 2).
- Lambda는 공개 URL 없이 EC2의 IAM 역할로만 호출할 수 있습니다. API 서버를 거치지 않은 추론 요청은 들어올 수 없습니다.

## 문제 1. 서버 부하 테스트 후 장애 문제 해결

### 성능 테스트

**테스트 목적**

예상 트래픽을 안전하게 처리할 수 있는지 확인하고, DB I/O가 몰릴 때 생기는 문제를 파악하기 위해 성능 테스트를 진행했습니다.

**테스트 환경**

- 서버: EC2 2 vCPU 1대, Spring Boot, 커넥션 풀 10
- DB: RDS PostgreSQL
- 도구: k6(부하 발생), Grafana(지표 확인)

**테스트 시나리오**

- 대상: 포장 프로세스(운반함 스캔, 주문 상세 조회, 포장 완료)
- 부하: 작업자 10명, 50명 동시 작업, 각 3분
- 판정 기준: 포장 완료 p95 500ms 이하, 실패율 1% 미만

**테스트 결과**

작업자 10명부터 판정 기준을 넘었고, 50명에서는 포장 완료의 40.4%가 실패했습니다.

| 항목 | 작업자 10명 | 작업자 50명 |
| :-: | :-: | :-: |
| 포장 완료 실패율 | 12.1% | **40.4%** |
| 포장 완료 p95 | 3.0초 | **10.1초** |
| 초당 포장 완료 | 5.4건 | 2.9건 |
| 스캔·상세 조회 p95 | 0.1초 | 5~6초 |
| EC2 CPU | 10% | 6% |
| 커넥션 풀 사용 / 대기 | 8 / 0 | 10 / 39 |
| DB 락 대기 세션 | 6 | 10 |

![개선 전, 작업자 50명](images/02-packing-before.png)

### 문제 배경

- **공용 자원 대기**: 작업자를 5배로 늘리자 처리량은 오히려 절반으로 줄었고, 락을 잡지 않는 조회까지 5초 넘게 걸렸습니다. CPU는 6%로 한가했지만 커넥션 10개가 모두 PostgreSQL 안에서 행 락을 기다렸고, 그 뒤로 요청 39개가 커넥션을 기다렸습니다.
- **데드락 확인**: 락 대기 시간 제한이 없는데도 요청이 실패했다면 DB가 트랜잭션을 끊었다는 뜻입니다. 서버 로그와 `pg_stat_database`에서 데드락 356건을 확인했습니다.
- **데드락 원인**: 포장 완료는 주문에 담긴 상품의 재고 행을 주문에 적힌 순서대로 잠갔습니다. 주문마다 상품 순서가 달라, 두 작업자가 같은 두 상품을 반대 순서로 잠그면 서로의 락을 기다렸습니다.
- **다른 요청까지 막힌 이유**: PostgreSQL이 데드락을 끊기 전까지 두 트랜잭션은 커넥션을 반환하지 않습니다. 이런 트랜잭션이 커넥션 10개를 모두 차지해, 락과 무관한 조회도 커넥션을 받지 못했습니다.

### 해결 과정

재고 수량을 직접 고치는 대신 변동을 기록하는 원장 방식으로 바꿨습니다. 고른 기준은 두 가지였습니다. 데드락이 생기지 않아야 하고, 재고가 실물과 어긋났을 때 어느 포장에서 틀렸는지 거슬러 찾을 수 있어야 했습니다.

| 해결 방안 | 장점 | 단점 및 기각 사유 |
| :-: | :-: | :-: |
| 1. 커넥션 풀 늘리기 | • 코드 변경 없음 | • DB 안에서 같은 행을 기다리는 트랜잭션만 늘어남 |
| 2. 상품 ID 순으로 잠그기 | • 순환 대기 제거 | • 상품마다 행 락과 대기는 그대로<br>• 재고 변동 이력이 없어 불일치 추적 불가 |
| 3. 낙관적 락(버전 컬럼) | • 행 락 없이 충돌 감지 | • 동시 요청이 많을수록 재시도 급증<br>• 변동 이력 없음 |
| 4. 데드락 시 재시도 | • 코드 변경 최소 | • 원인이 남아 부하가 커지면 재발 |
| **5. 재고 원장 (최종 채택)** | **• 잠그는 상품 행이 없어 데드락 불가<br>• 모든 변동이 기록돼 불일치 추적 가능** | **• 현재 수량을 계산하는 집계 필요** |

**핵심 설계 결정**

- **수량 대신 변동 기록**: 포장 완료는 상품 행을 수정하지 않고, 재고 변동을 쌓는 테이블(원장)에 "−1" 행만 추가합니다. 여러 작업자가 같은 상품을 동시에 포장해도 각자 새 행을 쓰므로 서로 기다릴 행이 없습니다.
- **현재 수량 계산**: 조회할 때마다 원장 전체를 합산하면 원장이 쌓일수록 느려집니다. 그래서 5초마다 상품별 합계를 집계표에 저장하고, 조회 때는 그 뒤 추가된 원장 행만 더합니다. 커밋 순서가 어긋나 집계에서 빠진 행은 60초마다 전체 대조로 보정합니다.

### 결론

같은 부하에서 데드락과 실패가 모두 사라졌습니다.

| 항목 (작업자 50명, 3분) | 개선 전 | 개선 후 |
| :-: | :-: | :-: |
| 포장 완료 실패율 | 40.4% | **0%** |
| 포장 완료 p95 | 10.1초 | **73ms** |
| 초당 포장 완료 | 2.9건 | **32.6건** |
| 스캔·상세 조회 p95 | 5~6초 | 41ms 이하 |
| 데드락 | 356건 | 0건 |
| 커넥션 풀 대기 / DB 락 대기 세션 | 39 / 10 | 0 / 2 |

![개선 후, 같은 부하](images/03-packing-after.png)

- **지연 해소**: 포장 완료가 상품 행을 잠그지 않게 되면서 커넥션을 오래 점유하던 트랜잭션이 사라졌습니다. 커넥션 대기도 0이 되어 락과 무관하던 조회도 41ms 이하로 돌아왔습니다.
- **갱신 손실 발견**: 원장으로 옮기며 기존 재고를 포장 기록과 대조하자, 재고가 포장 수량의 절반만 줄어 있었습니다. JPA가 잠금 전에 읽어 둔 상품 객체를 그대로 돌려줬기 때문입니다. 그래서 포장 완료는 락을 잡고도 옛 수량으로 재고를 저장했습니다.
- **복구**: 원장에 변동 기록이 모두 남아 있어 재고를 다시 계산할 수 있었습니다.

## 문제 2. 치수 추론 서빙과 모델 배포 판정

치수 추론을 GPU 없이 Lambda에서 p95 609ms로 서빙하고, 배포 전 정확도 판정으로 정확도가 떨어진 모델을 자동으로 걸러냈습니다.

### 문제 배경

- GPU 서버를 상시 띄우면 호출이 없는 시간에도 비용이 나갑니다(g4dn.xlarge 기준 월 약 380달러). 치수 추론은 입고가 있을 때만 호출됩니다.
- 모델을 바꿀 때 서비스 환경에서 정확도가 나아졌는지 판정할 기준이 없었습니다.

### 해결 과정

**서빙 위치**

Lambda 컨테이너에서 ONNX Runtime으로 CPU 추론합니다.

| 해결 방안 | 장점 | 단점 및 기각 사유 |
| :-: | :-: | :-: |
| 1. GPU 인스턴스 상시 가동 | • 추론이 가장 빠름 | • 입고가 없는 시간에도 비용 발생 |
| 2. API 서버 안에서 CPU 추론 | • 인프라 추가 없음 | • 2 vCPU에서 포장 요청과 CPU 경합<br>• Python 전처리를 Java로 재작성 |
| **3. Lambda 컨테이너 + ONNX Runtime (최종 채택)** | **• ONNX 변환으로 CPU 추론을 1.07초에서 185ms로 단축(로컬 측정)<br>• 호출한 만큼만 과금** | **• 콜드스타트 최대 9.5초** |

콜드스타트는 사용 시간대에만 실행 환경 1개를 미리 띄워 두는 Provisioned Concurrency로 막았습니다.

**배포 판정**

고정 검증셋 평가를 통과한 모델만 서비스에 배포합니다. GitHub Actions에서 2,024품목을 서비스와 같은 전처리로 평가하고, 아래 조건을 모두 만족하면 서비스가 호출하는 Lambda 버전으로 전환합니다.

- 가로·세로·높이별 평균 오차가 직전 모델보다 0.2cm 넘게 늘지 않을 것
- ±3cm 이내 적중률이 직전 모델보다 2%p 넘게 떨어지지 않을 것
- 가로·세로·높이별 평균 오차가 3cm 이하일 것

![모델 파이프라인. 빌드, 고정 검증셋 평가, Lambda 버전 전환](images/08-model-gate-actions.png)

### 결론

GPU 없이 서빙했고, 실제 호출 246건(콜드스타트 제외)의 Lambda 처리 시간 p95는 609ms로 목표 1초 안이었습니다.

배포 판정이 가장 빠른 INT8 양자화 모델(164ms)을 자동으로 걸러냈습니다. ±3cm 적중률이 62.5%에서 22.6%로 떨어졌기 때문입니다. 재학습 없이 통과한 경량화 모델이 없어 양자화하지 않은 ONNX 모델을 배포했습니다.
