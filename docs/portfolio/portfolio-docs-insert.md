## 시스템 아키텍처

![시스템 아키텍처](images/01-architecture.png)

**아키텍처 설계 이유**

- 입고 시각이 불규칙해 GPU 서버 상시 가동(월 약 380달러)은 유휴 비용이 컸습니다. PyTorch 모델을 ONNX로 변환해 CPU 추론을 1.07초에서 185ms로 줄이고, 치수 추론은 AWS Lambda 컨테이너에서 호출한 만큼만 과금되도록 구성했습니다.
- 모델을 바꿀 때 나아졌는지 판정할 기준이 없어, GitHub Actions 빌드 안에서 고정 검증셋 2,024품목을 서비스 전처리 그대로 평가하고 기준 안일 때만 Lambda 별칭을 옮기도록 했습니다. 가장 빠른 INT8 후보(164ms)는 적중률 62.5%에서 22.6% 하락으로 자동 차단됐습니다.
- 학습 환경(OneFlow AI)과 서비스 환경(AWS)은 직접 연결하지 않고 Hugging Face의 가중치 파일만 주고받습니다. AI 담당은 서비스 코드를, 서비스는 학습 환경 자격 증명을 다루지 않습니다.
- 배포는 GitHub Actions가 OIDC로 AWS 역할을 맡아 액세스 키 없이 하고, EC2 교체는 SSH 대신 SSM Run Command로 합니다. 헬스 체크 실패 시 이전 이미지로 자동 복귀합니다.
- 작업자 수십 명 규모라 API 서버는 EC2 1대의 Spring Boot 단일 서버로 두고, 동시 처리 한계는 부하 테스트로 확인했습니다(성과 1).
- 동시 포장에서 재고 행 갱신이 데드락을 냈습니다. RDS(PostgreSQL)의 재고는 수량을 갱신하지 않고 변동 행만 추가하는 원장으로 바꿔 잠글 대상을 없앴습니다(성과 1).
- 촬영 사진은 S3에 저장하되, 커밋 뒤 비동기 업로드가 부하에서 유실돼 추론과 병렬로 올리고 둘 다 끝나야 응답하도록 했습니다. 같은 부하에서 미저장 사진 27장에서 0장.
- 개인 고도화에서 Prometheus·Grafana·k6를 추가해 커넥션 풀, Tomcat 스레드, DB 대기 이벤트를 보며 부하 테스트를 반복했습니다.

## 성과 1. 재고 원장 전환으로 동시 포장 데드락 제거

### 문제 배경

- 포장 완료는 박스에 담긴 상품 행을 하나씩 잠그고 재고 수량을 줄이는 구조였습니다. 박스마다 잠그는 순서가 달라 동시 포장에서 데드락이 발생했습니다.
- 잠금 전에 읽어 둔 수량으로 갱신해 갱신 손실도 함께 생겼습니다. 재고 감소분이 포장 건수의 절반만 반영됐습니다.
- 락 대기가 커넥션 풀(10개)을 점유해 락과 무관한 조회까지 최대 10.5초 기다렸습니다.
- 포장 작업자 50명 동시 부하(k6, 3분)에서 에러율 40.4%, 포장 완료 p95 10초 이상(프론트 타임아웃), 데드락 356건이 측정됐습니다.

![개선 전 포장 50명 부하. 응답 p95 10초, 실패율 40%, 커넥션 대기 39](images/02-packing-before.png)

### 해결 과정

| 해결 방안 | 장점 | 단점 |
| :-: | :-: | :-: |
| 원자적 갱신과 상품 ID 순 잠금 | 데드락과 갱신 손실을 제거합니다. | 상품 수만큼 락은 그대로 남고, 변동 이력이 없습니다. |
| 낙관적 락 | 락 없이 버전 비교로 충돌을 감지합니다. | 동시 요청이 많을수록 재시도가 늘고, 변동 이력이 없습니다. |
| **재고 원장(append-only ledger)** | **수량을 고치지 않고 변동 행만 추가해 잠글 대상 자체가 없습니다. 모든 변동이 한 곳에 남습니다.** | **현재 수량을 읽는 집계 구조가 필요합니다.** |

- 락 순서 통일은 데드락은 막지만 상품 락 대기가 처리량 상한으로 남고, 재고 불일치가 났을 때 추적할 이력이 없어 제외했습니다.
- 현재 수량은 5초마다 갱신하는 스냅샷에 아직 집계되지 않은 원장 행을 더해 읽습니다. 커밋 순서가 어긋나 건너뛴 행은 60초마다 전체 대조로 잡습니다.
- 재고 부족 판정은 주문 접수 단계에서만 합니다. 포장대에 온 상품은 이미 꺼낸 실물이라 포장 완료에서는 판정하지 않습니다.

### 결론

재고 수량을 갱신하는 행 자체를 없애, 데드락과 갱신 손실이 구조적으로 발생하지 않습니다. 원장이 105만 행까지 쌓이면 집계 쿼리가 상품마다 원장을 풀 스캔하는 문제는 인덱스 범위 스캔으로 고쳐 3.39초에서 0.66ms로 줄였습니다. 커넥션 풀은 실측으로 10개를 유지하고 타임아웃만 30초에서 3초로 내려, 락 대기가 화면 멈춤으로 번지지 않게 했습니다.

그 결과 같은 부하(포장 작업자 50명, 3분)에서 에러율 40.4%에서 0%, 포장 완료 p95 10초 이상에서 73ms, 처리량 초당 2.9건에서 32.6건으로 개선했습니다.

![개선 후 포장 50명 부하. 응답 p95 73ms, 실패 0, 커넥션 대기 0](images/03-packing-after.png)
