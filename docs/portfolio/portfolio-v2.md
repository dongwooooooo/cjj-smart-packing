### 아키텍처 설계 이유

1. **치수 추론은 GPU 서버 대신 Lambda(CPU)에 두었습니다.**
   - API 서버 안에서 CPU 추론하는 안은 기각했습니다. 2 vCPU 서버에서 추론이 포장 요청과 CPU를 경합하기 때문입니다. 디코딩·전처리 코드가 Python이라 API 서버에 넣으려면 다시 써야 하고, 모델 배포 주기도 서버 배포와 분리할 수 없습니다. 상시 CPU 인스턴스를 따로 두는 안은 입고 시각이 불규칙해 유휴 시간 비용이 듭니다. 인스턴스 운영도 하나 늘어 기각했습니다.
   - 비용: 운영에서는 Lambda가 GPU 상시 가동보다 쌉니다. 시연처럼 시간대가 정해져 있으면 GPU도 그 시간만 켤 수 있지만, 운영에서 입고 시각은 불규칙합니다. GPU 인스턴스는 켜 둔 시간 전체만큼 비용이 듭니다(g4dn.xlarge 온디맨드 시간당 0.526달러, 상시 가동 시 월 약 380달러, instances.vantage.sh). Lambda는 호출한 만큼만 비용이 듭니다(시연 기간 호출 319건은 1센트 수준, aws.amazon.com/lambda/pricing). 이 단가면 운영 호출이 월 100만 건이어도 약 30달러이고, 24시간 예약(8시간 예약 하루 0.4달러의 3배인 1.2달러 × 30일 = 월 약 36달러)을 더해도 GPU 상시 가동보다 낮습니다.
   - 추론 시간: 모델을 ONNX로 변환하고 ONNX Runtime에서 실행해 CPU 추론 시간을 1.07초(PyTorch)에서 185ms로 줄였습니다(로컬 CPU, 모델 실행만).
   - 콜드스타트: 최대 9.5초라 시연 시간대 8시간에만 미리 띄워 둔 실행 환경(Provisioned Concurrency)을 예약했습니다. 배포 직후에는 웜업 호출을 넣었습니다(24시간 운영은 더 개선할 부분 6).
   - 목표 대비 실측: 촬영 응답 목표는 팀에서 정한 p95 1초입니다. 그중 Lambda 몫인 핸들러 시간은 시연 기간 호출 중 배포 검증일과 콜드스타트를 뺀 정상 상태 호출 246건에서 p95 609ms였습니다(디코딩·전처리 포함). 이 호출의 사진은 한 장을 세 번 복제한 82~353KB 측정용 파일이었고, 실제 3뷰 원본(5~9KB)으로 바꾼 뒤의 촬영 응답 전체 p95는 이보다 낮습니다(Problem 4 결과 표).
2. **재고는 현재 수량을 갱신하지 않고 변동을 원장에 쌓습니다.** (Problem 1)
3. **박스 편성은 부피 비교 대신 3D 빈 패킹(3D Bin Packing) 시뮬레이션으로 판정하고, 총 배송비를 최소화합니다.** (Problem 3)
4. **촬영 사진 업로드는 추론과 병렬로 실행하고, 둘 다 끝나면 응답합니다.** (Problem 4)
5. **모델은 자동 검증을 통과한 것만 배포합니다.** (Problem 5)
6. **API 서버는 1대입니다.** 가정한 포장 피크를 1대가 대기 없이 처리해(Problem 2 결과 표), 이중화는 무중단 배포가 필요해질 때로 미뤘습니다(더 개선할 부분 5).

## 부하 테스트 v1 ~ v5

**목적.** 창고 규모의 동시 작업에서 어디서 먼저 병목이 생기는지 찾기 위해 수행했습니다. 시연은 작업자 1명이었습니다.

**도구·환경.** 수집 지표는 응답 시간, 커넥션 풀, Tomcat 작업 스레드, DB 대기 이벤트(wait event)입니다. API 서버 EC2(2 vCPU), DB RDS(2 vCPU, 메모리 1GB). 프론트엔드 타임아웃은 10초입니다. 시나리오는 작업자 행동 단위로, 촬영은 "촬영 버튼 → 결과 확인", 포장은 "토트(상품을 담아 옮기는 운반함) 스캔 → 주문 확인 → 포장 완료"입니다. 촬영·포장 테스트(v1·v3·v4)는 작업자가 1건을 끝내고 1초 뒤 다음 건을 시작하는 방식입니다. 포장은 요청 3개에 평균 100ms가 걸려 사이클이 약 1.1초입니다(작업자 1명이 분당 약 55건). 촬영은 응답 약 450ms로 사이클이 약 1.5초입니다(분당 약 40건). 현장 속도(작업자당 분당 1~2건, 가정)의 20~55배입니다.

## Problem 1. 동시 포장 시 재고 갱신 데드락과 원장 전환

**[문제배경]**
포장 작업자 50명이 동시에 포장 완료를 누르자 요청의 40.4%가 실패했습니다(10명에서는 12.1%). 포장 완료는 박스 1개 단위로 처리되며, 그 박스에 담긴 상품마다 락을 걸고 재고 수량을 1씩 줄입니다. 박스마다 상품을 잠그는 순서가 달라 데드락이 발생했습니다.

같은 테스트에서 재고 감소분이 실제 포장 건수의 절반만 반영됐습니다(갱신 손실). 락은 잡혔지만 갱신에 쓴 값이 락 이전에 읽어 둔 값이었습니다.

테스트 준비 중에는 관리자 재고 조정이 별도 이력에만 기록되고 수량에는 반영되지 않는 문제도 나왔습니다(재고 이중 기록). 조정으로 늘린 재고가 수량에서는 0으로 남아 주문 접수가 전부 거절됐습니다.

**[접근법]**

| 방안 | 평가 |
| :-: | :-: |
| 단일 쿼리로 원자적 갱신 + 락 획득 순서 통일 | 데드락과 갱신 손실은 막힘. 박스 자재(포장에 쓰는 박스) 재고 락 위에 상품 수만큼 락이 더해져 트랜잭션당 락 보유가 그대로임. 변동 이력을 따로 두면 수량과 이력 두 곳을 항상 함께 맞춰야 하고, 문제배경의 이중 기록이 그 경로 하나가 빠진 사례 |
| 낙관적 락(Optimistic Lock) | 잠그지 않고 갱신 시 충돌을 감지해 재시도. 스트레스 부하에서는 재시도가 늘어나고, 변동 이력이 없어 불일치 추적 문제가 그대로 남음 |
| **원장** | 수량을 고치지 않고 "−1" 같은 변동을 한 줄씩 추가. 상품 락 없음. 대가: 현재 수량을 읽는 집계 구조, 원장 행의 커밋 시간 전제, 원장 보관 정책 |

두 안은 실측하지 않고 기각했습니다. 이중 기록은 어느 안이든 관리자 조정 경로를 고쳐야 없어집니다.

채택안에서 현재 수량은 5초마다 원장을 집계해 둔 스냅샷에, 아직 집계되지 않은 원장 행을 더해 읽습니다. 집계는 원장 행의 ID 순서로 진행하는데, ID는 앞이지만 커밋이 늦은 행이 있으면 건너뛰게 됩니다. 그래서 기록된 지 60초가 지난 행만 집계 대상으로 하고, 원장 행이 60초 안에는 커밋된다고 전제합니다. 60초마다 스냅샷과 원장 전체를 대조해 어긋나면 다시 계산합니다(원장 105만 건 기준 300ms). 전제를 벗어나 건너뛴 행도 이 대조로 최대 60초 안에 반영되지만, 그 60초 동안은 조회값이 틀립니다(더 개선할 부분 3).

재고 부족 판정은 주문 접수 단계에서 이 값으로 하고, 포장 완료에서는 하지 않습니다. 포장대에 온 상품은 이미 창고에서 꺼낸 실물이기 때문입니다. 접수는 재고를 예약하지 않고 현재 수량만 읽으므로, 포장으로 차감되기 전에 들어온 다음 접수가 같은 재고를 다시 받을 수 있습니다. 전환 전에도 같았습니다(더 개선할 부분 4).

포장 완료는 박스 상태가 "포장 중"일 때만 받습니다. 상태 변경과 원장 기록을 한 트랜잭션으로 처리하므로, 작업자가 다시 눌러도 두 번째 요청은 현재 상태(포장 완료)를 담은 거부 응답을 받습니다. 첫 요청이 프론트엔드 타임아웃 뒤에 커밋된 경우도 같은 응답으로 완료 여부를 알 수 있습니다. 같은 박스에 동시에 들어온 두 요청은 검증하지 않았습니다(더 개선할 부분 2).

박스 자재 재고(박스 호수(1호·2호처럼 크기 등급)별 남은 수량)는 락과 완료 시점 판정을 그대로 두었습니다. 자재가 없을 때 대체 박스를 고르는 흐름이 상품과 달라 별도 설계가 필요합니다. 그래서 개인 고도화 2주 범위에서 제외했습니다. 판정을 남긴 상태에서 락을 빼면 끼어든 다른 요청과 둘 다 통과합니다. 박스도 상품처럼 실물이 있으므로 판정을 없애고 원장으로 옮길 수 있습니다(더 개선할 부분 2).

접수 때는 박스 자재 재고를 보지 않아 재고가 없는 호수를 추천할 수 있습니다. 추천 박스가 선반에 없으면 작업자는 담기 전에 화면에서 다른 호수를 고릅니다. 대체 박스는 적재를 다시 판정하지 않고, 예상 무게만 그 박스 무게로 다시 계산합니다(더 개선할 부분 7). 완료 시점 거부는 실물은 있는데 전산 수량이 0인 경우에만 일어나고, 이 불일치도 더 개선할 부분 2에서 다룹니다.

포장 완료마다 여러 요청이 겹치는 락은 박스 자재 행 하나뿐이라 데드락이 생기지 않습니다(포화 부하 영향은 Problem 2).

**[사용이유]**
상품 락이 없어 다품목 박스의 락 경합이 사라지고, 상품 재고의 모든 변동이 원장 한 곳에 남아 재고 불일치를 추적할 수 있습니다.

**[결과]** 같은 부하(작업자 50명, 3분).

## Problem 2. 커넥션 풀 크기와 커넥션 타임아웃 결정

**[문제배경]**
v3에서 락 대기 요청이 커넥션을 점유하자 락과 무관한 요청까지 최대 10.5초를 기다렸습니다. 커넥션 풀은 기본값(풀 크기 10, 커넥션 타임아웃 30초)을 그대로 썼고, 이 창고 규모에 맞는지는 측정하지 않았습니다. 30초로 두면 프론트엔드 타임아웃(10초)이 지난 요청도 API 서버에서 20초 더 커넥션을 기다립니다. 원장 전환 뒤에도 박스 자재 락은 남아 같은 대기가 재발할 수 있었습니다.

`[캡처] docs/evidence/loadtest/20260922-104007-packing/grafana-packing-run6.png — v3 50명: 커넥션 대기 스레드 39`

**[접근법]**

| 방안 | 평가 |
| :-: | :-: |
| HikariCP 권장 공식(코어 수 × 2 + 유효 스핀들 수)으로 계산 | 4개. 커넥션 점유 시간이 DB 실행 시간과 같다는 전제라 이 시스템에 맞는지 알 수 없음 |
| 리틀의 법칙(Little's Law)으로 추정 | 6개. 동시 작업자 100명(창고 규모 미확인, 가정)이 분당 1건 포장하고 1건에 요청 3개, 즉 초당 요청 5개 × 요청당 점유 22ms(예비 실행 평균) = 평균 동시 커넥션 0.11개. 피크 3배(0.33개)에서 5개 이상 겹칠 확률이 포아송 분포(Poisson distribution) 기준 0.002%라 요청 처리용 4개 + 일괄 접수 1개 + 집계 스케줄러 1개. 평균 기반이라 포화·락 대기를 반영 못 함 |
| **부하를 고정하고 풀 크기·타임아웃만 바꿔 실측** | 판정 규칙과 예측을 실험 전에 적음 |

- 풀 크기 규칙(하한): 커넥션 대기가 사라지는 최소 풀, 최고 처리량의 98%를 내는 최소 풀. 풀 크기 규칙(상한): DB 락·I/O 대기 비중이 5%p 넘게 늘기 시작하는 풀(그 풀 포함, 실험 전 문구 그대로), 처리량은 늘지 않고 p95만 20% 넘게 나빠지는 풀.
- 타임아웃 규칙: 락 구간에서 락과 무관한 요청이 프론트엔드 타임아웃보다 먼저 실패하고, 현장 부하에서는 타임아웃이 0건인 가장 작은 값.
- 예측: 현장 부하에서는 풀 크기와 무관하게 처리량이 같고, 풀 5개 이상이면 커넥션 획득 시간이 1ms 미만일 것으로 봤습니다.
- 부하: 현장 부하(리틀의 법칙 계산과 같은 부하, 피크는 3배), 포화(100명, 생각 시간(think time) 0 — 응답을 받자마자 다음 요청), 락 점유 주입(피크 현장 부하 위에서 박스 자재 재고 1건을 20초 잠근 상태로 커넥션 타임아웃 30초·3초·1초 비교).

**[사용이유]**
락 대기가 점유 시간을 늘리는 구간이 있어 두 계산식의 전제가 맞는지 알 수 없으므로, 계산값은 예측으로만 두고 실측으로 정했습니다.

**[결과]**

| 부하 | 결과 | 규칙 판정 |
| :-: | :-: | :-: |
| 현장 부하 100·300명 | 풀 5~40개 모두 처리량 같음, 대기 없음. 풀 2개만 300명에서 대기 발생. 타임아웃 1초·3초 모두 0건 | 대기 소멸: 측정값 중 5개(3·4개 미측정). 타임아웃 규칙: 1초 |

풀을 늘릴수록 커넥션이 박스 자재 락 대기열에 쌓여, 포화 처리량의 상한은 박스 자재 락입니다(더 개선할 부분 2).

결과 표는 타임아웃 1초 재검증 2회를 빼고 조건마다 원장을 2만 건으로 되돌려 잰 값입니다. 집계 쿼리를 고치기 전 측정이며, 수정 뒤 재측정은 박스 자재 락 개선 때 함께 합니다(더 개선할 부분 2).

**풀 크기 결정.** 기본값과 같은 10개를 유지했습니다. 하한 규칙 중 큰 값은 20개, 상한 규칙 중 작은 값은 10개로 서로 어긋났고, 규칙 간 우선순위는 실험 전에 정해 두지 않았습니다. 20개는 포화 처리량이 약 10% 높지만 DB 락 대기 비중이 47%로 10개(19%)보다 크고 p95도 더 깁니다. 현장 부하에서는 두 값의 처리량이 같습니다. 이 기준은 결과를 본 뒤 추가한 것이라 한계로 남깁니다.

**커넥션 타임아웃 결정.** 30초에서 3초로 바꿨습니다. 타임아웃 규칙은 현장 부하 기준이라 1초도 통과합니다. 그러나 포화 부하 재검증에서 1초를 넘게 기다린 요청이 에러로 끝났습니다. 같은 시점의 기본값 조건에서는 커넥션 대기 최대값이 2.6초였고 모두 성공했습니다. 그래서 2.6초보다 긴 3초로 올렸습니다. 두 회차의 원장 조건이 달라 에러율 자체는 비교하지 못했고, 이 기준도 결과를 본 뒤 추가한 것입니다. 포화 부하 재검증에서 처리량은 기본값과 1% 차이였습니다.

3초가 지나 에러를 받은 작업자는 화면에서 다시 시도합니다. 에러 응답은 500이고, 과부하를 구분하는 503은 검토하지 않았습니다. 커넥션 타임아웃은 락과 무관한 요청을 빨리 끊을 뿐 락 대기 요청의 점유는 그대로이므로, 락 대기 시간 상한은 박스 자재 락 구간 개선과 함께 다룹니다(더 개선할 부분 2).

**예측 검증.** 첫 예측은 풀 5~40개에서 맞았습니다. 두 번째 예측(획득 시간)은 실측 1.6ms로 빗나갔습니다. 원인은 500ms 넘게 사용되지 않은 커넥션을 내주기 전에 거치는 유효성 검사(validation) 왕복이었습니다. 실험에서 검사를 끄자 0.1ms가 됐지만, 끊긴 커넥션을 받은 요청이 에러로 끝나는 위험이 1.5ms 이득보다 커서 운영에는 적용하지 않았습니다.

## Problem 3. 박스 편성 — 부피 비교에서 3D 빈 패킹으로, 무게를 목적 함수에

**[문제배경]**
초기 박스 편성은 실제로는 들어가지 않는 상품 조합을 통과시켰습니다. 판정 규칙이 "상품 부피 합이 박스 부피보다 작으면 된다"였기 때문입니다. 30×30×30cm 박스에 25×25×20cm 상품 두 개는 부피로는 들어가지만 어떤 방향으로도 함께 들어가지 않습니다.

사전 필터는 가장 큰 박스에 안 들어가면 어느 박스에도 안 들어간다고 가정했습니다. 박스 호수가 커져도 세 변이 모두 커지지는 않아, 긴 소형 박스에는 들어가는 상품까지 거부했습니다.

발표 심사에서 현업 심사위원이 묻기 전까지 무게는 계산에 없었습니다. 택배 요금은 크기 구간과 무게 구간 중 높은 쪽으로 정해집니다. 무게를 빼면 예상 요금이 실제보다 낮게 계산되고, 취급 한도를 넘는 주문도 걸러지지 않습니다.

**[접근법]**

**3-1. 박스 판정**

| 방안 | 평가 |
| :-: | :-: |
| 부피 합산 비교 | 들어가지 않는 박스를 추천. 현장에서 재포장 |
| 상품 하나씩 6방향 회전 검사 | 여러 상품을 함께 넣을 때를 판정 못 함 |
| 주문 분할 후 박스 판정 | 분할 방식이 고정돼 박스 수를 줄이는 조합을 못 찾음 |
| **3D 빈 패킹 휴리스틱 + 국소 탐색(local search), 모든 박스 호수를 후보로 검사** | 입력 치수가 맞다는 전제에서 판정이 곧 실제 배치. 주문 분할과 적재를 같은 목적 함수로 최적화 |

**3-2. 무게 반영**

| 방안 | 평가 |
| :-: | :-: |
| 박스마다 무게 한도 하나 | 한도가 택배 취급 한도와 같음. 한도 초과 주문의 분할만 되고 한도 이하 주문의 요금 구간 상승은 반영하지 못함 |
| 요금 구간의 무게 상한을 박스의 물리 한도로 사용 | 예: 무게 상한 2kg 구간의 박스에 2.5kg 주문이 오면 두 박스로 나눔. 실제로는 한 박스로 보내고 요금 구간만 오르면 됨 |
| **목적 함수를 총 배송비로 교체** | 배송비가 같으면 박스 수가 적은 쪽, 그것도 같으면 총 부피가 작은 쪽. 요금표에서 나눠 담는 쪽이 싼 주문만 나눔 |

적재 알고리즘은 박스 안 극점(extreme point, 이미 놓인 상품이 만드는 빈 모서리)마다 상품을 6방향으로 놓아 봅니다. 박스 안치수는 각 변에서 3cm를 뺀 값으로 계산해 치수 오차와 완충재 여유를 둡니다. 초기 해는 부피 내림차순 최초 적합(First Fit)으로 만들고, 상품을 다른 박스로 옮기는 국소 탐색으로 개선합니다. 나눠 담는 쪽이 싼 요금표에 대비해 박스를 하나 늘리는 이동도 탐색에 넣었습니다.

요금표는 CJ대한통운 2024 표준운임 5구간(5,000~9,000원)입니다. 이 표에서는 두 박스 요금 합(최소 1만 원)이 항상 최상단 구간 요금(9,000원)보다 높아, 취급 한도 이하 주문은 무게로 나뉘지 않고 요금 구간만 오릅니다. 최상단 구간 상한(20kg, 세 변 합 160cm)이 택배 취급 한도입니다. 이를 넘는 박스는 요금이 없어 후보에서 빠지고, 상품 하나가 한도를 넘으면 주문을 거부합니다.

편성에 쓰는 예상 무게는 상품 정보에 입력된 무게(실측 아님)의 합에 박스 자체 무게를 더한 값입니다. 포장 완료 때 실측 무게가 예상과 3%(최소 0.1kg) 넘게 다르면 담긴 상품이 빠졌거나 바뀐 것으로 보고 완료를 차단합니다. 작업자가 내용물을 확인하고 다시 잽니다. 허용 오차는 잠정값이고 저울 오차와 완충재 무게를 재서 조정합니다. 등록 무게 자체가 틀린 경우 차단을 푸는 경로는 없습니다(더 개선할 부분 7).

**[사용이유]**
3D 빈 패킹은 다항 시간 알고리즘이 알려지지 않은 문제(NP-hard)라, 주문 접수 시점에 실시간으로 편성하려면 휴리스틱이 필요합니다. 목적 함수를 배송비로 두면 요금표가 바뀌어도 편성이 따라가므로 한도 방식 대신 택했습니다.

**[결과]**

| 검증 | 결과 |
| :-: | :-: |
| "부피 합은 통과하나 배치 불가" 테스트 | 부피 방식 실패, 3D 빈 패킹 통과 |
| "부피 큰 박스가 치수로 탈락" 테스트 | 가장 큰 박스에 안 맞아도 다른 호수에서 통과 |

## Problem 4. 촬영 사진 업로드 경로 재설계

**[문제배경]**
v1(9분)에서 응답은 정상인데 45명부터 S3에 올라가지 않는 사진이 생겨 1,155장이 남았습니다. 비동기 업로드 작업은 촬영 1건(사진 3장) 단위로 메모리 안 큐(용량 2,000건)에 들어갑니다. 큐가 차면 작업이 에러 없이 버려지고, 다시 올리는 경로가 없어 그 사진은 S3에 영구히 올라가지 않습니다(큐에 남은 작업은 나중에 처리).

**[접근법]**

| 방안 | 평가 |
| :-: | :-: |
| 트랜잭션 안 동기 업로드 (v1 이전) | 저장 구간이 추론 대기를 뺀 API 서버 처리 중 가장 큰 몫이고 업로드 동안 커넥션 점유 |
| 커밋 뒤 비동기 업로드 (1차 적용) | 저장 구간 p95 36ms→12ms, API 서버 처리 p95(추론 대기 포함) 243ms→192ms(로컬, 추론·저장소는 로컬 대체 서버, 측정용 큰 사진). 큐 포화·프로세스 재시작 때 사진 유실 |
| 남은 사진을 스케줄러가 다시 업로드 | 응답 시점에 사진이 없는 상태는 그대로 |
| 클라이언트가 API 서버가 발급한 임시 업로드 주소(presigned URL)로 S3에 직접 업로드 | 추론용 사진은 API 서버가 따로 받아야 해서 업로드 경로가 둘로 갈림. 프론트엔드 변경 |
| 사진을 먼저 올리고 추론이 S3에서 읽기 | 추론 API 입력 형식을 바꿔야 하고, Lambda가 S3에서 사진을 읽는 시간은 측정하지 않음 |
| 메시지 큐 + 업로드 워커 | 유실은 막지만 브로커 운영이 추가됨 |
| **추론과 업로드를 병렬 실행, 둘 다 끝나면 응답** | 업로드 3장 병렬 37ms가 추론 호출 320ms(Lambda 왕복 p50) 안에 끝남. 응답이 곧 "사진 저장 완료" |

업로드는 전용 스레드 풀에서 트랜잭션 밖으로 실행해 커넥션을 점유하지 않습니다. 스레드 풀이 포화되면 작업을 거절하지 않고, 요청을 처리하던 Tomcat 작업 스레드가 직접 업로드합니다. 업로드 대기가 8초를 넘으면 프론트엔드 타임아웃 10초 전에 에러 응답으로 끝냅니다.

업로드가 실패하면 3회 재시도한 뒤 에러 응답을 보내고, 추론 결과는 저장하지 않으며, 작업자가 다시 촬영합니다.

추론이나 DB 저장이 실패하면 S3에 올라간 사진은 그대로 남습니다. 조회되지 않는 객체라 기능에는 영향이 없습니다(더 개선할 부분 9).

## Problem 5. 모델 배포 전 정확도 회귀 자동 검증

**[문제배경]**
모델을 바꿀 때 나아졌는지 판정할 기준이 없었습니다. 학습 환경에서 측정한 평균 절대 오차(MAE)는 가로 기준 1.31cm였는데, 서비스 코드로 고정 검증셋 2,024품목(학습에 쓰지 않은 분할)을 측정하니 2.06cm였습니다. 학습 리포트의 검증 분할과 서비스용 고정셋이 달랐고, 서비스 평가만 촬영 각도를 고정했습니다. 두 원인의 기여도는 나누지 못했습니다. 양자화처럼 속도를 얻고 정확도를 잃을 수 있는 후보도 같은 기준으로 걸러야 했습니다. 판정 지표는 MAE와 ±3cm 적중률(3축 모두 ±3cm 안에 든 품목의 비율)입니다.

**[접근법]**

| 방안 | 평가 |
| :-: | :-: |
| 학습 리포트의 수치를 그대로 신뢰 | 평가 방법이 서비스와 달라 비교가 안 됨 |
| 절대 상한만 검사 | 상한 안에서 한 번에 크게 나빠지는 회귀를 못 잡음 |
| **직전 모델 대비 회귀 기준 + 절대 상한, 고정 검증셋으로 매번 같은 방법 평가** | 회귀 기준 축별 MAE +0.2cm, ±3cm 적중률 −2%p 이내. 절대 상한 축별 MAE 3cm. 적중률 하한은 수정 비율 측정 뒤 정함. 기준값은 초기값이고 운영 데이터로 조정 |

통과한 모델만 Lambda 별칭(alias, 특정 모델 버전을 가리키는 이름)에 연결합니다.

**[사용이유]**
직전 모델 대비 기준은 한 번에 크게 나빠지는 회귀를 잡습니다. MAE의 누적 악화는 절대 상한이 막고, 적중률은 하한을 정하기 전까지 누적 하락을 막지 못합니다. 적중률의 ±3cm는 편성 여유와 같은 값이라, 상품 1개를 완충재 없이 담을 때 그대로 들어가는 품목의 비율로 읽을 수 있어 MAE와 별도로 봅니다.

**[결과]**

INT8은 축별 MAE가 1.1~1.5cm 나빠졌는데 적중률은 40%p 떨어져 두 기준을 모두 넘었습니다. 오차가 품목 전반에 퍼졌다는 뜻입니다.

## 더 개선할 부분

1. **주문 접수의 토트 배정.** v2에서 5,000건 배치 접수가 빈 토트 3만 건을 주문마다 읽어 60초를 넘겼고, 그 사이 들어온 다음 배치가 같은 토트를 골라 전체 롤백됐습니다. 락이 걸린 행은 건너뛰고 한 건만 잠가 가져오는 방식과 500건 단위로 묶어 저장하는 방식으로 바꿉니다. 완료 기준: 겹친 배치 2건 롤백 0. 주문당 접수 시간은 측정 전용.
2. **포화 처리량의 상한인 박스 자재 락.** 박스 자재도 원장으로 옮겨 완료 시점 판정과 락을 없애는 안을 우선 검토합니다. 락을 유지하는 안이면 잡은 채 실행하는 집계 조회(작업 구역별 포장 건수)를 트랜잭션 밖으로 뺍니다. 락 대기 시간 상한도 실험합니다. 같은 박스에 동시에 들어온 포장 완료 두 요청도 검증합니다. 완료 기준: 포화 부하에서 풀 20개의 p95가 풀 10개와 같은 수준이고 처리량은 더 높음.
3. **원장 집계의 커밋 시간 전제.** 이 전제를 트랜잭션 최대 실행 시간 제한으로 강제합니다. 접수는 원장에 쓰지 않지만 배치 접수 트랜잭션이 이 제한을 넘으므로(v2) 1번과 함께 진행합니다. 완료 기준: 제한을 넘는 트랜잭션이 끊기고 배치 접수가 영향받지 않음.
4. **주문 접수의 재고 초과 접수.** 접수 때 재고를 예약하는 원장 행을 기록하고 접수 단위로 직렬화합니다. 접수 때 원장에 기록을 남기게 되므로 배치 분할(1번)과 커밋 시간 제한(3번) 이후에 진행합니다. 완료 기준: 연속 또는 동시 접수 2건이 마지막 재고 1개를 둘 다 받지 않음.
