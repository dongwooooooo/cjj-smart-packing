### 아키텍처 설계 이유

1. **치수 추론은 GPU 서버 대신 Lambda(CPU)에 두었습니다.** 입고는 간헐적이라 GPU를 상시 켜 두면 사용량과 무관하게 비용이 듭니다. 모델을 ONNX로 변환하고 ONNX Runtime에서 실행해 CPU 추론 시간을 1,070ms(PyTorch)에서 185ms로 줄였습니다(로컬 CPU, 사진 3장). 콜드스타트는 최대 9.5초라, 시연 시간대에만 Provisioned Concurrency를 예약하고 배포 직후 웜업 호출을 넣었습니다. 응답 목표는 p95 1초로 정했고 시연 기간 Lambda 호출 246건의 핸들러 p95는 609ms였습니다.
2. **재고는 현재 수량을 갱신하지 않고 변동을 원장에 쌓습니다.** (Problem 1)
3. **촬영 사진 업로드는 추론과 병렬로 실행하고, 둘 다 끝나면 응답합니다.** (Problem 4)
4. **모델은 자동 검증을 통과한 것만 배포합니다.** (Problem 5)

## Problem 1. 동시 포장 시 재고 갱신 데드락과 원장 전환

**[문제배경]**
포장 작업자 50명이 동시에 포장 완료를 누르자 요청의 40.4%가 실패했습니다. 포장 완료는 주문의 상품마다 락을 걸고 재고 수량을 1씩 줄입니다. 주문마다 상품을 잠그는 순서가 달라 데드락(교착 상태)이 발생했습니다. 락을 기다리는 요청이 커넥션을 점유한 채 멈추자, 락과 관계없는 조회까지 커넥션을 얻지 못해 최대 10.5초 지연됐습니다.

두 문제가 더 있었습니다. 동시 포장 중 재고 감소분이 실제 포장 건수의 절반만 반영됐습니다(Lost Update). 락은 잡혔지만 갱신에 쓴 값이 락 이전에 읽어 둔 값이었습니다. 관리자 재고 조정은 별도 이력에만 기록되고 수량에는 반영되지 않아 주문 접수가 전부 거절된 일도 있었습니다(재고 이중 기록).

**[접근법]**

| 방안 | 평가 |
| :-: | :-: |
| 원자적 UPDATE + 락 획득 순서 통일 | 데드락과 Lost Update는 막힘. 락 대기가 커넥션을 점유하는 구조는 그대로. 이중 기록은 조정 경로를 따로 고쳐야 함 |
| 낙관적 락(Optimistic Lock) | 잠그지 않고 갱신 시 충돌을 감지해 재시도. 동시 요청이 많을수록 재시도가 늘어남. 실측하지 않고 기각 |
| **원장(append-only ledger)** | 수량을 고치지 않고 "−1" 같은 변동을 한 줄씩 INSERT. 락 없음. 현재 수량을 읽는 방법을 따로 설계해야 함 |

채택안의 설계는 다음과 같습니다. 현재 수량은 5초마다 원장을 집계해 둔 스냅샷에, 아직 집계되지 않은 원장 행을 더해 읽습니다. 집계는 기록된 지 60초가 지난 행만 대상으로 합니다. 원장 행을 기록한 트랜잭션이 60초 안에 커밋된다는 전제입니다. 1분마다 스냅샷과 원장 전체를 대조해 어긋나면 다시 계산합니다. 재고 부족 판정은 주문 접수 단계에서 이 값으로 하고, 포장 완료에서는 하지 않습니다. 포장대에 온 상품은 이미 창고에서 꺼낸 실물이기 때문입니다. 포장 박스 자재 재고는 락을 유지했습니다. 박스는 포장 시점에 소모되므로 부족하면 즉시 막아야 합니다. 포장 1건이 박스 1개를 쓰므로 락은 하나이고 데드락이 생기지 않습니다.

**[사용이유]**
원장은 세 문제를 함께 없앱니다. 락이 없으니 데드락과 Lost Update가 없고, 재고 기록처가 원장 하나라 이중 기록이 없습니다. 락 대기가 커넥션을 점유하는 구조 자체가 사라져 다른 요청이 영향을 받지 않습니다. 변동 이력이 남아 재고 불일치를 추적할 수 있습니다.

**[결과]** 같은 부하(작업자 50명, 3분)

| | 전환 전 | 전환 후 |
| :-: | :-: | :-: |
| 에러율 | 40.4% | 0% |
| 포장 완료 p95 | 10.07초(프론트엔드 타임아웃에서 끊긴 값) | 73ms |
| 처리량 | 2.9 TPS | 32.6 TPS |
| 데드락 | 356건 | 0건 |
| 원장 합계와 포장 건수 일치 | 감소분이 절반 | 일치 |

`[캡처] docs/evidence/loadtest/20260924-160456-packing/grafana-packing-after.png — 전환 후: 커넥션 대기 0, p95 73ms`

**집계 쿼리에서 잡은 결함 2건.** 코드 검토에서 집계가 시퀀스 ID 순서와 커밋 순서가 같다고 가정한 것을 찾았습니다. 늦게 커밋된 행을 영구히 건너뛸 수 있어, 위의 60초 규칙을 넣었습니다. v5에서 찾은 처리량 하락은 집계 범위를 찾는 쿼리가 원장 전체를 풀 스캔한 탓이었습니다. 인덱스 범위 스캔으로 고쳐 원장 105만 건에서 3,393ms를 0.66ms로 줄였습니다. 무부하 DB CPU는 26~30%에서 5~7%로 돌아왔습니다.

## Problem 2. 커넥션 풀 크기와 커넥션 타임아웃 결정

**[문제배경]**
v3에서 락을 기다리는 요청이 커넥션을 점유하자 락과 무관한 요청까지 최대 10.5초를 기다렸습니다. 커넥션 풀은 HikariCP 기본값(풀 크기 10, 커넥션 타임아웃 30초) 그대로였습니다. 10개가 이 창고 규모에 맞는지 측정한 적이 없었습니다. 30초로 두면 프론트엔드 타임아웃(10초)이 지난 요청도 서버에서 20초 더 커넥션을 기다립니다.

**[접근법]**
부하를 고정하고 풀 크기만 바꾸며 처리량, 커넥션 획득 시간, 커넥션 점유 시간, DB 대기 이벤트를 같은 표에 놓았습니다. 판정 규칙과 예측을 실험 전에 적었습니다.

- 규칙: 최고 처리량의 98%를 내는 최소 풀, 커넥션 대기가 사라지는 최소 풀, DB 락·I/O 대기 비중이 5%p 넘게 늘기 시작하는 풀, 처리량은 늘지 않고 p95만 20% 넘게 나빠지는 풀.
- 예측: 현장 피크에서는 풀 크기와 무관하게 처리량이 같다. 풀 5개 이상이면 커넥션 획득 시간이 1ms 미만이다.
- 필요 커넥션 수 추정: 동시 작업자 100명이 분당 1건 포장한다고 가정했습니다(창고 규모는 미확인). 1건에 요청이 3개라 초당 5건입니다. 요청당 커넥션 점유가 22ms이므로 리틀의 법칙(Little's Law)으로 평균 동시 커넥션은 0.11개입니다. 피크 3배(0.33개)에서 동시 4개 이상 겹칠 확률은 포아송 기준 0.04%입니다. 여기에 일괄 접수 1개와 집계 스케줄러 1개를 더해 6개면 충분하다는 계산입니다.
- 세 가지 부하: 현장 피크(100명·300명, 분당 1건), 포화 부하(100명, think time 0 — 응답을 받자마자 다음 요청), 락 점유 주입(박스 재고 1건을 20초 잠근 상태에서 커넥션 타임아웃 30초·3초·1초 비교).

**[사용이유]**
풀 크기는 10개로 정했습니다. 20개는 처리량이 10% 높지만 DB 락 대기 비중이 19%에서 47%로 뛰었습니다. 처리량 규칙은 20개, DB 대기 규칙은 10개를 가리켜 충돌했고, 규칙 간 우선순위를 미리 정하지 않았으므로 DB 쪽 여유가 있는 10개를 골랐습니다. 커넥션 타임아웃은 3초로 정했습니다. 1초에서는 포화 부하 때 성공했어야 할 요청의 0.03~2.76%가 에러로 끝났고, 3초에서는 에러가 0건이었습니다. 3초에 에러를 받은 작업자는 화면에서 다시 시도합니다.

**[결과]**

| 부하 | 결과 |
| :-: | :-: |
| 현장 피크 100·300명 | 풀 5~40개 모두 처리량 같음, 대기 없음. 풀 2개만 300명에서 대기 발생 |
| 포화 | 5→10→20개에서 78→125→137 TPS. 30·40개는 처리량 그대로, p95만 571ms→1.3초 |
| 락 점유 주입 | 30초: 락과 무관한 조회 절반이 6~7초, 일부 10초 타임아웃, Tomcat 작업 스레드 184·200(2회). 3초·1초: 그 시간에 에러 응답(500), 화면 멈춤 없음 |

`[캡처] docs/evidence/pool-sizing/timeout/peak3x-p10-t30000-th200-r1/grafana.png — 커넥션 타임아웃 30초에서 락 20초 주입: 커넥션 대기 174, Tomcat 작업 스레드 184`

포화 처리량의 상한은 박스 재고 락입니다. 풀을 20개 넘게 늘려도 커넥션은 박스 락 대기열에 쌓여 p95만 늘었습니다. 커넥션 점유 시간의 74%는 DB 실행이 아니라 트랜잭션 안에서 애플리케이션이 다음 쿼리를 보내기 전까지의 시간이었습니다(트랜잭션을 연 세션 9.5개 중 7.0개). 그래서 HikariCP 권장 공식(코어 수 × 2 + 유효 스핀들 수 = 4개)보다 큰 풀이 맞았습니다. 재검증에서 결정값은 기본값 대비 처리량 차이 1%, 에러 0건이었습니다.

**예측 대 실측.** "풀 5개 이상이면 획득 시간 1ms 미만"은 실측 1.6ms로 빗나갔습니다. 원인은 500ms 넘게 사용되지 않은 커넥션을 내주기 전에 거치는 유효성 검사(validation) 왕복이었습니다. 실험에서 검사를 끄자 0.1ms가 됐지만, 끊긴 커넥션을 감지하지 못하는 위험이 1.5ms 이득보다 커서 운영에는 적용하지 않았습니다. 풀 30·40개에서 처리량이 떨어져 큰 풀이 원인이라고 판단했으나, 실제 원인은 실험 중 누적된 데이터였습니다(Problem 1의 집계 쿼리). 조건마다 데이터를 초기화하자 처리량은 유지되고 p95만 늘었습니다.

## Problem 3. 박스 편성 — 부피 비교에서 3D 빈 패킹으로

**[문제배경]**
30×30×30cm 박스에 25×25×20cm 상품 두 개는 부피로는 들어가지만 어떤 방향으로도 함께 들어가지 않습니다. 박스 편성(cartonization, 주문을 어떤 박스 몇 개에 나눠 담을지 정하는 계산)의 초기 규칙이 "상품 부피 합이 박스 부피보다 작으면 된다"였습니다. 사전 필터는 가장 큰 박스에만 넣어 보는 방식이었습니다. 박스 호수(1호·2호처럼 크기 등급)가 커져도 세 변이 모두 커지지는 않아서, 이 필터로는 안 들어가는 상품을 걸러내지 못했습니다. 발표 심사에서 현업 심사위원이 묻기 전까지 무게는 계산에 없었습니다. 택배 요금은 크기 구간과 무게 구간 중 높은 쪽으로 정해지므로, 무게를 빼면 요금이 한 구간 올라가는 편성이 최적으로 나옵니다.

**[접근법]**

| 방안 | 평가 |
| :-: | :-: |
| 부피 합산 비교 | 들어가지 않는 박스를 추천. 현장에서 재포장 |
| 상품 하나씩 6방향 회전 검사 | 여러 상품을 함께 넣을 때를 판정 못 함 |
| 주문 분할 후 박스 판정 | 분할 방식이 고정돼 박스 수를 줄이는 조합을 못 찾음 |
| **3D 빈 패킹(3D Bin Packing) 휴리스틱 + 국소 탐색(local search)** | 판정이 곧 실제 배치. 주문 분할과 적재를 같은 목적 함수로 최적화 |
| 무게: 박스마다 무게 한도 하나 | 한도에 걸리는 주문이 드물어 편성이 바뀌지 않음 |
| 무게: 요금 구간 상한을 박스의 물리 한도로 사용 | 그대로 보내도 되는 2.5kg 박스까지 나눠 담게 함 |
| **무게: 목적 함수를 총 배송비로 교체** | 배송비가 같으면 박스 수가 적은 쪽, 그것도 같으면 총 부피가 작은 쪽 |

적재 알고리즘은 박스 안 빈 모서리(extreme point)마다 상품을 6방향으로 놓아 보는 방식이고, 초기 해는 부피 내림차순 First Fit, 개선은 상품을 다른 박스로 옮기거나 박스를 늘리는 국소 탐색입니다. 요금표는 CJ대한통운 2024 표준운임입니다. 상품 하나가 택배 취급 한도(20kg)를 넘으면 거부합니다. 포장 완료 때 실측 무게가 예상과 3%(최소 0.1kg) 넘게 다르면 포장 완료를 차단합니다.

**[사용이유]**
3D 빈 패킹은 정확해를 구할 수 없는 문제(NP-hard)라, 주문당 상품 수십 개를 실시간으로 처리하려면 휴리스틱이 필요합니다. 목적 함수 순서는 비용이 큰 것부터입니다. 배송비가 실제 지출이고, 박스 수는 자재와 작업 시간, 부피는 동점 처리입니다. 나누는 편이 싼 경우가 있어 국소 탐색이 박스를 늘리는 이동도 후보로 봅니다.

**[결과]**
문제배경의 두 반례가 테스트 케이스로 들어갔습니다. "부피 합은 통과하나 배치 불가"는 부피 방식에서 실패하고 3D 빈 패킹에서 통과합니다. "무게로 요금이 오르면 나눠 담기"는 한 박스에 담기는 주문을 배송비 기준으로 둘로 나눕니다. 편성 테스트 케이스는 21개에서 39개가 됐습니다. 합성 주문 벤치마크(SKU 500종, 단일 스레드)에서 주문당 p50은 2.3ms, p95는 13.8ms였고, 5,000건 처리에 21.0초가 걸렸습니다. 기존 부피 방식 대비 추천이 바뀐 주문 비율과 배송비 차이는 측정하지 않았습니다(더 개선할 부분 7).

`[캡처] docs/evidence/benchmark/screens/bench-console.png — 벤치마크 콘솔: 100·1,000·5,000주문 p50/p95/최대`

**벤치마크가 잡은 예외.** 국소 탐색이 상품 하나를 다른 박스로 옮길 때 받는 쪽만 다시 판정하고, 상품을 뺀 쪽은 그대로 담긴다고 가정했습니다. 휴리스틱 판정이라 17개는 담기는데 하나를 뺀 16개는 못 담긴다고 판정되는 주문이 나왔고, 박스를 정하지 못한 편성이 요금 계산으로 넘어가 예외가 발생했습니다. 주문 접수 API에서 발생했다면 500 응답으로 끝났을 경로입니다. 뺀 쪽도 판정하도록 고치고 그 주문을 회귀 테스트로 고정했습니다.

## Problem 4. 촬영 사진 업로드 경로 재설계

**[문제배경]**
촬영 API는 사진 3장을 읽고, 추론을 호출하고, 결과와 사진을 저장한 뒤 응답합니다. 구간별로 측정하니 API 서버 자체 처리 시간(추론 대기 제외) p50 90~220ms 중 저장 구간(DB 커밋과 사진 3장 S3 업로드)이 32~81ms로 가장 컸습니다. 업로드가 트랜잭션 안에 있어 그동안 커넥션도 점유했습니다. 업로드를 커밋 뒤 비동기로 뺐더니 저장 구간 p95는 36ms에서 12ms로 줄었지만(로컬), v1에서 응답은 정상인데 45명부터 S3에 올라가지 않는 사진이 생겨 1,155장이 남았습니다. 비동기 업로드는 메모리 안 큐에 들어가는데, 큐가 차면 작업이 에러 없이 버려지고 다시 올리는 경로가 없었습니다. 큐에 남은 작업은 나중에 처리되지만 버려진 작업은 영구히 미업로드로 남습니다.

**[접근법]**

| 방안 | 평가 |
| :-: | :-: |
| 커밋 뒤 비동기 업로드 (1차 적용) | 응답은 빠르지만 큐 포화·프로세스 재시작 때 사진 유실 |
| 남은 사진을 스케줄러가 다시 업로드 | 응답 시점에 사진이 없는 상태는 그대로 |
| 사진을 먼저 올리고 추론이 S3에서 읽기 | 추론 API 입력 형식을 바꿔야 하고 응답에 업로드 시간이 더해짐 |
| 메시지 큐 + 업로드 워커 | 유실은 막지만 브로커 운영이 추가됨 |
| **추론과 업로드를 병렬 실행, 둘 다 끝나면 응답** | 업로드 3장 병렬 37ms가 추론 호출 320ms(Lambda 왕복 p50) 안에 끝남. 응답이 곧 "사진 저장 완료" |

**[사용이유]**
응답 시간을 유지하면서 사진 저장을 응답의 조건으로 만들 수 있는 유일한 안이었습니다. 업로드는 트랜잭션 밖에서 실행해 커넥션을 점유하지 않습니다. 업로드가 실패하면 3회 재시도한 뒤 에러 응답을 보내고, 추론 결과는 저장하지 않으며, 작업자가 다시 촬영합니다.

**[결과]** 시연 환경(EC2·RDS·S3·Lambda)에서 두 방식을 같은 조건으로 비교

| :-: | :-: | :-: |

## Problem 5. 모델 배포 전 정확도 회귀 자동 검증

**[문제배경]**
학습 환경에서 측정한 평균 절대 오차(MAE)는 가로 기준 1.31cm였는데, 서비스 코드로 고정 검증셋 2,024품목을 측정하니 2.06cm였습니다. 학습 리포트의 검증 분할과 서비스용 고정셋이 달랐고, 촬영 각도 고정 여부도 달랐습니다. 양자화처럼 속도를 얻고 정확도를 잃을 수 있는 후보를 포함해, 모델을 바꿀 때 나아졌는지 판정할 기준이 없었습니다.

**[접근법]**
검증셋 2,024품목을 고정하고, 배포할 모델 그대로 같은 방법으로 평가합니다. 배포 후보는 두 기준을 모두 통과해야 합니다. 직전 모델 대비 회귀 기준(MAE +0.2cm, ±3cm 적중률 −2%p 이내)과 절대 상한(MAE 3cm)입니다. ±3cm 적중률은 3축 모두 ±3cm 안에 든 품목의 비율입니다. 두 기준값은 초기값이고 운영 데이터로 조정합니다. 통과한 모델만 Lambda 별칭(alias, 서비스가 가리키는 모델 버전)에 연결합니다.

**[사용이유]**
적중률은 박스 추천에 그대로 쓸 수 있는 품목의 비율이라 MAE와 별도로 봅니다. 기준 모델의 62.5%는 품목 3개 중 1개가 한 축 이상 3cm 넘게 틀린다는 뜻입니다. 입고 작업자가 화면에서 치수를 확인해 확정하는 단계가 이 오차를 흡수합니다.

**[결과]**

| 후보 | 축별 MAE (가로/세로/높이, cm) | ±3cm 적중률 | 추론 시간(평가 서버 2 vCPU) | 판정 |
| :-: | :-: | :-: | :-: | :-: |
| 기준 모델(FP32) | 2.06 / 2.17 / 1.62 | 62.5% | 243ms | 기준선 |
| FP16 | 동일 | 62.5% | 243ms | 통과, 이득 없음 |
| INT8 양자화 | 3.57 / 3.24 / 2.89 | 22.6% | 164ms | 차단 |

INT8은 MAE 기준으로 차단됩니다. 축별 MAE가 1.1~1.5cm 나빠지는 동안 적중률은 40%p 떨어졌는데, 오차가 품목 전반에 퍼졌다는 뜻입니다. 재학습 없이 통과하는 추론 시간 단축 후보는 없었습니다.

## 더 개선할 부분

1. **주문 접수의 토트 배정.** v2에서 찾은 문제입니다. 락이 걸린 행은 건너뛰고 한 건만 잠가 가져오는 쿼리(SKIP LOCKED)와 500건 단위 배치 INSERT로 바꿉니다.
2. **포화 처리량의 상한인 박스 재고 락.** 락을 잡은 채 실행하는 포장 라인(포장대 묶음)별 건수 조회를 트랜잭션 밖으로 빼고, 락 타임아웃(lock_timeout)을 실험합니다.
3. **원장 집계의 60초 전제.** Problem 1의 "60초 안에 커밋" 전제를 트랜잭션 최대 실행 시간 제한으로 강제합니다.
4. **주문 접수의 재고 경합.** 동시 접수 2건이 같은 가용 재고를 읽고 둘 다 수용할 수 있습니다. 접수 단위 직렬화가 필요합니다.
5. **API 서버 이중화.** 서버 1대라 장애 지점이 하나이고 무중단 배포가 안 됩니다. 집계 스케줄러 중복 실행 방지(분산 락)와 로드밸런서 구성이 필요합니다.
6. **24시간 운영의 콜드스타트.** Provisioned Concurrency 상시 예약 비용과 주기적 웜업 호출을 월 비용과 첫 응답 지연으로 비교해 정합니다.
7. **박스 편성 효과 측정.** 기존 부피 방식 대비 추천이 바뀐 주문 비율과 배송비 차이를 실제 주문으로 측정합니다.
