### 아키텍처 설계 이유

1. **치수 추론은 GPU 서버 대신 CPU 서버리스로 두었습니다.** 입고는 하루 종일 드문드문 일어나서 GPU를 상시 켜 두면 사용량과 무관하게 비용이 나갑니다. 모델을 CPU용 실행 형식(ONNX)으로 바꿔 추론 1건을 1,070ms에서 185ms로 줄였고, 서버리스의 첫 호출 지연(콜드스타트)은 시연 시간대 예열과 배포 직후 워밍 호출로 막았습니다.
2. **재고는 "현재 수량" 대신 "변동 내역"을 기록합니다.** 여러 작업자가 동시에 포장을 끝내면 같은 상품의 수량 한 칸을 서로 갱신하려다 잠금을 기다리는 교착이 났습니다. 변동을 한 줄씩 추가만 하는 방식으로 바꾸고, 현재 수량은 주기적으로 합산한 값에 아직 합산 안 된 내역을 더해 읽습니다.
3. **촬영 사진 저장은 응답과 분리했습니다.** 사진 3장을 저장소에 올리는 시간이 촬영 응답의 절반이었습니다. 추론과 업로드를 동시에 시작하고 둘 다 끝나면 응답합니다.
4. **모델은 자동 검증을 통과한 것만 배포합니다.** 학습 쪽이 보고한 정확도와 서비스에서 잰 정확도가 달랐습니다. 고정 검증셋으로 매번 같은 기준으로 재고, 기준을 넘는 후보만 배포 대상으로 올립니다.

## 테스트 진행 v1 ~ v5

**테스트 이유.** 시연은 상품 11종, 작업자 1명이었습니다. 실제 창고 규모(작업자 수십 명 동시 작업, 주문 수천 건 일괄 접수)에서 어디가 먼저 무너지는지 찾기 위해 부하 테스트를 했습니다.

**도구·환경.** 부하 발생 k6, 지표 수집 Prometheus·Grafana(응답 시간, DB 연결 풀, 스레드, DB 대기 이벤트). API 서버 EC2(2 vCPU), DB RDS(2 vCPU, 1GB). 시나리오는 작업자 행동 단위입니다. 촬영은 "촬영 버튼 → 결과 확인", 포장은 "토트 스캔 → 주문 확인 → 포장 완료".

입고 작업자를 1명에서 100명까지 늘리며 연속 촬영. 현장 속도의 수십 배입니다.

- 결과: 100명까지 응답 p95 0.54초, 실패 0.
- 찾은 것: 응답은 정상인데 사진 1,155장이 저장소에 올라가지 않은 채 남았습니다. 사진 업로드를 응답 뒤로 미룬 대기 줄이 가득 차면 조용히 버려지는 구조였습니다. → Problem 4

### v2. 주문 일괄 접수

주문 100건·1,000건·5,000건을 한 번에 접수.

- 결과: 주문 1건당 53ms로 선형. 5,000건은 272초.
- 찾은 것: 접수마다 빈 운반함 목록 전체(3만 건)를 읽어 하나만 쓰고 있었습니다. 접수 2건이 동시에 들어오면 같은 운반함을 골라 한쪽이 통째로 실패했습니다. → 더 개선할 부분 1

### v3. 동시 포장

포장 작업자 10명·50명이 "토트 스캔 → 주문 확인 → 포장 완료"를 반복.

`[캡처] docs/evidence/loadtest/20260922-104007-packing/grafana-packing-run6.png — 50명: DB 연결 대기 39, 포장 완료 p95 10초`

### v4. 재고 방식 전환 후 재측정

v3와 같은 부하.

## Problem 1. 동시 포장 시 재고 갱신 교착

**[문제배경]**
포장 작업자 50명이 동시에 포장 완료를 누르자 요청의 40.4%가 실패했습니다. 포장 완료는 주문에 담긴 상품마다 재고 수량을 1씩 줄이는데, 상품 수량 한 칸을 갱신하는 동안 다른 요청이 같은 칸을 못 건드리게 잠급니다. 주문마다 상품 순서가 달라서 A는 사과를 잠근 채 배를 기다리고 B는 배를 잠근 채 사과를 기다리는 교착이 났습니다. 교착에 걸린 요청이 DB 연결을 붙든 채 기다리자, 잠금과 관계없는 조회까지 연결을 못 받아 5초 넘게 멈췄습니다.

원인을 좇다 두 가지가 더 나왔습니다. 동시 포장 중 재고 감소분이 실제 포장 건수의 절반만 반영되고 있었고(갱신 유실), 관리자 재고 조정이 수량 칸에 반영되지 않아 주문 접수가 전부 거절된 일도 있었습니다. 세 문제의 공통 원인은 재고 숫자를 "현재 수량 한 칸"으로 들고 있고, 그 칸의 갱신이 잠금에 묶여 있다는 것이었습니다.

**[접근법]**

| 방안 | 내용 | 기각 이유 |
| :-: | :-: | :-: |
| 잠금 순서 통일 | 상품을 항상 같은 순서로 잠가 교착 방지 | 교착은 줄지만 갱신 유실과 "재고가 두 곳" 문제는 그대로 |
| 낙관적 잠금 | 잠그지 않고 갱신 시 충돌을 감지해 재시도 | 동시 요청이 많을수록 재시도가 늘어 부하를 키움 |
| **변동 내역 기록(원장)** | 수량을 고치지 않고 "−1" 같은 변동을 한 줄씩 추가만 함 | 현재 수량을 읽는 방법을 따로 설계해야 함 |

**[사용이유]**
추가만 하는 기록에는 잠금이 필요 없습니다. 포장 완료가 잡는 잠금은 박스 재고 하나로 줄었습니다. 현재 수량은 5초마다 변동 내역을 합산해 둔 값에, 아직 합산되지 않은 내역을 더해 읽습니다. 합산이 늦어도 읽는 값은 항상 정확합니다. 1분마다 합산값과 전체 내역을 대조해 어긋나면 다시 계산합니다. 회계 장부와 같은 원리이고, 재고를 한 곳에서만 기록하므로 "두 곳이 어긋나는" 문제도 함께 사라집니다.

**[결과]** 같은 부하(작업자 50명, 3분)

| | 전환 전 | 전환 후 |
| :-: | :-: | :-: |
| 포장 완료 실패율 | 40.4% | 0 |
| 포장 완료 p95 | 10.07초 | 73ms |
| 처리량 | 2.9건/s | 32.6건/s |
| 교착 | 356건 | 0 |

`[캡처] docs/evidence/loadtest/20260924-160456-packing/grafana-packing-after.png — 전환 후 3분: 연결 대기 0, p95 73ms`

**전환 뒤 잡은 결함 2건.** 코드 검토에서, 합산 작업이 "번호 순서 = 기록 순서"라고 가정해 늦게 확정된 내역을 건너뛸 수 있는 결함을 찾았습니다. 기록된 지 일정 시간이 지난 내역만 합산하도록 바꿨습니다. 부하 실험 중에는 합산 작업이 내역이 쌓일수록 느려져 처리량이 절반으로 떨어지는 현상을 찾았습니다. 합산 대상 범위를 찾는 질의가 전체를 훑고 있었고, 범위만 읽도록 고쳐 내역 105만 건에서 3,393ms를 0.66ms로 줄였습니다.

## Problem 2. DB 연결 개수와 대기 상한을 부하 실험으로 결정

**[문제배경]**
DB 연결 풀은 프레임워크 기본값(연결 10개, 연결을 얻기까지 최대 30초 대기) 그대로였습니다. 10개가 이 창고 규모에 맞는지 잰 적이 없었고, 30초는 작업자 화면이 10초에 포기한 요청을 서버가 20초 더 붙들고 있게 두는 값이었습니다. v3에서 잠금을 기다리는 요청이 연결을 붙들자 무관한 요청까지 최대 10.5초를 기다린 것이 그 결과입니다.

**[접근법]**
부하를 고정하고 연결 개수만 바꾸며 처리량, 연결을 얻는 데 걸린 시간, 연결을 쥔 시간, DB 안 대기 이벤트를 같은 표에 놓았습니다. 판정 기준은 실험 전에 문서로 정했습니다.

1. 필요 연결 수 계산: 작업자 100명이 분당 1건, 요청당 연결 점유 22ms → 평균 동시 연결 0.1개. 피크 3배와 배치 작업을 더해도 6개면 충분.
2. 세 가지 부하: 현장 피크(100·300명), 포화(100명 쉬지 않고), 잠금 주입(재고 한 건을 20초 잠근 상태에서 대기 상한 30초·3초·1초 비교).

**[사용이유]**
공식(코어 수 × 2 = 4)보다 실측이 맞았습니다. 연결을 쥔 시간 대부분이 DB 실행이 아니라 서버가 다음 질의를 보내기까지의 대기여서, 같은 코어 수에 더 많은 연결이 필요했습니다.

**[결과]**

| 부하 | 결과 |
| :-: | :-: |
| 현장 피크 | 연결 5~40개 모두 처리량 같음, 대기 없음 |
| 포화 | 5→10→20개에서 78→125→137건/s. 30·40개는 처리량 그대로, p95만 0.57초→1.3초 (재고 잠금 대기열만 늘어남) |
| 잠금 주입 | 상한 30초: 무관한 조회 절반이 6~7초, 일부 10초 실패. 상한 3초: 3초에 실패 응답, 화면 멈춤 없음 |
| 결정 | 연결 10개, 대기 상한 3초. 재검증에서 기본값 대비 처리량 차이 1%, 실패 0 |

`[캡처] docs/evidence/pool-sizing/timeout/peak3x-p10-t30000-th200-r1/grafana.png — 대기 상한 30초에서 잠금 20초 주입: 연결 대기 174, 서버 스레드 184`

## Problem 3. 박스 추천 — 부피 계산의 함정과 배송비 기준 최적화

**[문제배경]**
주문을 어떤 박스 몇 개에 담을지 정하는 규칙이 "상품 부피 합이 박스 부피보다 작으면 된다"였습니다. 30×30×30 박스에 25×25×20 상품 두 개는 부피로는 들어가지만 어떤 방향으로도 함께 들어가지 않습니다. 박스 크기 종류가 커진다고 세 변이 모두 커지지도 않아서 "제일 큰 박스만 검사"로는 안 들어가는 상품을 못 걸렀습니다. 무게는 계산에 없었는데, 택배 요금은 크기 구간과 무게 구간 중 높은 쪽으로 정해지므로 무게를 빼면 요금이 한 구간 올라가는 편성이 최적으로 나옵니다. 발표 심사에서 현업 심사위원이 이 점을 물었습니다.

**[접근법]**

| 방안 | 기각 이유 |
| :-: | :-: |
| 부피 합산 비교 | 들어가지 않는 박스를 추천. 현장에서 재포장 |
| 상품 하나씩 6방향 회전 검사 | 여러 상품을 함께 넣을 때를 판정 못 함 |
| 주문을 먼저 나누고 박스 판정 | 나누는 방식이 고정돼 박스 수를 줄이는 조합을 못 찾음 |
| **3차원 적재 시뮬레이션 + 국소 탐색** | 판정이 곧 실제 배치. 나누기와 담기를 한 기준으로 최적화 |

무게는 "박스마다 한도 1개"(효과 없음), "요금 구간을 물리 한도로 사용"(2.5kg 상자를 불필요하게 분할)을 기각하고, **최적화 기준을 총 배송비로 바꿨습니다.** 배송비가 같으면 박스 수, 그다음 부피 순입니다. 상품 하나가 접수 한도(20kg)를 넘으면 거부하고, 포장 완료 때 실측 무게가 예상과 어긋나면 막습니다.

**[사용이유]**
실제 물류 시스템의 박스 최적화(카토나이제이션)가 쓰는 기준과 같습니다. 무게 때문에 한 박스에 담기더라도 나누는 편이 싼 경우가 있어, 탐색이 "박스를 늘리는 방향"도 후보로 봅니다.

**[결과]**
편성 테스트 21개 → 39개("부피는 통과하나 배치 불가", "무게로 요금이 오르면 나눠 담기" 포함). 합성 주문 벤치마크:

| 주문 수 | 총 시간 | 주문당 p50 / p95 |
| :-: | :-: | :-: |
| 100 | 0.36초 | 1.8 / 12.8ms |
| 5,000 | 21.0초 | 2.3 / 13.8ms |

주문 50배에 주문당 시간 1.16배. 첫 벤치마크는 예외로 멈췄습니다. 상품 하나를 다른 박스로 옮길 때 받는 쪽만 검사하고 뺀 쪽은 검사하지 않아, 17개는 담기는데 16개는 못 담긴다고 판정되는 조합이 나왔습니다. 접수 API였다면 500 응답이었을 경로를 고치고 그 주문을 회귀 테스트로 고정했습니다.

## Problem 4. 촬영 응답 1초 — 서버리스 전환과 저장 경로 재설계

**[문제배경]**
치수 추론은 GPU 서버 전제로 타임아웃 8초였습니다. 비용 때문에 CPU 서버리스로 옮기자 첫 호출 지연이 최대 9.5초로 타임아웃을 넘겼고, 8초는 작업자가 버튼을 누르고 기다리는 기준으로도 쓸 수 없는 값이었습니다. 목표를 응답 p95 1초로 다시 정했는데, 서버가 사진을 읽고 추론을 부르고 저장하는 각 구간을 잰 적이 없었습니다.

**[접근법]**
1. 모델을 CPU용 형식(ONNX)으로 변환해 추론 1,070ms → 185ms. 변환 결과가 원본과 다르면 빌드를 실패시키는 검사를 둠.
2. 첫 호출 지연은 시연 시간대만 인스턴스 예열, 배포·리셋 직후 워밍 호출.
3. 구간 실측: 사진 읽기 / 요청 조립 / 추론 호출 / 저장. 저장(사진 3장 업로드 포함)이 서버 구간의 절반.
4. 저장 경로: 메모리 상향(계정 한도), 사진 축소(이득 작음), 메시지 큐(규모 대비 과함)를 기각하고 업로드를 응답 뒤 비동기로.

**[사용이유]**
응답 경로에서 업로드가 빠지면서 DB 연결 점유도 함께 사라집니다. 추론 호출도 트랜잭션 밖으로 빼서 느린 호출이 연결을 쥐지 않게 했습니다.

**[결과]**

| 지표 | 전 | 후 |
| :-: | :-: | :-: |
| CPU 추론 | 1,070ms | 185ms |
| 저장 구간 p95 | 36ms | 12ms |
| 운영 응답 p95(실제 사진) | — | 611ms |
| 시연 기간 추론 246건 | — | p95 609ms, 8초 초과 0 |

**비동기화가 숨긴 실패와 두 번째 수정.** v1 부하 상한 탐색에서 응답은 정상인데 사진 1,155장이 저장되지 않았습니다. 업로드 대기 줄이 차면 거절이 로그 한 줄로 끝나고 다시 올리는 경로가 없었습니다. 세 안을 비교했습니다. 남은 것을 나중에 다시 올리는 재처리 스케줄러는 응답 시점에 사진이 없는 상태가 그대로이고, 사진을 먼저 올린 뒤 추론이 저장소에서 읽는 안은 추론 쪽 계약을 바꾸고 응답이 느려집니다. **채택한 안은 업로드와 추론을 동시에 시작해 둘 다 끝나면 응답하는 것**입니다. 업로드 3장 병렬 37ms가 추론 320ms 안에 끝나므로 응답 시간은 그대로이고, 응답이 곧 "사진이 저장됐다"는 보장이 됩니다. 업로드가 실패하면 촬영 실패로 응답합니다.

| 같은 환경 비교 | 응답 뒤 비동기 | 동시 시작 후 응답 |
| :-: | :-: | :-: |
| 단일 요청 E2E p50 / p95 | 437 / 467ms | 441 / 482ms |
| 작업자 30명 p95 | 524ms | 544ms |
| 작업자 60명 포화 후 미저장 사진 | 최대 5,700장, 종료 후 27장 잔존 | 0 |

## Problem 5. 모델 교체 시 정확도 자동 검증

**[문제배경]**
학습 쪽이 보고한 오차는 1.31cm였는데 서비스 코드로 같은 검증셋을 재니 2.06cm였습니다. 평가 방법(데이터 분할, 촬영 각도 고정 여부)이 달라서 생긴 차이였고, 이 상태로는 모델을 바꿀 때 나아졌는지 판정할 기준이 없었습니다. 속도를 위해 경량화(양자화) 후보를 시험하려면 더욱 필요했습니다.

**[접근법]**
검증셋 2,024품목을 고정해 두고, 배포할 모델 그대로 같은 방법으로 평가합니다. 판정은 두 단계입니다. 직전 모델보다 나빠지지 않았는가(평균 오차 +0.2cm, 3축 모두 ±3cm 안에 드는 비율 −2%p 이내), 그리고 절대 상한(평균 오차 3cm)을 넘지 않는가. 통과한 모델만 서비스 별칭에 연결합니다.

**[사용이유]**
평균 오차 하나로는 오차가 한쪽으로 치우친 모델을 못 잡습니다. 3축이 모두 허용 범위 안에 드는 비율을 함께 봅니다.

**[결과]**

| 후보 | 평균 오차(cm) | 3축 ±3cm | 속도 | 판정 |
| :-: | :-: | :-: | :-: | :-: |
| 현행 | 2.06 / 2.17 / 1.62 | 62.5% | 243ms | 기준 |
| 반정밀도(FP16) | 동일 | 62.5% | 243ms | 통과, 이득 없음 |
| 8비트 양자화 | 3.57 / 3.24 / 2.89 | **22.6%** | 164ms | **차단** |

8비트 양자화는 1.48배 빠르고 평균 오차 악화는 1.5cm뿐이라 평균만 봤다면 통과했을 후보입니다. 3축 정답률이 62.5%에서 22.6%로 떨어져 검증이 막았습니다. 재학습 없이 통과하는 속도 후보는 없다는 결론을 얻었습니다.

## 더 개선할 부분

1. **주문 접수의 운반함 배정.** 접수마다 빈 운반함 전체를 읽어 주문 1건당 53ms가 들고, 동시 접수가 같은 운반함을 골라 한쪽이 실패합니다. 하나만 잠그고 가져오는 질의와 500건 단위 나눠 저장으로 바꿉니다.
2. **포화 처리량의 상한은 박스 재고 잠금입니다.** 연결을 20개 넘게 늘려도 처리량이 오르지 않고 잠금 대기열만 늡니다. 잠금을 쥔 채 실행하는 집계를 밖으로 빼고, 잠금 대기 자체에 상한을 두는 실험이 남았습니다.
3. **재고 합산의 60초 가정.** 변동 내역이 60초 안에 확정된다는 가정을 DB 설정으로 강제하는 방법이 남았습니다.
4. **서버 2대 전환.** 필요한 이유는 성능이 아니라 무중단 배포이며, 합산 작업의 중복 실행 방지와 로드밸런서 구성이 필요합니다.
5. **S3 업로드가 SDK 안에서 멈춘 원인.** 11,427건 중 1건이 9.9초 걸렸고 재현되지 않았습니다. 상한과 호출별 지표를 넣어 두었으므로 다음 발생 때 단계를 확정합니다.
