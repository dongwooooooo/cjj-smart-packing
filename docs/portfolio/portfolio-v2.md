### 아키텍처 설계 이유

1. **치수 추론은 GPU 서버 대신 Lambda(CPU)에 두었습니다.** 시연처럼 시간대가 정해져 있으면 GPU도 그 시간만 켤 수 있지만, 운영에서 입고 시각은 불규칙합니다. GPU 인스턴스는 시간당 과금이라 켜 둔 시간 전체를 내고(g4dn.xlarge 온디맨드 시간당 0.526달러, 상시 가동 시 월 약 380달러, instances.vantage.sh), Lambda는 호출한 만큼만 냅니다(시연 기간 호출 319건은 1센트 수준, 시연 시간대 8시간 Provisioned Concurrency 예약은 하루 약 0.4달러, aws.amazon.com/lambda/pricing). 모델을 ONNX로 변환하고 ONNX Runtime에서 실행해 CPU 추론 시간을 1.07초(PyTorch)에서 185ms로 줄였습니다(로컬 CPU, 모델 실행만). 콜드스타트는 최대 9.5초라 시연 시간대에만 Provisioned Concurrency(미리 띄워 둔 실행 환경)를 예약하고 배포 직후 웜업 호출을 넣었습니다(24시간 운영은 더 개선할 부분 6). 응답 목표는 p95 1초이고, 319건 중 배포 검증일과 콜드스타트를 뺀 웜 호출 246건의 핸들러 p95는 609ms였습니다(사진 82~353KB, 디코딩·전처리 포함).
2. **재고는 현재 수량을 갱신하지 않고 변동을 원장에 쌓습니다.** (Problem 1)
3. **박스 편성은 부피 비교 대신 3D 빈 패킹(3D Bin Packing) 시뮬레이션으로 판정하고, 총 배송비를 최소화합니다.** (Problem 3)
4. **촬영 사진 업로드는 추론과 병렬로 실행하고, 둘 다 끝나면 응답합니다.** (Problem 4)
5. **모델은 자동 검증을 통과한 것만 배포합니다.** (Problem 5)
6. **API 서버는 1대입니다.** 시연 규모와 부하 테스트 결과(Problem 2)에서 1대로 처리량이 남아, 이중화는 무중단 배포가 필요해질 때로 미뤘습니다(더 개선할 부분 5).

## 부하 테스트 v1 ~ v5

**목적.** 창고 규모의 동시 작업에서 어디서 먼저 병목이 생기는지 찾기 위해 수행했습니다. 시연은 작업자 1명이었습니다.

**도구·환경.** 부하 발생 k6, 지표 수집 Prometheus·Grafana(응답 시간, HikariCP 커넥션 풀, Tomcat 스레드, DB 대기 이벤트(wait event)). API 서버 EC2(2 vCPU), DB RDS(2 vCPU, 메모리 1GB). 시나리오는 작업자 행동 단위입니다. 촬영은 "촬영 버튼 → 결과 확인", 포장은 "토트(상품을 담아 옮기는 운반함) 스캔 → 주문 확인 → 포장 완료"입니다. 작업자는 포장 1건을 1초 간격으로 반복합니다. 이 속도는 현장 속도(작업자당 분당 1~2건)의 30~60배입니다.

## Problem 1. 동시 포장 시 재고 갱신 데드락과 원장 전환

**[문제배경]**
포장 작업자 50명이 동시에 포장 완료를 누르자 요청의 40.4%가 실패했습니다(10명에서는 12.1%). 포장 완료는 박스 1개 단위로 처리되며, 그 박스에 담긴 상품마다 락을 걸고 재고 수량을 1씩 줄입니다. 박스마다 상품을 잠그는 순서가 달라 데드락이 발생했습니다.

같은 테스트에서 재고 감소분이 실제 포장 건수의 절반만 반영됐습니다(갱신 손실). 락은 잡혔지만 갱신에 쓴 값이 락 이전에 읽어 둔 값이었습니다. 테스트 준비 중에는 관리자 재고 조정이 별도 이력에만 기록되고 수량에는 반영되지 않는 문제도 나왔습니다(재고 이중 기록). 조정으로 늘린 재고가 수량에서는 0으로 남아 주문 접수가 전부 거절됐습니다.

**[접근법]**

| 방안 | 평가 |
| :-: | :-: |
| 단일 쿼리로 원자적 갱신 + 락 획득 순서 통일 | 데드락과 갱신 손실은 막힘. 상품 락은 남아 다품목 박스일수록 락 경합이 늘고, 변동 이력이 없음. 실측하지 않고 기각 |
| 낙관적 락(Optimistic Lock) | 잠그지 않고 갱신 시 충돌을 감지해 재시도. 동시 요청이 많을수록 재시도가 늘어남. 실측하지 않고 기각 |
| **원장** | 수량을 고치지 않고 "−1" 같은 변동을 한 줄씩 추가. 상품 락 없음. 대가: 현재 수량을 읽는 집계 구조, 원장 행이 60초 안에 커밋된다는 전제, 원장 보관 정책 |

이중 기록은 어느 안이든 관리자 조정 경로를 고쳐야 없어집니다. 원장에서는 조정도 원장 행 추가라 경로가 하나로 모입니다.

채택안에서 현재 수량은 5초마다 원장을 집계해 둔 스냅샷에, 아직 집계되지 않은 원장 행을 더해 읽습니다. 집계는 기록된 지 60초가 지난 행만 대상으로 하는데, 시퀀스 ID 순서와 커밋 순서가 같다고 가정하면 늦게 커밋된 행을 영구히 건너뛸 수 있기 때문입니다(더 개선할 부분 3). 1분마다 스냅샷과 원장 전체를 대조해 어긋나면 다시 계산합니다(원장 105만 건 기준 0.3초).

재고 부족 판정은 주문 접수 단계에서 이 값으로 하고, 포장 완료에서는 하지 않습니다. 포장대에 온 상품은 이미 창고에서 꺼낸 실물이기 때문입니다. 접수 단계의 판정은 전환 전에도 락 없이 수량을 읽었으므로, 동시 접수 경합은 전환 전과 같습니다(더 개선할 부분 4).

포장 박스 자재 재고는 락을 유지합니다. 박스는 포장 시점에 소모되므로 부족하면 즉시 막아야 합니다. 포장 완료 1건이 박스 1개만 쓰고 락도 하나만 잡으므로 데드락이 생기지 않습니다. 포화 부하에서의 영향은 Problem 2에 있습니다.

**[사용이유]**
상품 락을 잡지 않으니 데드락과 갱신 손실이 생기지 않고, 모든 변동이 원장 한 곳에 남아 재고 불일치를 추적할 수 있습니다.

**[결과]** 같은 부하(작업자 50명, 3분). TPS는 포장 완료 건/초이고, 작업자 1명의 사이클에는 요청 3개의 응답 대기와 1초 휴지가 들어갑니다.

| | 전환 전 | 전환 후 |
| :-: | :-: | :-: |
| 에러율 | 40.4% | 0% |
| 포장 완료 p95 | 10.07초(프론트엔드 타임아웃에서 끊긴 값) | 73ms |
| 처리량 | 2.9 TPS | 32.6 TPS |
| 데드락 | 356건 | 0건 |
| 원장 합계와 포장 건수 | 감소분이 절반 | 일치 |

`[캡처] docs/evidence/loadtest/20260924-160456-packing/grafana-packing-after.png — 전환 후: 커넥션 대기 0`

관리자 조정 뒤 주문 접수는 별도 조건(1,000건 배치)에서 전부 거절에서 정상 접수로 바뀌었습니다. 현장 속도에서 데드락 빈도는 측정하지 않았습니다.

**집계 쿼리의 풀 스캔.** 커넥션 풀 실험(v5) 중 원장이 2만 건에서 105만 건으로 쌓이는 4시간 동안 같은 조건의 처리량이 절반으로 떨어졌습니다. 집계 범위를 구하는 쿼리가 원장 전체를 풀 스캔한 탓이었습니다. 인덱스 범위 스캔으로 고쳐 원장 105만 건 기준 쿼리 시간을 3.39초에서 0.66ms로 줄였습니다. 무부하 DB CPU는 26~30%에서 5~7%로 돌아왔습니다(원장 보관 정책은 더 개선할 부분 8).

## Problem 2. 커넥션 풀 크기와 커넥션 타임아웃 결정

**[문제배경]**
v3에서 락 대기 요청이 커넥션을 점유하자 락과 무관한 요청까지 최대 10.5초를 기다렸습니다. 원장 전환 뒤에도 박스 락은 남았습니다. 커넥션 풀은 HikariCP 기본값(풀 크기 10, 커넥션 타임아웃 30초)을 그대로 썼고, 이 창고 규모에 맞는지는 측정하지 않았습니다. 30초로 두면 프론트엔드 타임아웃(10초)이 지난 요청도 서버에서 20초 더 커넥션을 기다립니다.

`[캡처] docs/evidence/loadtest/20260922-104007-packing/grafana-packing-run6.png — v3 50명: 커넥션 대기 스레드 39`

**[접근법]**

| 방안 | 평가 |
| :-: | :-: |
| HikariCP 권장 공식(코어 수 × 2 + 유효 스핀들 수)으로 계산 | 4개. 커넥션 점유 시간이 DB 실행 시간과 같다는 전제라 이 시스템에 맞는지 알 수 없음 |
| 리틀의 법칙(Little's Law)으로 추정 | 6개. 평균 기반이라 포화·락 대기를 반영 못 함 |
| **부하를 고정하고 풀 크기·타임아웃만 바꿔 실측** | 판정 규칙과 예측을 실험 전에 적음 |

리틀의 법칙에는 동시 작업자 100명(창고 규모 미확인, 가정)이 분당 1건 포장하고 1건에 요청이 3개인 부하, 즉 초당 5건을 넣었습니다. 여기에 요청당 점유 22ms를 곱하면 평균 동시 커넥션은 0.11개입니다. 피크 3배(0.33개)에서 4개 이상 겹칠 확률은 포아송 기준 0.04%이고, 일괄 접수 1개와 집계 스케줄러 1개를 더해 6개입니다.

- 풀 크기 규칙(하한): 커넥션 대기가 사라지는 최소 풀, 최고 처리량의 98%를 내는 최소 풀. 풀 크기 규칙(상한): DB 락·I/O 대기 비중이 5%p 넘게 늘기 시작하는 풀, 처리량은 늘지 않고 p95만 20% 넘게 나빠지는 풀.
- 타임아웃 규칙: 락 구간에서 락과 무관한 요청이 프론트엔드 타임아웃(10초)보다 먼저 실패하고, 현장 피크에서는 타임아웃이 0건인 가장 작은 값.
- 예측: 현장 피크에서는 풀 크기와 무관하게 처리량이 같고, 풀 5개 이상이면 커넥션 획득 시간이 1ms 미만일 것으로 봤습니다.
- 부하: 현장 피크(100명·300명, 분당 1건), 포화(100명, think time 0 — 응답을 받자마자 다음 요청), 락 점유 주입(박스 재고 1건을 20초 잠근 상태에서 커넥션 타임아웃 30초·3초·1초 비교).

**[사용이유]**
풀 크기는 기본값과 같은 10개를 유지했습니다. 하한 규칙은 5·20개, 상한 규칙은 10·30개를 가리켜 20개와 10개 사이에서 충돌했습니다. 규칙 간 우선순위는 실험 전에 정해 두지 않았고, 둘 중 DB 대기 비중이 낮은 10개를 골랐습니다. 커넥션 타임아웃은 30초에서 3초로 바꿨습니다. 타임아웃 규칙은 현장 피크 기준이라 1초도 통과하지만, 포화 부하에서 성공했어야 할 요청이 에러로 끝나 3초로 올렸습니다. 3초가 지나 에러를 받은 작업자는 화면에서 다시 시도합니다.

**[결과]**

## Problem 3. 박스 편성 — 부피 비교에서 3D 빈 패킹으로, 무게를 목적 함수에

**[문제배경]**
박스 편성의 초기 규칙은 "상품 부피 합이 박스 부피보다 작으면 된다"였습니다. 30×30×30cm 박스에 25×25×20cm 상품 두 개는 부피로는 들어가지만 어떤 방향으로도 함께 들어가지 않습니다. 사전 필터는 가장 큰 박스에 안 들어가면 어느 박스에도 안 들어간다고 가정했습니다. 그러나 박스 호수(1호·2호처럼 크기 등급)가 커져도 세 변이 모두 커지지는 않습니다. 그래서 가장 큰 박스에는 안 맞지만 긴 소형 박스에는 들어가는 상품을 잘못 거부했습니다.

발표 심사에서 현업 심사위원이 묻기 전까지 무게는 계산에 없었습니다. 택배 요금은 크기 구간과 무게 구간 중 높은 쪽으로 정해지므로, 무게를 빼면 요금이 한 구간 올라가는 편성이 최적으로 나옵니다. 예상 무게가 요금을 정하므로 실측 무게가 예상과 다르면 요금도 달라집니다.

**[접근법]**

박스 판정

| 방안 | 평가 |
| :-: | :-: |
| 부피 합산 비교 | 들어가지 않는 박스를 추천. 현장에서 재포장 |
| 상품 하나씩 6방향 회전 검사 | 여러 상품을 함께 넣을 때를 판정 못 함 |
| 주문 분할 후 박스 판정 | 분할 방식이 고정돼 박스 수를 줄이는 조합을 못 찾음 |
| **3D 빈 패킹 휴리스틱 + 국소 탐색(local search), 모든 박스 호수를 후보로 검사** | 판정이 곧 실제 배치. 주문 분할과 적재를 같은 목적 함수로 최적화 |

무게 반영

| 방안 | 평가 |
| :-: | :-: |
| 박스마다 무게 한도 하나 | 한도가 택배 취급 한도(20kg)와 같음. 20kg 초과 주문은 어느 안이든 나눠야 하므로 이 안이 바꾸는 편성이 없음 |
| 요금 구간의 무게 상한을 박스의 물리 한도로 사용 | 예: 무게 상한 2kg 구간의 박스에 2.5kg 주문이 오면 두 박스로 나눔. 실제로는 한 박스로 보내고 요금 구간만 오르면 됨 |
| **목적 함수를 총 배송비로 교체** | 배송비가 같으면 박스 수가 적은 쪽, 그것도 같으면 총 부피가 작은 쪽 |

적재 알고리즘은 박스 안 빈 모서리(extreme point)마다 상품을 6방향으로 놓아 봅니다. 초기 해는 부피 내림차순 최초 적합(First Fit)으로 만들고, 상품을 다른 박스로 옮기거나 박스를 늘리는 국소 탐색으로 개선합니다. 박스를 늘리는 이동을 넣은 이유는 나누는 편이 싼 경우가 있어서입니다. 요금표는 CJ대한통운 2024 표준운임입니다. 상품 하나가 택배 취급 한도를 넘으면 거부합니다. 포장 완료 때 실측 무게가 예상과 3%(최소 0.1kg) 넘게 다르면 완료를 차단합니다.

**[사용이유]**
3D 빈 패킹은 다항 시간 알고리즘이 알려지지 않은 문제(NP-hard)라, 주문당 상품 평균 16.5개를 실시간으로 처리하려면 휴리스틱이 필요합니다. 배송비를 1순위로 두고 박스 수와 부피는 동점을 가르는 기준으로 썼습니다.

**[결과]**

| 검증 | 결과 |
| :-: | :-: |
| "부피 합은 통과하나 배치 불가" 테스트 | 부피 방식 실패, 3D 빈 패킹 통과 |
| "부피 큰 박스가 치수로 탈락" 테스트 | 가장 큰 박스에 안 맞아도 다른 호수에서 통과 |
| "무게로 요금이 오르면 나눠 담기" 테스트 | 한 박스에 담기는 주문을 배송비 기준으로 둘로 나눔 |
| 합성 주문 벤치마크(재고관리 단위(SKU) 500종, 주문당 상품 평균 16.5개, 단일 스레드) | 주문당 p50 2.3ms, p95 13.8ms. 5,000건 21.0초 |
| 기존 부피 방식 대비 추천 변경 비율·배송비 차이, 최적해 대비 품질 | 미측정(더 개선할 부분 7) |

`[캡처] docs/evidence/benchmark/screens/bench-console.png — 벤치마크 콘솔: 100·1,000·5,000주문 p50/p95/최대`

**벤치마크가 잡은 예외.** 국소 탐색이 상품 하나를 다른 박스로 옮길 때 받는 쪽만 다시 판정하고, 상품을 뺀 쪽은 그대로 담긴다고 가정했습니다. 휴리스틱 판정이라 17개는 담기는데 하나를 뺀 16개는 못 담긴다고 나오는 주문이 있었습니다. 박스를 정하지 못한 편성이 요금 계산으로 넘어가 예외가 발생했습니다. 같은 예외가 주문 접수 API에서 발생했다면 500 응답으로 끝났을 것입니다. 뺀 쪽도 판정하도록 고치고 그 주문을 회귀 테스트로 고정했습니다.

## Problem 4. 촬영 사진 업로드 경로 재설계

**[문제배경]**
v1에서 응답은 정상인데 45명부터 S3에 올라가지 않는 사진이 생겨 1,155장이 남았습니다. 비동기 업로드 작업은 메모리 안 큐에 들어갑니다. 큐가 차면 작업이 에러 없이 버려지고, 다시 올리는 경로가 없어 그 사진은 S3에 영구히 올라가지 않습니다(큐에 남은 작업은 나중에 처리).

이 비동기 업로드는 v1 이전에 도입한 것입니다. 처음 촬영 API는 사진 3장을 읽고, 추론을 호출하고, 결과와 사진을 저장한 뒤 응답했습니다. 추론 대기를 뺀 API 서버 처리 구간의 p50은 사진 읽기 6~15ms, 요청 조립 12~21ms, 응답 파싱 1~8ms, 저장(DB 커밋과 사진 3장 S3 업로드) 32~81ms였습니다(로컬, 사진 57KB·490KB 두 종류). 업로드가 트랜잭션 안에 있어 그동안 커넥션도 점유했습니다. 업로드를 커밋 뒤 비동기로 옮기자 저장 구간 p95는 36ms에서 12ms로, 백엔드 처리 p95(추론 대기 포함)는 243ms에서 192ms로 줄었습니다(로컬, 사진 490KB).

**[접근법]**

| 방안 | 평가 |
| :-: | :-: |
| 커밋 뒤 비동기 업로드 (1차 적용) | 응답은 빠르지만 큐 포화·프로세스 재시작 때 사진 유실 |
| 남은 사진을 스케줄러가 다시 업로드 | 응답 시점에 사진이 없는 상태는 그대로 |
| 클라이언트가 presigned URL(서버가 발급한 임시 업로드 주소)로 S3에 직접 업로드 | 추론용 사진을 서버가 따로 받아야 해서 사진을 두 번 전송하거나 추론이 S3에서 읽어야 함. 프론트엔드 변경 |
| 사진을 먼저 올리고 추론이 S3에서 읽기 | 추론 API 입력 형식을 바꿔야 하고 응답에 업로드 시간이 더해짐 |
| 메시지 큐 + 업로드 워커 | 유실은 막지만 브로커 운영이 추가됨 |
| **추론과 업로드를 병렬 실행, 둘 다 끝나면 응답** | 업로드 3장 병렬 37ms가 추론 호출 320ms(Lambda 왕복 p50) 안에 끝남. 응답이 곧 "사진 저장 완료" |

업로드는 전용 스레드 풀에서 트랜잭션 밖으로 실행해 커넥션을 점유하지 않습니다. 스레드 풀이 포화되면 작업을 거절하지 않고 요청 스레드가 직접 업로드하며, 업로드 대기가 8초를 넘으면 에러 응답으로 끝냅니다. 업로드가 실패하면 3회 재시도한 뒤 에러 응답을 보내고, 추론 결과는 저장하지 않으며, 작업자가 다시 촬영합니다. 추론이나 DB 저장이 실패하면 S3에 올라간 사진은 그대로 남습니다. 조회되지 않는 객체라 기능에는 영향이 없습니다(더 개선할 부분 9).

**[사용이유]**
병렬 실행은 메시지 큐 안과 달리 브로커 없이, 응답 시간을 유지하면서 사진 저장을 응답의 조건으로 만들 수 있었습니다.

## Problem 5. 모델 배포 전 정확도 회귀 자동 검증

**[문제배경]**
모델을 바꿀 때 나아졌는지 판정할 기준이 없었습니다. 학습 환경에서 측정한 평균 절대 오차(MAE)는 가로 기준 1.31cm였는데, 서비스 코드로 고정 검증셋 2,024품목을 측정하니 2.06cm였습니다. 학습 리포트의 검증 분할과 서비스용 고정셋이 달랐고, 서비스 평가만 촬영 각도를 고정했습니다. 두 원인의 기여도는 나누지 못했습니다. 양자화처럼 속도를 얻고 정확도를 잃을 수 있는 후보도 같은 기준으로 걸러야 했습니다. 판정 지표는 MAE와 ±3cm 적중률(3축 모두 ±3cm 안에 든 품목의 비율)입니다.

**[접근법]**

| 방안 | 평가 |
| :-: | :-: |
| 학습 리포트의 수치를 그대로 신뢰 | 평가 방법이 서비스와 달라 비교가 안 됨 |
| 절대 상한(MAE 3cm)만 검사 | 상한 안에서 서서히 나빠지는 회귀를 못 잡음 |
| **직전 모델 대비 회귀 기준 + 절대 상한, 고정 검증셋으로 매번 같은 방법 평가** | 회귀 기준 MAE +0.2cm, ±3cm 적중률 −2%p 이내. 절대 상한 MAE 3cm. 두 기준값은 초기값이고 운영 데이터로 조정 |

통과한 모델만 Lambda 별칭(alias, 특정 모델 버전을 가리키는 이름)에 연결합니다.

**[사용이유]**
절대 상한만 두는 안은 상한 안의 회귀를 놓치므로 직전 모델 대비 기준을 함께 둡니다. 적중률은 박스 추천에 그대로 쓸 수 있는 품목의 비율이라 MAE와 별도로 봅니다. 기준 모델의 62.5%는 품목 3개 중 1개가 한 축 이상 3cm 넘게 틀린다는 뜻입니다. 입고 작업자가 화면에서 치수를 확인해 확정하는 단계가 이 오차를 흡수합니다(수정 비율은 미측정, 더 개선할 부분 10).

**[결과]**

| 후보 | 축별 MAE (가로/세로/높이, cm) | ±3cm 적중률 | 모델 실행 시간(평가 서버 2 vCPU) | 판정 |
| :-: | :-: | :-: | :-: | :-: |
| 기준 모델(32비트 부동소수점, FP32) | 2.06 / 2.17 / 1.62 | 62.5% | 243ms | 기준선 |
| 16비트 부동소수점(FP16) | 동일 | 62.5% | 243ms | 통과, 이득 없음 |
| 8비트 정수 양자화(INT8) | 3.57 / 3.24 / 2.89 | 22.6% | 164ms | 차단 |

`[캡처] docs/evidence/eval/screens/gate-run-jobs.png — GitHub Actions: 빌드 → 정확도 검증 → Lambda 갱신 3잡 통과`

INT8은 MAE 기준으로 차단됐습니다. 축별 MAE는 1.1~1.5cm 나빠졌는데 적중률은 40%p 떨어졌습니다. 오차가 품목 전반에 퍼졌다는 뜻입니다. 재학습 없이 통과하는 추론 시간 단축 후보는 없었습니다.

## 더 개선할 부분

1. **주문 접수의 토트 배정.** v2에서 찾은 문제입니다. 락이 걸린 행은 건너뛰고 한 건만 잠가 가져오는 방식과 500건 단위로 묶어 저장하는 방식으로 바꿉니다.
2. **포화 처리량의 상한인 박스 재고 락.** 락을 잡은 채 실행하는 조회(포장 라인별 건수)를 트랜잭션 밖으로 빼고 트랜잭션 안의 애플리케이션 처리 구간(점유 시간의 74%)을 줄입니다. 락 대기 시간 상한을 실험합니다.
3. **원장 집계의 커밋 시간 전제.** 이 전제를 트랜잭션 최대 실행 시간 제한으로 강제합니다.
4. **주문 접수의 재고 경합.** 접수 단위로 직렬화합니다.
5. **API 서버 이중화.** 집계 스케줄러 중복 실행 방지(분산 락)와 로드밸런서 구성이 필요합니다.
6. **24시간 운영의 콜드스타트.** Provisioned Concurrency 상시 예약 비용과 주기적 웜업 호출을 월 비용과 첫 응답 지연으로 비교해 정합니다.
7. **박스 편성 효과 측정.** Problem 3 벤치마크와 같은 합성 주문으로 부피 방식 대비 추천 변경 비율과 배송비 차이를 비교하고, 소형 주문은 전수 탐색과 비교해 휴리스틱 품질을 확인합니다.
8. **원장 보관 정책.** 오래된 원장 행을 스냅샷에 합산하고 따로 보관하는 정책을 정합니다.
9. **S3 잔존 사진 정리.** 추론·저장 실패 뒤 남은 객체를 정리하는 규칙을 정합니다.
10. **모델 정확도.** 양자화 인식 학습(QAT)을 적용하고, 작업자의 치수 수정 비율을 측정합니다.
