### 아키텍처 설계 이유

1. **치수 추론은 GPU 서버 대신 CPU 서버리스(Lambda)에 두었습니다.** 입고는 간헐적이라 GPU를 상시 켜 두면 사용량과 무관하게 비용이 나갑니다. 모델을 ONNX로 변환해 ONNX Runtime(CPU)에서 실행합니다(Problem 4).
2. **재고는 현재 수량을 갱신하지 않고 변동을 원장에 쌓습니다.** 동시 포장에서 같은 상품 수량을 갱신하려는 요청끼리 락을 기다리다 데드락이 났습니다(Problem 1).
3. **촬영 사진 업로드는 추론과 병렬로 실행합니다.** 업로드가 API 서버 처리 시간에서 가장 큰 몫이었고, 응답 뒤로 미루자 사진이 유실되는 구조가 됐습니다(Problem 4).
4. **모델은 자동 검증을 통과한 것만 배포합니다.** 학습 환경에서 측정한 오차와 서비스 코드로 측정한 오차가 달랐습니다(Problem 5).

## Problem 1. 동시 포장 시 재고 갱신 데드락 → 원장 전환

**[문제배경]**
포장 작업자 50명이 동시에 포장 완료를 누르자 요청의 40.4%가 실패했습니다. 포장 완료는 주문의 상품마다 재고 수량을 1씩 줄입니다. 수량을 갱신하는 동안 다른 요청이 같은 상품을 건드리지 못하게 락을 겁니다. 주문마다 상품 순서가 달라서 A는 사과를 잠근 채 배를 기다리고 B는 배를 잠근 채 사과를 기다리는 데드락(교착 상태)이 났습니다. 데드락에 걸린 요청이 커넥션을 점유한 채 기다리자, 락과 관계없는 조회까지 커넥션을 얻지 못해 최대 10.5초 지연됐습니다.

같은 원인으로 두 문제가 더 있었습니다. 동시 포장 중 재고 감소분이 실제 포장 건수의 절반만 반영됐습니다(Lost Update). 락 쿼리를 실행했지만 락 전에 읽어 둔 객체 값을 그대로 써서 락이 효과가 없었습니다. 관리자 재고 조정은 별도 이력에만 기록되고 수량에는 반영되지 않아 주문 접수가 전부 거절된 일도 있었습니다(재고 이중 기록). 세 문제 모두 재고를 "현재 수량 한 값"으로 저장하고 그 값의 갱신을 락에 묶어 둔 구조에서 나왔습니다.

**[접근법]**

| 방안 | 내용 | 평가 |
| :-: | :-: | :-: |
| 원자적 UPDATE + 락 획득 순서 통일 | 차감을 한 문장으로, 상품은 항상 같은 순서로 잠금 | Lost Update와 데드락은 막힘. 락 대기가 커넥션을 점유하는 구조와 재고 이중 기록은 그대로 |
| 낙관적 락(Optimistic Lock) | 잠그지 않고 갱신 시 충돌을 감지해 재시도 | 동시 요청이 많을수록 재시도가 늘어남. 실측하지 않고 기각 |
| **원장(append-only ledger)** | 수량을 고치지 않고 "−1" 같은 변동을 한 줄씩 INSERT | 현재 수량을 읽는 방법을 따로 설계해야 함 |

**[사용이유]**
INSERT만 하는 원장에는 락이 필요 없습니다. 현재 수량은 5초마다 원장을 집계해 둔 스냅샷에, 아직 집계되지 않은 원장 행을 더해 읽습니다. 집계가 늦어도 읽는 값이 원장 합과 같도록 설계했고, 1분마다 스냅샷과 원장 전체를 대조해 어긋나면 다시 계산합니다. 재고 부족 판정은 주문 접수 단계에서 이 값으로 하고, 포장 완료에서는 하지 않습니다. 포장대에 온 상품은 이미 창고에서 꺼낸 실물이기 때문입니다. 포장 박스 자재 재고는 락을 유지했습니다. 박스는 포장 시점에 소모되어 부족하면 즉시 막아야 하고, 종류가 6개라 락 순서가 하나뿐이어서 데드락이 나지 않습니다.

**[결과]** 같은 부하(작업자 50명, 3분)

| | 전환 전 | 전환 후 |
| :-: | :-: | :-: |
| 에러율 | 40.4% | 0% |
| 포장 완료 p95 | 10.07초 | 73ms |
| 처리량 | 2.9 TPS | 32.6 TPS |
| 데드락 | 356건 | 0건 |

**전환 뒤 잡은 결함 2건.** 코드 검토에서, 집계가 "시퀀스 ID 순서 = 커밋 순서"라고 가정해 늦게 커밋된 행을 건너뛸 수 있는 결함을 찾았습니다. 커밋된 지 60초가 지난 행만 집계하도록 바꿨습니다. v5에서 찾은 처리량 하락은 이 집계 쿼리가 원인이었습니다. 집계 범위를 찾는 쿼리가 원장 전체를 풀 스캔하고 있었습니다. 인덱스 범위 스캔으로 고쳐 원장 105만 건에서 3,393ms를 0.66ms로 줄였고, 무부하 DB CPU가 26~30%에서 5~7%로 돌아왔습니다.

## Problem 2. 커넥션 풀 크기와 커넥션 타임아웃을 부하 실험으로 결정

**[문제배경]**
커넥션 풀은 HikariCP 기본값(풀 크기 10, 커넥션 타임아웃 30초) 그대로였습니다. 10개가 이 창고 규모에 맞는지 측정한 적이 없었습니다. 30초는 프론트엔드 타임아웃(10초)이 지난 요청을 서버가 20초 더 붙들고 있게 두는 값이었습니다.

**[접근법]**
부하를 고정하고 풀 크기만 바꾸며 처리량, 커넥션 획득 시간, 커넥션 점유 시간, DB 대기 이벤트(wait event)를 같은 표에 놓았습니다. 판정 규칙은 실험 전에 정했습니다. 최고 처리량의 98%를 내는 최소 풀, 커넥션 대기가 사라지는 최소 풀, DB 락·I/O 대기 비중이 5%p 넘게 늘기 시작하는 풀, 처리량 없이 p95만 20% 넘게 나빠지는 풀.

1. 리틀의 법칙(Little's Law)으로 필요 커넥션 수 추정. 작업자 100명이 분당 1건 포장, 1건에 요청 3개 → 초당 5건. 요청당 커넥션 점유 22ms → 평균 동시 커넥션 0.11개. 동시 5개 이상 겹칠 확률은 0.04%. 여기에 일괄 접수 1개와 집계 스케줄러 1개를 더해 6개면 충분하다는 계산입니다.
2. 세 가지 부하. 현장 피크(100명·300명, 분당 1건), 포화 부하(100명, think time 0), 락 점유 주입(박스 재고 1건을 20초 잠근 상태에서 커넥션 타임아웃 30초·3초·1초 비교).

**[사용이유]**
HikariCP 권장 공식(코어 수 × 2 + 유효 스핀들 수)은 4개인데, 포화 처리량은 풀 10개에서 125 TPS로 4~5개(78 TPS)보다 높았습니다. 커넥션 점유 시간 대부분이 DB 실행이 아니라 트랜잭션 안에서 애플리케이션이 다음 쿼리를 보내기 전까지의 시간이어서, 같은 코어 수에 더 많은 커넥션이 필요했습니다.

**[결과]**

| 부하 | 결과 |
| :-: | :-: |
| 현장 피크 100·300명 | 풀 5~40개 모두 처리량 같음, 대기 없음. 풀 2개만 300명에서 대기 발생 |
| 포화 | 5→10→20개에서 78→125→137 TPS. 30·40개는 처리량 그대로, p95만 571ms→1.3초(박스 재고 락 대기열만 늘어남) |
| 락 점유 주입 | 30초: 락과 무관한 조회 절반이 6~7초, 일부 10초 타임아웃, Tomcat 작업 스레드 200 포화. 3초·1초: 그 시간에 에러 응답(500), 화면 멈춤 없음 |

풀 크기는 10개로 정했습니다. 20개가 처리량 10% 높지만 DB 락 대기 비중이 19%에서 47%로 뛰어, 처리량 규칙(20)과 DB 대기 규칙(10)이 충돌한 경우 DB 쪽 여유를 택했습니다. 기본값과 같은 숫자지만 이제 근거가 있습니다. 커넥션 타임아웃은 3초로 정했습니다. 1초는 포화 부하에서 성공할 요청의 0.03~2.76%를 에러로 끝냈고, 3초는 실패 0이었습니다. 3초에 에러를 받은 작업자는 화면에서 다시 시도합니다. 재검증에서 기본값 대비 처리량 차이 1%, 에러 0.

`[캡처] docs/evidence/pool-sizing/timeout/peak3x-p10-t30000-th200-r1/grafana.png — 커넥션 타임아웃 30초에서 락 20초 주입: 커넥션 대기 174, Tomcat 작업 스레드 184`

**틀린 예측 2건.** "풀 5개 이상이면 커넥션 획득 시간 1ms 미만"은 실측 1.6ms로 빗나갔습니다. 500ms 넘게 쉰 커넥션을 내주기 전에 하는 유효성 검사(validation) 왕복이 원인이었고, 실험에서 검사를 끄자 0.1ms가 됐습니다(운영에는 적용하지 않았습니다). 풀 30·40개에서 처리량이 무너진다고 판단했으나, 원인은 실험 중 누적된 데이터였습니다. 조건마다 데이터를 초기화하자 처리량은 유지되고 p95만 늘었습니다.

## Problem 3. 박스 편성 — 부피 비교에서 3D 빈 패킹으로, 무게를 목적 함수에

**[문제배경]**
박스 편성(cartonization)은 주문을 어떤 박스 몇 개에 나눠 담을지 정하는 일입니다. 초기 규칙은 "상품 부피 합이 박스 부피보다 작으면 된다"였습니다. 30×30×30cm 박스에 25×25×20cm 상품 두 개는 부피로는 들어가지만 어떤 방향으로도 함께 들어가지 않습니다. 사전 필터는 가장 큰 박스에만 넣어 보는 방식이었는데, 박스 호수가 커져도 세 변이 모두 커지지 않아 안 들어가는 상품을 걸러내지 못했습니다. 무게는 계산에 없었습니다. 택배 요금은 크기 구간과 무게 구간 중 높은 쪽으로 정해지므로, 무게를 빼면 요금이 한 구간 올라가는 편성이 최적으로 나옵니다. 발표 심사에서 현업 심사위원이 무게를 물었습니다.

**[접근법]**

| 방안 | 평가 |
| :-: | :-: |
| 부피 합산 비교 | 들어가지 않는 박스를 추천. 현장에서 재포장 |
| 상품 하나씩 6방향 회전 검사 | 여러 상품을 함께 넣을 때를 판정 못 함 |
| 주문 분할 후 박스 판정 | 분할 방식이 고정돼 박스 수를 줄이는 조합을 못 찾음 |
| **3D 빈 패킹(3D Bin Packing) 휴리스틱 + 국소 탐색(local search)** | 판정이 곧 실제 배치. 주문 분할과 적재를 같은 목적 함수로 최적화 |

무게는 두 안을 기각했습니다. 박스마다 무게 한도 하나를 두는 안은 한도에 걸리는 주문이 거의 없어 편성이 바뀌지 않았습니다. 요금 구간의 무게 상한을 박스의 물리 한도로 쓰는 안은 2.5kg 박스를 그대로 보내도 되는데 나누게 만들었습니다. 채택한 안은 목적 함수를 총 배송비로 바꾸는 것입니다. 배송비가 같으면 박스 수가 적은 쪽, 그다음 총 부피가 작은 쪽입니다. 요금표는 CJ대한통운 2024 표준운임을 넣었습니다. 상품 하나가 택배 취급 한도(20kg)를 넘으면 거부합니다. 포장 완료 때 실측 무게가 예상과 3%(최소 0.1kg) 넘게 다르면 포장 완료를 차단합니다.

**[사용이유]**
무게 때문에 한 박스에 담기더라도 나누는 편이 싼 경우가 있습니다. 그래서 국소 탐색이 박스를 늘리는 이동도 후보로 봅니다.

**[결과]**
박스 편성 테스트 케이스를 21개에서 39개로 늘렸습니다. "부피는 통과하나 배치 불가", "무게로 요금이 오르면 나눠 담기"가 들어 있습니다. 합성 주문 벤치마크(SKU 500종, 단일 스레드)에서 주문당 p50 2.3ms, p95 13.8ms, 5,000건 21.0초입니다. 기존 부피 방식 대비 추천이 바뀐 주문 비율과 배송비 차이는 측정하지 않았습니다.

`[캡처] docs/evidence/benchmark/screens/bench-console.png — 벤치마크 콘솔: 100·1,000·5,000주문 p50/p95/최대`

**벤치마크에서 잡은 결함.** 첫 실행은 예외로 멈췄습니다. 국소 탐색이 상품 하나를 다른 박스로 옮길 때 받는 쪽만 다시 판정하고, 상품을 뺀 쪽은 그대로 담긴다고 가정했습니다. 휴리스틱 판정이라 그 가정은 성립하지 않습니다. 17개는 담기는데 그중 하나를 뺀 16개는 어느 박스에도 못 담긴다고 판정되는 주문이 나왔고, 박스를 못 정한 편성이 요금 계산에서 예외를 냈습니다. 접수 API였다면 500 응답이었을 경로입니다. 뺀 쪽도 판정하도록 고치고 그 주문을 회귀 테스트로 고정했습니다.

## Problem 4. 촬영 API 응답 p95 1초 — 서버리스 전환과 사진 업로드 경로 재설계

**[문제배경]**
추론 호출 타임아웃은 GPU 서버 전제로 8초였습니다. 비용 때문에 CPU 서버리스로 옮기자 콜드스타트가 최대 9.5초로 타임아웃을 넘겼습니다. 8초는 작업자가 버튼을 누르고 기다리는 기준으로도 쓸 수 없는 값이라, 목표를 응답 p95 1초로 다시 정했습니다. 그런데 서버가 사진을 읽고 추론을 부르고 저장하는 구간별 시간을 측정한 적이 없었습니다.

**[접근법]**
1. 모델을 ONNX로 변환해 ONNX Runtime(CPU)에서 실행. 변환 전후 출력 차이가 허용 오차를 넘으면 빌드를 실패시킵니다. 모델 실행 시간 1,070ms → 185ms(로컬 CPU, 사진 3장).
2. 콜드스타트는 시연 시간대에만 Provisioned Concurrency를 예약하고, 배포 직후 웜업 호출을 넣었습니다.
3. 구간 실측: 사진 읽기 / 추론 요청 페이로드 생성 / 추론 호출 / 저장. 저장(DB 커밋과 사진 3장 S3 업로드)이 API 서버 처리 시간에서 가장 큰 몫이었습니다.
4. 업로드 경로 대안. Lambda 메모리 상향은 계정 한도로 불가, 이미지 리사이징은 이득이 작았고, 메시지 큐는 규모 대비 과했습니다. 업로드를 응답 뒤 비동기로 뺐습니다.

**[사용이유]**
응답 경로에서 업로드가 빠지면 그 시간만큼 응답이 빨라지고, 업로드 동안 커넥션을 점유하지 않습니다. 추론 호출도 트랜잭션 밖에서 실행해 느린 호출이 커넥션을 쥐지 않게 했습니다.

**[결과]** 로컬 동일 조건(11종 × 5회)

| | 비동기 전 | 비동기 후 |
| :-: | :-: | :-: |
| 저장 구간 p95 | 36ms | 12ms |
| 클라이언트 E2E p95 | 250ms | 198ms |

시연 환경(실제 AWS) 응답 p95는 611ms로 목표 1초 안입니다. 시연 기간 Lambda 호출 246건은 핸들러 p95 609ms, 8초 초과 0건이었습니다.

**비동기화가 숨긴 실패와 두 번째 수정.** v1에서 응답은 정상인데 사진 1,155장이 S3에 없었습니다. 업로드 작업 큐가 차면 작업이 에러 없이 버려지고, 다시 올리는 경로가 없었습니다.

| 방안 | 평가 |
| :-: | :-: |
| 남은 사진을 스케줄러가 다시 업로드 | 응답 시점에 사진이 없는 상태는 그대로 |

| **추론과 업로드를 병렬 실행, 둘 다 끝나면 응답** | 업로드 3장 병렬 37ms가 추론 호출 320ms 안에 끝나 응답 시간이 유지됨. 응답이 곧 "사진 저장 완료" |

업로드가 실패하면 3회 재시도 뒤 에러 응답을 보내 다시 촬영하게 합니다. 같은 환경에서 두 방식을 비교했습니다.

## Problem 5. 모델 배포 전 정확도 회귀 자동 검증

**[문제배경]**
학습 환경에서 측정한 평균 절대 오차(MAE)는 가로 기준 1.31cm였는데, 서비스 코드로 같은 검증셋을 측정하니 2.06cm였습니다. 평가 방법(데이터 분할, 촬영 각도 고정 여부)이 달라서 생긴 차이였습니다. 이 상태로는 모델을 바꿀 때 나아졌는지 판정할 기준이 없었습니다. 양자화처럼 속도를 얻고 정확도를 잃을 수 있는 후보를 걸러낼 기준이 필요했습니다.

**[접근법]**
검증셋 2,024품목을 고정하고, 배포할 모델 그대로 같은 방법으로 평가합니다. 판정은 직전 모델 대비 회귀(MAE +0.2cm, ±3cm 적중률 −2%p 이내)와 절대 상한(MAE 3cm, 박스 편성 여유 3cm에서 가져온 값) 둘 다 통과해야 합니다. ±3cm 적중률은 3축 모두 ±3cm 안에 든 품목의 비율입니다. 통과한 모델만 Lambda 별칭(alias)에 연결합니다.

**[사용이유]**
평균 오차 하나로는 오차 분포가 넓어진 모델을 잡기 어렵습니다. 적중률을 함께 봅니다.

**[결과]**

| 후보 | 축별 MAE (가로/세로/높이, cm) | ±3cm 적중률 | 추론 시간 | 판정 |
| :-: | :-: | :-: | :-: | :-: |
| 기준 모델(FP32) | 2.06 / 2.17 / 1.62 | 62.5% | 243ms | 기준선 |
| FP16 | 동일 | 62.5% | 243ms | 통과, 이득 없음 |
| INT8 양자화 | 3.57 / 3.24 / 2.89 | 22.6% | 164ms | 차단 |

INT8은 1.48배 빠르지만 MAE 기준으로도 차단됩니다. 평균 악화 1.5cm에 비해 적중률은 62.5%에서 22.6%로 떨어져, 오차가 일부 품목·축에 몰려 있음을 평균이 가립니다. 재학습 없이 통과하는 추론 시간 단축 후보는 없었습니다. 추론 시간은 평가 서버(2 vCPU) 기준입니다.

## 더 개선할 부분

1. **주문 접수의 토트 배정.** v2에서 찾은 문제입니다. 락이 걸린 행은 건너뛰고 한 건만 잠가 가져오는 쿼리(SKIP LOCKED)와 500건 단위 배치 INSERT로 바꿉니다. 재고 정합성과 커넥션 풀을 먼저 처리하느라 착수하지 못했습니다.
2. **포화 처리량의 상한은 박스 재고 락입니다.** 락을 쥔 채 실행하는 라인별 포장 건수 조회를 트랜잭션 밖으로 빼고, 락 타임아웃(lock_timeout)을 실험합니다.
3. **원장 집계의 60초 가정.** 원장 행이 60초 안에 커밋된다는 가정을 트랜잭션 최대 실행 시간 제한으로 강제하는 방법이 남았습니다.
4. **API 서버 이중화.** 서버 1대라 장애 지점이 하나이고 무중단 배포가 안 됩니다. 집계 스케줄러 중복 실행 방지(분산 락)와 로드밸런서 구성이 필요합니다.
5. **24시간 운영의 콜드스타트.** Provisioned Concurrency 상시 예약 비용과 주기적 웜업 호출을 비교해 정해야 합니다.
