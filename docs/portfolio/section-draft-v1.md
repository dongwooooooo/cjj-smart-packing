## 요구사항과 MVP 범위

풀필먼트 전체 공정 중 입고와 출고 두 지점만 다뤘습니다. 입고 작업자는 신상품을 고정 카메라 아래 올려 촬영하면 화면에 치수가 표시되고, 확정 후 수량을 입고합니다. 포장 작업자는 토트를 스캔하면 배송 단위의 주문 내역과 추천 박스를 보고 포장을 완료합니다.

### 기능 요구사항

  - 촬영 사진 3장에서 가로·세로·높이(cm)를 추론하고, 작업자가 확정한 값만 상품 마스터에 저장합니다.
  - 출고지시를 배치로 받아 배송 단위 편성, 박스 추천, 라인 배정, 토트 할당을 한 트랜잭션으로 처리합니다.
  - 재고 차감은 포장 완료 시점 한 곳에서만 일어납니다.

### 비기능 요구사항

  - 추론은 동기 응답이며 계약 타임아웃은 8초입니다. 초과하면 측정 실패로 기록하고 재촬영합니다.
  - 추론 모델 서버가 준비되기 전에도 입고 흐름 전체가 동작해야 합니다(미설정 시 mock 응답).
  - 같은 입력의 배치 편성은 항상 같은 결과를 냅니다(결정성).

### MVP에서 다루지 않은 것

  - 피킹, 창고 적재 방식, 창고 사용률 예측
  - 3D 형상 재구성, 무게 자동 추정(저울 연동값 사용)
  - 실시간 창고 시스템 연동

## 문제 1. 출고지시 배치 — 부피 근사가 아닌 배치 기반 박스 추천

### 문제 배경

출고지시 배치를 받으면 주문별로 어떤 박스 몇 개에 담을지 결정해야 했습니다. 원본 MVP 문서에는 "6방향 회전, 3cm 마진, 최소 박스" 초안 규칙만 있었고 완충재·분할·적층불가 처리는 정의되지 않아 개발을 시작할 수 없었습니다.

  - **부피 합산의 무효 추천:** 상품 부피 합이 박스 부피보다 작아도 실제로는 들어가지 않는 조합이 있습니다. 유효 내치수 30×30×30 박스에 25×25×20 상품 두 개는 부피로는 통과하지만 어떤 방향으로도 함께 들어가지 않습니다.
  - **박스 라인업의 비례 관계 부재:** 우체국 소포 규격을 준용한 박스 A~E호는 부피가 커진다고 모든 변이 커지지 않습니다. 2호는 1호보다 부피가 커도 한 변이 좁습니다. "최대 박스 하나만 검사"로는 초과 치수 상품을 걸러낼 수 없었습니다.
  - **편성과 적재의 분리:** 주문을 배송 단위로 먼저 나누고 각 단위의 박스를 고르면, 나누는 방식 자체가 박스 개수를 좌우하는데도 최적화 대상에서 빠집니다.

### 해결 과정

| **해결 방안** | **장점** | **단점 및 기각 사유** |
| :-: | :-: | :-: |
| 1. 부피 합산 비교 | 구현 단순, 계산 즉시 | 위 25×25×20 사례처럼 들어가지 않는 박스를 추천 — 작업자가 현장에서 재포장 |
| 2. 단일 상품 6방향 회전 검사(초안 규칙) | 낱개 통과 여부는 정확 | 여러 상품의 동시 적재를 판정하지 못함. 분할·완충재 규칙이 없어 다품목 주문 처리 불가 |
| 3. 배송 단위 선분할 후 박스 판정 | 단계가 명확 | 분할 방식이 고정돼 박스 개수를 줄일 기회를 놓침 |
| **4. extreme point 배치 + FFD 초기해 + 국소 탐색 (최종 채택)** | **판정이 곧 실제 배치라 무효 추천이 없음. 편성과 적재를 한 목적함수로 최적화** | **휴리스틱이라 "실제로는 들어가는데 못 찾는" 경우가 이론상 남음 — 단, 오류 방향은 박스가 한 단계 커지는 쪽** |

**핵심 설계 결정**

  - **목적함수 2단:** 1순위 박스 개수 최소, 동점이면 선택된 박스들의 총 부피 최소. 편성(나누기)과 적재(쌓기)를 Multiple Bin-Size 3D Bin Packing 한 문제로 풀었습니다.
  - **배치 엔진:** 박스 안에 놓인 블록들의 모서리가 만드는 후보점(extreme point)에 블록을 축 평행 6방향으로 놓아보며 실제 배치를 구성합니다. 유효 내치수는 각 변에서 마진 3cm를 뺀 값이고, 파손주의 상품은 각 변에 완충재 두께×2를 더한 블록으로 취급합니다.
  - **편성 최적화:** 주문 전체를 박스 1개에 부피 오름차순으로 통째 시도 → 실패 시 FFD(부피 내림차순, 수용 가능한 첫 배송 단위) → 단위 간 블록 이동으로 목적함수가 좋아지는 변경만 채택.
  - **적층불가 선분리·초과 치수 선검사:** 적층불가 SKU는 다른 SKU와 동거 금지. 시작 전 어떤 박스에도 안 들어가는 낱개는 전 박스를 검사해 `OVERSIZED_ITEM`으로 거부합니다.
  - **의도적 보류:** 같은 SKU를 격자로 합치는 슈퍼블록, 투입 순서를 바꿔 재시도하는 다양화는 구현하지 않았습니다. 단일 고정 순서가 실패하는 배치 가능 조합을 테스트로 만들지 못했고, 탐색 순서를 고정해야 같은 입력에 같은 결과가 나옵니다.

### 결론

계약은 상용 풀필먼트 API 4종(ShipBob, Shopify Fulfillment Orders, 카페24, 네이버 커머스)을 대조해 정했습니다. 검증은 2층으로 나눠 요청 결함은 배치 전체 400, 주문별 문제(미등록 지역·재고 부족·초과 치수)는 해당 주문만 거부 목록에 싣고 나머지는 저장합니다. 재전송 멱등은 ShipBob과 같이 주문번호 UNIQUE 제약으로 처리하고 별도 멱등 키는 두지 않았습니다.

배치 엔진·편성은 순수 로직으로 분리해 TDD로 작성했습니다. "부피 합은 통과하나 배치 불가", "부피 큰 박스가 치수로 탈락", "FFD 초기해를 국소 탐색이 개선", "같은 입력 반복 실행 시 같은 편성"을 포함한 단위 테스트 21개와 접수·검증·상태 전이 통합 테스트가 통과합니다. 라인 배정과 토트 할당까지 배치 전체를 단일 트랜잭션으로 묶어, 거부 주문 제외는 트랜잭션 안의 분기이지 부분 커밋이 아닙니다.

`[그림] 출고지시 배치 처리 흐름 — 접수·검증 → 블록화 → 배치 엔진 → 편성 최적화 → 라인·토트 → 저장`

## 문제 2. 치수 추론 서빙 — GPU 전제 8초 계약을 CPU 서버리스로

### 문제 배경

추론 API 계약은 GPU 개발 파드에서 서빙한다는 전제로 타임아웃 8초를 확정했습니다(CPU 실측 V3 5.87초 / V2 17.47초). AI팀은 학습 결과를 torch 형식(`model.safetensors`)으로 Hugging Face 비공개 저장소에 올리는 방식으로 작업했고, 시연 환경에 GPU는 없었습니다.

  - **트래픽 특성과 비용:** 입고 신규 상품 등록은 상시 트래픽이 아닙니다. 상시 서버를 띄우면 대부분의 시간 유휴 비용을 냅니다.
  - **콜드스타트가 계약 초과:** Lambda 첫 호출은 모델 로드까지 약 10초로 8초 계약을 넘겼습니다. 대응 없이는 시연의 첫 촬영이 실패 화면으로 보입니다.
  - **모델 교체 경로:** AI팀이 ONNX 변환을 직접 돌려 올리는 절차를 새로 만들면 모델 교체마다 사람 손을 탑니다.

### 해결 과정

**서빙 위치**

| **해결 방안** | **장점** | **단점 및 기각 사유** |
| :-: | :-: | :-: |
| 1. GPU 개발 파드 | 계약 산정 기준 그대로 | 시연 환경에서 접근·가용 보장 없음. 외부 의존이 요청 경로에 남음 |
| 2. EC2 상시 서버 + torch | 구조 단순, 콜드스타트 없음 | CPU torch 추론 1,070ms. 간헐 트래픽에 상시 비용. 백엔드와 같은 인스턴스에 동거 |
| **3. Lambda 컨테이너 + ONNX Runtime (최종 채택)** | **호출당 과금. ONNX로 추론 185ms, 모델 로드 0.22초** | **콜드스타트 관리 필요. zip 250MB 한도라 컨테이너 이미지(10GB) 필수** |

**콜드스타트 대응**

| **해결 방안** | **장점** | **단점 및 기각 사유** |
| :-: | :-: | :-: |
| 1. 타임아웃 상향(8→15초) | 첫 호출도 성공 | 시연 첫 촬영 10초 대기가 화면에 그대로 노출 |
| 2. 백엔드 주기 워밍 핑 | AWS 변경 없음 | 환경 교체 시 보장 안 됨. 백엔드 기동 직후 첫 호출은 콜드 |
| 3. Provisioned concurrency 상시 1 | 콜드스타트 제거 | 유휴 과금 월 약 $32(3,008MB 상시) — 간헐 등록에 낼 이유 없음 |
| **4. 시연 시간대만 Provisioned concurrency 예약 (최종 채택)** | **계약 8초 유지, 시연 시간 외 비용 0** | **버전 발행·별칭·Application Auto Scaling 예약 액션 관리 필요** |

**핵심 설계 결정**

  - **빌드 타임 ONNX 변환:** Dockerfile을 변환 스테이지와 런타임 스테이지로 나눴습니다. 변환 스테이지가 safetensors를 받아 ONNX로 바꾸고 torch 출력과 대조해 `max diff`가 1e-4를 넘으면 빌드를 실패시킵니다. 런타임 이미지에는 `model.onnx`와 `config.json`만 남고 torch·원본 가중치·토큰이 들어가지 않습니다. AI팀은 지금처럼 safetensors만 올리면 됩니다.
  - **호출 경로:** 공개 URL을 두지 않고 백엔드가 EC2 인스턴스 프로파일로 SDK Invoke합니다. 저장된 자격증명이 없습니다.
  - **추론 호출을 트랜잭션 밖으로:** 측정 저장을 별도 빈으로 분리해 콜드스타트 10초 동안 DB 커넥션을 잡지 않게 했습니다. 세션은 결과 상태로 한 번에 생성되므로 중간 상태가 생기지 않습니다.
  - **confidence 부재:** 모델이 신뢰도를 주지 않아(표본 부족으로 의도적 제외) 필드는 유지하되 null 허용, null이면 저신뢰 판정을 생략합니다. 근거 없는 대체값 생성은 기각했습니다.

### 결론

torch → ONNX 전환으로 같은 사진 3장 기준 추론 1,070ms → 185ms, 모델 로드 3.10초 → 0.22초, 예측값은 소수 1자리까지 동일(원시 출력 max diff 7.45e-08)했습니다. EC2 실서버 E2E에서 콜드 호출 4.9초, 웜 호출 0.3~0.5초로 8초 계약 안에 들어왔고, 시연 당일 시간대만 provisioned concurrency 1을 예약해 첫 촬영도 웜으로 처리했습니다.

배포는 GitHub Actions가 OIDC로 AWS 역할을 위임받아 ECR push → Lambda 코드 갱신 → `live` 별칭 이동까지 자동화했습니다. Hugging Face 토큰은 BuildKit secret mount로만 전달해 이미지 레이어와 `docker history`에 남지 않습니다.

`[그림] 추론 배포 파이프라인 — HF safetensors → 2단계 이미지 빌드(변환·검증) → ECR → Lambda live 별칭 → EC2 백엔드 SDK Invoke`
