## 요구사항과 범위 결정

풀필먼트 공정 중 입고와 출고 두 지점만 다뤘습니다. 입고 작업자는 신상품을 카메라 아래 올려 촬영하고, 화면에 표시된 치수를 확정한 뒤 수량을 입고합니다. 포장 작업자는 토트를 스캔해 배송 단위의 주문 내역과 추천 박스를 확인하고 포장을 완료합니다.

### 기능 요구사항

  - 촬영 사진 3장에서 가로·세로·높이(cm)를 추론하고, 작업자가 확정한 값만 상품 마스터에 저장합니다.
  - 출고지시를 배치로 받아 배송 단위 편성, 박스 추천, 라인 배정, 토트 할당을 한 트랜잭션으로 처리합니다.
  - 재고 차감은 포장 완료 시점 한 곳에서만 실행됩니다. 포장 완료 시 실측 무게를 받아 예상 무게와 대조합니다.

### 비기능 요구사항

  - 추론은 동기 응답이며 촬영 응답 p95 1초를 SLO로 둡니다. 초기 계약 8초는 GPU 서빙 전제였고, CPU 서빙으로 전환한 뒤 문제 2에서 재설정했습니다. 타임아웃(실패 판정)은 별도 값입니다.
  - 추론 모델 서버가 준비되기 전에도 입고 흐름 전체가 동작해야 합니다(미설정 시 mock 응답).
  - 배치 편성은 같은 입력에 대해 항상 같은 결과를 산출합니다(결정성).

**Vision AI 모델 성능.** 학습 데이터는 AI-Hub "물류공간 예측 데이터"(512px 리사이즈본)이며 학습·검증 물품은 7,676 / 958개로 겹치지 않습니다. 손실은 Huber에 비대칭 가중을 더한 형태로, 가로·세로 축에서 실제보다 작게 예측하는 오차에 1.6배 벌점을 줍니다. 작게 예측하면 들어가지 않는 박스를 추천하고, 크게 예측하면 박스가 한 단계 커지는 데 그치기 때문입니다. 검증셋 2,024품목을 서빙 코드로 평가한 축별 MAE는 length 2.06 / width 2.17 / height 1.62cm(이하 같은 순서)이고, 과정 시작 시 베이스라인은 2.69 / 3.74 / 4.99cm였습니다. 학습 당시 검증에서는 학습 배경 1.31 / 1.41 / 1.17cm, 학습에 쓰지 않은 배경 1.57 / 1.69 / 1.77cm로 배경이 바뀌어도 악화가 0.3~0.6cm에 그쳤습니다. 배경 합성 증강을 적용하고 매 실험마다 미학습 배경으로 검증한 결과입니다. 두 평가의 절대값 차이는 분할·촬영 슬롯 고정 여부가 달라서 생겼습니다. 문제 3은 이 불일치를 다룹니다. 모델은 신뢰도를 출력하지 않으며(표본 958개로는 구간별 확률표가 불안정), 촬영 구도가 학습 데이터와 다르면 성능을 보장할 수 없습니다.

**서빙.** torch 가중치를 빌드 시 ONNX로 변환해 같은 사진 3장 기준 추론 1,070ms를 185ms로, 모델 로드 3.10초를 0.22초로 줄였습니다(로컬 CPU 실측 2026-08-25, 예측값은 소수 1자리까지 동일). Hugging Face 토큰은 BuildKit secret mount로만 전달해 이미지 레이어에 남지 않습니다.

## 문제 1. 출고지시 배치 — 배치 기반 박스 추천과 무게 반영

### 문제 배경

출고지시 배치를 받으면 주문별로 어떤 박스 몇 개에 담을지 결정해야 했습니다. 원본 MVP 문서에는 "6방향 회전, 3cm 마진, 최소 박스" 초안 규칙만 있었습니다. 완충재·분할·적층불가 처리는 정의되지 않아 개발에 착수할 수 없었습니다.

  - **부피 합산의 무효 추천:** 상품 부피 합이 박스 부피보다 작아도 실제로는 들어가지 않는 조합이 있습니다. 유효 내치수 30×30×30 박스에 25×25×20 상품 두 개는 부피로는 통과하지만 어떤 방향으로도 함께 들어가지 않습니다.
  - **박스 라인업의 비례 관계 부재:** 우체국 소포 규격을 준용한 박스 A~F호는 부피가 커진다고 해서 세 변이 모두 커지지는 않습니다. 2호는 1호보다 부피가 커도 한 변이 더 짧습니다. "최대 박스 하나만 검사"하는 방식으로는 치수를 초과하는 상품을 판별할 수 없었습니다.
  - **편성과 적재의 분리:** 주문을 배송 단위로 먼저 나누고 각 단위의 박스를 고르는 순서입니다. 나누는 방식이 박스 개수를 결정하는데도, 그 방식 자체는 최적화 대상에서 빠집니다.
  - **무게 부재:** 초안 규칙에는 무게가 없었습니다. 택배 요금은 세 변의 합 구간과 무게 구간 중 높은 쪽으로 정해집니다. 무게를 계산에 넣지 않으면 요금이 한 구간 올라가는 편성이 최적해로 나옵니다. 결과 발표에서 CJ 현업 심사위원이 이 부분을 질문했습니다.

### 해결 과정

**1) 박스 판정과 편성**

| **해결 방안** | **장점** | **단점 및 기각 사유** |
| :-: | :-: | :-: |
| 1. 부피 합산 비교 | 구현 단순, 계산 즉시 | 위 25×25×20 사례처럼 들어가지 않는 박스를 추천. 작업자가 현장에서 재포장 |
| 2. 단일 상품 6방향 회전 검사(초안 규칙) | 낱개 통과 여부는 정확 | 여러 상품의 동시 적재를 판정하지 못함. 분할·완충재 규칙이 없어 다품목 주문 처리 불가 |
| 3. 배송 단위 선분할 후 박스 판정 | 단계가 명확 | 분할 방식이 고정돼 박스 개수를 줄이는 편성을 찾지 못함 |
| **4. extreme point 배치 + FFD 초기해 + 국소 탐색 (채택)** | **판정이 곧 실제 배치라 무효 추천이 없음. 편성과 적재를 한 목적함수로 최적화** | **휴리스틱이라 실제로는 적재 가능한 조합을 찾지 못하는 경우가 이론상 남음. 낱개 하나면 박스가 한 단계 커지는 방향이고, 여러 낱개면 후보가 사라져 과잉 거부로 이어질 수 있음** |

**2) 무게를 어디에 넣는가**

| **해결 방안** | **장점** | **단점 및 기각 사유** |
| :-: | :-: | :-: |
| 1. 박스마다 한도 1개(택배사 전체 상한) | 구현량이 적음 | 상한에 걸리는 경우가 거의 없음. 무게가 편성 결과를 바꾸지 못함 |
| 2. 박스 한도 = 세 변 합이 속한 요금 구간의 무게 상한 | 무게가 분할에 개입 | 요금 구간을 물리 한도로 오해한 모델. 무게 2.5kg인 C호 상자는 그대로 배송되는데도 분할함 |
| **3. 목적함수를 총 배송비로 교체 (채택)** | **요금 = 세 변 합 구간과 무게 구간 중 높은 쪽. 분할과 상위 구간 중 어느 쪽이 싼지를 계산이 판정. 현업 카토나이제이션의 목적함수와 같음** | **요금 구간표 기준정보 추가, 국소 탐색 목적함수 교체. 구현 범위가 가장 큼** |

**핵심 설계 결정**

  - **목적함수:** 1순위 총 배송비 최소, 동점이면 박스 개수, 그다음 총 부피. 편성(배송 단위 분할)과 적재(박스 내 배치)를 Multiple Bin-Size 3D Bin Packing 하나의 문제로 풀었습니다.
  - **배치 엔진:** 박스 안에 놓인 블록들의 모서리가 만드는 후보점(extreme point)마다 블록을 축 평행 6방향으로 시도해 실제 배치를 구성합니다. 유효 내치수는 각 변에서 마진 3cm를 뺀 값입니다. 파손주의 상품은 각 변에 완충재 두께×2를 더한 블록으로 취급합니다.
  - **편성 최적화:** 주문 전체를 박스 1개에 담는 통째 후보와, FFD(부피 내림차순) 초기해에 단위 간 이동과 새 단위 분리를 적용한 후보를 둘 다 만들어 목적함수로 고릅니다. 무게를 목적함수에 넣으면 한 박스에 담기는데도 나누는 편이 싼 경우가 생기므로, 국소 탐색은 배송 단위를 늘리는 이동도 후보에 포함합니다.
  - **요금 구간과 하드 제약:** 요금 구간표(세 변 합 80/100/120/140/160cm, 무게 2/5/10/15/20kg)는 기준정보 테이블로 두고 CJ대한통운 2024 표준운임을 시드 데이터로 넣었습니다. 세 변 합·최장변·총무게의 접수 한도를 넘는 단위는 편성 대상에서 제외하고, 낱개 하나가 한도를 넘으면 `OVERWEIGHT_ITEM`으로 거부합니다. 세 변 합 판정은 박스 외치수(내치수 + 판두께 × 2)로 합니다.
  - **출고 무게 검수:** 입고 단계에서 확정한 상품 무게(시연에서는 사전 등록값)로 배송 단위의 예상 총무게를 계산합니다. 포장 완료 시 실측 무게를 입력받아 허용 오차를 벗어나면 `WEIGHT_MISMATCH`로 차단합니다.
  - **의도적 보류:** 같은 SKU를 격자로 합치는 슈퍼블록, 투입 순서를 바꿔 재시도하는 다양화는 구현하지 않았습니다. 단일 고정 순서가 실패하는 배치 가능 조합을 테스트로 만들지 못했고, 아래 실측에서도 도입 근거를 확인하지 못했습니다.

### 결론

계약은 상용 풀필먼트 API 4종(ShipBob, Shopify Fulfillment Orders, 카페24, 네이버 커머스)을 대조해 정했습니다. 검증은 두 층으로 나눴습니다. 요청 결함은 배치 전체를 400으로 거부하고, 주문별 문제(미등록 지역·재고 부족·초과 치수·초과 무게)는 해당 주문만 거부 목록에 넣은 뒤 나머지는 저장합니다. 재전송 멱등은 ShipBob과 같이 주문번호 UNIQUE 제약으로 처리했습니다.

배치 엔진·편성은 순수 로직으로 분리해 TDD로 작성했습니다. 편성 단위 테스트 39개와 접수·검증·상태 전이 통합 테스트가 통과합니다. 단위 테스트에는 "부피 합은 통과하나 배치 불가", "부피 큰 박스가 치수로 탈락", "무게로 요금 구간이 올라가면 한 박스에 들어가도 나눠 담는다", "같은 입력 반복 실행 시 같은 편성" 케이스가 들어 있습니다.

**확장성 실측.** 시연 상품 11종에서 파생한 SKU 500종으로 주문(1~10줄, 평균 낱개 16.5개)을 합성해 편성 시간을 측정했습니다(단일 스레드, 순수 로직, Apple M2 Pro).

| 주문 수 | 총 시간 | 주문당 p50 | p95 | 최대 | 분할 주문 |
| :-: | :-: | :-: | :-: | :-: | :-: |
| 100 | 0.36초 | 1.8ms | 12.8ms | 16.9ms | 15.0% |
| 1,000 | 4.0초 | 2.4ms | 12.9ms | 31.2ms | 21.6% |
| 5,000 | 21.0초 | 2.3ms | 13.8ms | 96.6ms | 20.0% |

주문 수가 50배가 되어도 주문당 시간은 1.16배에 그치고 p50·p95는 변하지 않았습니다. 시간 상위 구간을 만드는 요인은 배송 단위 수가 아니라 낱개 수였습니다. 상위 10건 중 9건이 낱개 31개 이상이고, 그중 6건은 배송 단위 1개로 끝난 주문입니다. 한 박스에 담기는 주문에서도 국소 탐색이 낱개마다 새 단위 후보를 생성하기 때문입니다. 최대값 96.6ms의 주문은 낱개 25개·배송 단위 1개로 낱개 수만으로는 설명되지 않으며, 재실행 간 최대값이 54~97ms로 흔들려 꼬리 판단에는 반복 측정이 필요합니다. 배치 크기에 따른 초선형 증가가 없어 슈퍼블록과 시도 다양화는 보류를 유지했습니다.

**실측에서 확인한 결함.** 첫 벤치마크는 NPE로 중단됐습니다. 원인: 국소 탐색이 낱개를 옮길 때 받는 쪽만 수용 가능 여부를 검사하고, 낱개를 뺀 쪽은 검사 없이 적재 가능하다고 가정했습니다. 배치 판정이 휴리스틱이라 이 가정은 성립하지 않습니다. 낱개 17개는 F호에 담기는데 그중 하나를 빼면 16개가 어느 박스에도 담기지 않는다고 판정된 주문이 나왔고, 박스를 정하지 못한 편성이 후보로 남아 요금 계산에서 NPE가 발생했습니다. 접수 API로 들어온 요청이었다면 500 응답으로 이어졌을 경로입니다. 낱개를 뺀 쪽도 검사하도록 수정하고, 그 주문을 회귀 테스트로 고정했습니다.

**한계.** 상품별 내하중 데이터가 없어 적재 순서(무거운 상품을 아래에) 규칙은 두지 않았습니다. 요금표는 동일권역 표준운임 하나이고 권역별·계약 단가는 없습니다. 상품 무게가 비어 있으면 0kg으로 편성하고 출고 검수는 건너뜁니다.

`[그림 2] 출고지시 배치 처리 흐름 — 접수·검증 → 블록화 → 배치 엔진 → 편성 최적화(요금·박스 수·부피) → 라인·토트 → 저장`

## 문제 2. 촬영 응답 1초 — 저장 경로 병목의 측정과 제거

### 문제 배경

추론 계약의 타임아웃은 GPU 개발 파드 서빙을 전제로 8초였습니다(CPU 실측 V3 5.87초 / V2 17.47초). 간헐적인 입고 등록에 GPU를 상시 점유하는 비용을 피하려 CPU Lambda 컨테이너로 옮기고 런타임을 ONNX Runtime으로 교체했습니다. 추론 자체는 185ms(로컬)까지 내려왔지만 계약은 8초 그대로였습니다. 작업자가 촬영 버튼을 누르고 결과를 기다리는 시간 기준으로 8초는 기준값으로 쓸 수 없는 숫자였습니다.

  - **계약 재설정:** 응답 시간 한계는 Nielsen의 1초(사고 흐름이 끊기지 않는 한계)를 기준으로 삼았습니다. 상용 정적 치수 측정기(Cubiscan 100 1~2초, Mettler Toledo 3초 이내)와 같은 수준을 목표로 p95 ≤ 1초 SLO를 정했습니다. 타임아웃(실패 판정)은 별도 값입니다.
  - **구간별 측정값 부재:** 시연 기간 CloudWatch에 남은 Lambda 호출은 319건이고, 배포 검증일(8월 25일)을 뺀 웜 호출 246건은 p50 325ms / p95 609ms였습니다. 그러나 이 값은 Lambda 핸들러 안의 시간입니다. 백엔드가 사진을 읽고, 이벤트를 조립하고, 응답을 저장하는 구간은 측정한 적이 없었습니다. E2E 표본은 8월 26일 한 건(2.6초, 초기화 1.2초 포함)뿐이었고, 이 한 건만 놓고 보면 백엔드 경로가 0.9초로 계산됐습니다.

### 해결 과정

**1) 구간별 실측.** AWS 환경을 다시 구성하지 않고 Lambda 컨테이너 이미지를 로컬 Runtime Interface Emulator로 실행했습니다. 백엔드 SDK 클라이언트의 엔드포인트만 바꿔 같은 Invoke 경로(multipart → base64 → API Gateway 이벤트 → Mangum)를 그대로 재현했습니다. 백엔드에 구간 로그(사진 읽기 / 이벤트 조립 / Invoke 왕복 / 응답 파싱 / 저장)를 추가하고 사진 490KB·57KB 두 프로파일로 55회씩 측정했습니다.

| 구간 | p50 | p95 | 비고 |
| :-: | :-: | :-: | :-: |
| 사진 읽기 | 6~15ms | 26~40ms | 로컬 파일 |
| 이벤트 조립(base64 1.34배 팽창) | 12~21ms | 73~105ms | 페이로드 비례 |
| Invoke 왕복 − 핸들러 | 40~94ms | 240~248ms | 전송·에뮬레이터 |
| 응답 파싱 | 1~8ms | 26~33ms | |
| **저장(세션 커밋 + 사진 3장 동기 업로드)** | **32~81ms** | **144~227ms** | 백엔드 구간 중 최대 |

백엔드 경로 전체는 p50 90~220ms였습니다. 표본 1건에서 추정한 0.9초는 초기화와 첫 호출 비용이었습니다. 저장 구간은 백엔드 경로의 절반 이상을 차지했고, 운영 경로에서는 이 구간에 S3 put 3회가 트랜잭션 안에 포함돼 있었습니다.

**2) 단축 대상 선정.**

| **해결 방안** | **장점** | **단점 및 기각 사유** |
| :-: | :-: | :-: |
| 1. Lambda 메모리 상향(3,008 → 10,240MB) | 코드 변경 없이 vCPU 3배 | 계정 쿼터 상한이 3,008MB여서 증설 승인 대기. 핸들러 p95 611ms는 이미 1초 이내 |
| 2. 페이로드 축소(백엔드 리사이즈) | 조립·전송 비용 감소 | 실측 이득 조립 10ms·전송 20~80ms. 2순위 |
| 3. 저장을 트랜잭션 밖 동기 호출로 | 커넥션 점유 해소 | 응답 시간은 변하지 않음 |
| **4. 사진 업로드를 커밋 후 비동기로 (채택)** | **응답 경로에서 업로드가 빠짐. 세션은 사진 키만 저장하고 먼저 커밋** | **업로드 실패 처리·조회 시점 정합성을 따로 설계해야 함** |
| 5. 메시지 큐 + 업로드 워커 | 재시도·격리를 브로커가 담당 | 시연 규모에 인프라 추가. 대안으로만 기록 |

**핵심 설계 결정**

  - **커밋 후 이벤트:** 세션은 사진 키를 미리 정해 커밋하고, `AFTER_COMMIT` 이벤트 리스너가 전용 executor에서 3장을 업로드합니다. 응답은 업로드 완료를 기다리지 않습니다.
  - **실패 기록:** 재시도 3회 뒤에도 실패하면 WARN 로그와 함께 `upload_status = FAILED`로 기록합니다. 사진 조회(1-6)는 `STORED` 상태인 사진만 반환하고, 존재하지 않는 객체의 임시 주소는 발급하지 않습니다.
  - **로컬 저장소도 같은 경로:** 코드 경로를 하나로 두어 로컬 저장소와 S3의 동작이 달라지지 않게 했습니다.

### 결론

MinIO를 S3 대체로 두고 같은 조건(11상품 × 5회, 단일 스레드)으로 변경 전후를 비교했습니다.

| 지표 (사진 490KB) | 변경 전 p50 / p95 | 변경 후 p50 / p95 |
| :-: | :-: | :-: |
| 저장 구간 | 22 / 36ms | **7 / 12ms** |
| 백엔드 총 시간 | 185 / 243ms | 157 / 192ms |
| 클라이언트 E2E | 191 / 250ms | 162 / 198ms |
| 업로드(응답 밖) | — | 18 / 32ms |

저장 구간은 p95 기준 3분의 1로 줄었고, 줄어든 만큼 응답 경로의 시간이 감소했습니다. 이 수치는 로컬 MinIO 기준입니다. 실제 S3에서는 리전 왕복 시간이 업로드 구간에 더해지므로, 응답 경로에서 빠지는 시간은 더 커집니다. 운영 E2E는 CloudWatch 핸들러 p95 609ms에 백엔드 경로 p95 약 200ms를 더해 0.8초 안팎으로 추정되며, 1초 SLO 안에 들어옵니다.

**한계.** 로컬 측정은 같은 머신의 다른 컨테이너 부하로 핸들러 절대값이 실행마다 달라졌습니다(같은 조건 두 번 실행에서 p50 258ms와 597ms). 핸들러 시간은 CloudWatch 웜 호출 246건을 정본으로 사용했습니다. 동시 촬영은 에뮬레이터가 호출을 1건씩만 처리해 측정하지 못했습니다. 촬영 응답(1-3)의 사진 주소는 커밋 직후에 발급되므로, 업로드가 끝나기 전에 접근하면 객체가 없습니다. 시연 화면이 촬영 응답의 사진을 쓰지 않으므로 계약은 유지하고 한계로 기록했습니다.

`[그림 3] 촬영 1회의 응답 시간 분해 — 핸들러(CloudWatch) / 백엔드 구간(실측) / 변경 전후 저장 구간`

## 문제 3. 모델 교체 시 정확도 보증 — 배포 전 자동 평가 게이트

### 문제 배경

치수 추정 모델은 AI팀이 학습해 Hugging Face에 safetensors로 업로드하고, 배포 파이프라인이 ONNX로 변환해 Lambda에 배포합니다. 변환 단계에는 torch 출력과 ONNX 출력을 대조해 `max diff`가 1e-4를 넘으면 빌드를 중단하는 게이트가 있었습니다. 그러나 이 게이트는 변환의 정확성만 검사했고, 모델 자체의 정확도를 확인하는 단계는 없었습니다.

  - **학습 측과 서빙 측 수치 불일치:** 학습 리포트의 검증 MAE는 length 1.31cm였는데, 서빙 코드로 검증셋 2,024품목을 다시 평가하니 2.06cm였습니다. 평가 프로토콜(분할·촬영 슬롯 고정 여부)이 달라서 생긴 차이입니다. 학습 리포트의 수치를 배포 판정 근거로 쓸 수 없었습니다.
  - **정확도 계약 부재:** MVP 문서의 목표 MAE는 "미확정"으로 남아 있었지만, 참고할 업계 기준은 있었습니다. 상용 정적 치수 측정기는 0.5cm 단위(Mettler Toledo, MID ±5×5×2mm), 법정 계량은 OIML R129의 최대 허용 오차를 따릅니다. 이 모델(MAE 약 2cm)은 그 기준에 못 미치는 내부 측정 용도였고, 그 사실을 배포 기준에 명시할 필요가 있었습니다.
  - **속도를 위한 모델 변형 압력:** 응답 계약을 1초로 강화하면서 INT8 양자화처럼 더 빠른 변형을 배포할 동기가 생겼습니다. 변형이 정확도를 얼마나 떨어뜨리는지 자동으로 확인하지 못하면, 빠른 모델이 잘못된 치수를 내보내도 배포 전에 걸러지지 않습니다.

### 해결 과정

| **해결 방안** | **장점** | **단점 및 기각 사유** |
| :-: | :-: | :-: |
| 1. 학습 리포트 신뢰(현재) | 추가 작업 없음 | 학습 측 1.31cm와 서빙 측 2.06cm가 이미 어긋남. 프로토콜 차이를 걸러내지 못함 |
| 2. 배포 후 작업자 보정률로 사후 감지 | 현장 데이터 그대로 | 정확도가 떨어진 모델이 배포된 뒤에야 확인됨. 표본이 쌓일 때까지 며칠 소요 |
| **3. 배포 전 고정셋 자동 평가 + 임계 통과 시만 별칭 승격 (채택)** | **같은 프로토콜로 모든 후보를 비교. 서빙 코드로 평가하므로 학습-서빙 불일치가 발생하지 않음** | **평가 데이터(검증셋 2,024품목 × 3장)와 x86 평가 환경을 파이프라인이 확보해야 함** |
| 4. 카나리(별칭 가중치)·섀도우 호출 | 운영 트래픽으로 검증 | 입고 등록이 간헐적이라 표본이 느리게 쌓임. 3의 보완책으로만 |

**핵심 설계 결정**

  - **평가 프로토콜 고정:** 검증셋 2,024품목, 품목당 shot1 카메라 1·2·3, 정답은 데이터셋의 실측 CSV, 전처리는 서빙 코드(`dimension.py`)를 그대로 호출. 이 조건에서 현행 FP32가 8월 26일 평가값(2.06 / 2.17 / 1.62cm)을 그대로 재현하는지 먼저 확인했습니다.
  - **판정 기준 2단계:** 현행 대비 비열화(축별 MAE 악화 0.2cm 이하, 3축 ±3cm 정답률 하락 2%p 이하)와 절대 상한(축별 MAE 3cm 이하)입니다. 상용 0.5cm 기준은 달성 목표가 아니라 현재 한계를 표시하는 값으로 문서에 남깁니다.
  - **정적 양자화 보정 데이터는 학습셋에서:** 검증셋으로 보정하면 평가 결과가 오염되므로 학습셋 가공식품 100품목으로 보정했습니다.
  - **속도는 부차 지표:** 판정은 정확도로만 하고, 지연 시간은 표에 기록해 속도는 빨라지고 정확도는 낮아진 후보를 함께 확인합니다.

### 결론

x86(Xeon Sapphire Rapids, 2 vCPU, ONNX Runtime CPU) 환경에서 후보 전부를 같은 프로토콜로 평가했습니다.

| 변형 | 크기 | MAE L/W/H (cm) | 3축 ±3cm | p50 / p95 | 판정 |
| :-: | :-: | :-: | :-: | :-: | :-: |
| FP32 (현행) | 52.7MB | 2.06 / 2.17 / 1.62 | 62.5% | 243 / 250ms | 기준선 |
| FP16 | 26.4MB | 2.06 / 2.17 / 1.62 | 62.5% | 243 / 249ms | 통과(속도 이득 없음) |
| INT8 정적 PTQ (MinMax, 보정 100) | 14.8MB | 3.57 / 3.24 / 2.89 | 22.6% | 164 / 167ms | **차단** |
| INT8 정적 PTQ (첫 conv·헤드 FP32 유지) | 22.3MB | 3.71 / 3.42 / 2.66 | 20.5% | 167 / 171ms | **차단** |
| INT8 동적 (300품목) | 13.8MB | 11.45 / 8.22 / 7.72 | 6.7% | 1,828 / 1,871ms | **차단** |
| FP32 OpenVINO 실행기 (500품목) | 52.7MB | 현행과 동일 | 61.2% | 244 / 253ms | 통과(속도 이득 없음) |

게이트가 차단한 후보에서 판정 기준을 두 단계로 둔 효과가 확인됩니다. INT8 정적 양자화는 1.48배 빠르고 MAE 악화는 1.5cm에 그칩니다. 그러나 3축이 모두 ±3cm 안에 드는 비율은 62.5%에서 22.6%로 떨어졌습니다. 품목별로 보면 FP32와의 최대 축 차이가 중앙값 3.2cm, p95 7.5cm입니다. 오차가 한쪽으로 치우쳐 있어, 평균 MAE만 보는 기준이었다면 이 후보는 통과했을 것입니다. 첫 conv와 회귀 헤드를 FP32로 남기는 표준 처방도 결과를 개선하지 못했고, 백분위·엔트로피 보정은 4GB 평가 환경에서 메모리가 부족해 시도하지 못했습니다. EfficientNet 본체의 depthwise conv가 양자화에 민감한 구조라, 재학습(QAT) 없이는 이 모델의 INT8 변형을 배포할 수 없습니다.

FP16은 CPU에 fp16 연산기가 없어 속도 이득이 없고, OpenVINO 실행기는 최신 ONNX Runtime CPU 실행기와 같은 수준이었습니다. 재학습 없이 남는 속도 개선 수단은 vCPU 수(2→4스레드에서 1.6배, 로컬 실측)뿐이며, 이는 모델이 아니라 인프라 결정입니다.
