입고 작업자는 상품을 고정 카메라 3대로 촬영해 Vision AI가 추론한 치수를 확정하고 수량을 입고합니다. 출고 작업자는 토트를 스캔해 배송 단위의 주문 내역과 추천 박스를 확인하고 포장을 완료합니다. 재고 차감은 포장 완료 한 곳에서만 일어납니다.

`[그림 1] 시스템 아키텍처 — 프론트 / API 서버 / DB·S3 / 추론 Lambda / 모델 승격 파이프라인 / CI/CD / 모니터링·부하 도구`

### 왜 이런 아키텍처로 설계했는가

1. **추론은 CPU Lambda.** 입고 등록은 간헐적이라 GPU를 상시 점유하면 비용이 호출 수와 무관하게 나갑니다. 가중치를 빌드 시 ONNX로 변환해 CPU 추론 1,070ms를 185ms로 줄였고, 콜드스타트는 시연 시간대 Provisioned Concurrency 예약과 배포 뒤 워밍 호출로 막았습니다(카드 4).
2. **재고는 원장 하나가 진실.** 재고 숫자가 원장과 잔고 컬럼 두 곳에 있으면 동시 포장에서 데드락과 갱신 유실이 났습니다. 포장 완료는 원장에 행만 넣고, 잔고는 5초마다 집계한 스냅샷에 미집계 행을 더해 읽습니다(카드 1).
3. **사진 업로드는 커밋 뒤 비동기.** 촬영 응답에 S3 업로드 3회가 동기로 들어 있어 저장 구간이 백엔드 경로의 절반이었습니다. 응답은 사진 키만 커밋하고 업로드는 전용 executor가 맡습니다(카드 4).
4. **모델은 게이트를 통과한 것만 배포.** 학습 리포트의 정확도와 서빙 코드로 잰 정확도가 달랐습니다. 고정셋 2,024품목을 같은 프로토콜로 평가해 비열화 기준과 절대 상한을 통과한 후보만 `live` 별칭으로 승격합니다(카드 5).
5. **부하 테스트는 도구로 반복.** Prometheus·Grafana에 HikariCP·Tomcat·PostgreSQL 대기 이벤트를 모으고, k6 시나리오와 조건별 설정 교체·데이터 초기화·비교표 생성을 스크립트 하나로 묶었습니다. 실행 1~5와 풀 스윕 전부 이 도구로 돌렸습니다(테스트 진행).
6. **Redis는 두지 않았습니다.** 부하 테스트에서 DB가 병목인 적이 없고(작업자 50명 연타에 RDS CPU 20%대, 조회 p95 31~41ms), 재고는 정확성이 우선이라 캐시의 지연을 허용하지 않습니다. 서버 2대 이상에서 실시간 현황판을 붙일 때 다시 검토합니다.
7. **서버 1대, 2대 전환 체크리스트 보유.** 현장 피크(작업자 100명, 분당 1건)의 30배 부하에서도 1대로 처리량이 남습니다. 2대가 필요한 이유는 성능이 아니라 무중단 배포이며, 그때 바꿀 것(집계 스케줄러 ShedLock, 업로드 큐 Outbox, ALB)을 목록으로 두었습니다.

## Problem 1. 동시 포장 데드락과 재고 정합성 — 원장 기반 재고

**[문제배경]**
포장 작업자 50명이 동시에 포장 완료를 누르자 요청의 40.4%가 500으로 끝났습니다(10명일 때 12.1%, 품목 5개 배송단위는 82.6%). 포장 완료 트랜잭션이 상품 행을 `SELECT FOR UPDATE`로 잠그는데, 잠그는 순서가 배송단위마다 달라 순환 대기가 생겼습니다. 데드락에 걸린 트랜잭션이 커넥션 10개를 모두 붙들어 락과 무관한 토트 스캔·상세 조회까지 p95 5~6초로 밀렸습니다. 원인을 좇다 두 가지를 더 찾았습니다. 동시 포장 중 `stock_qty` 감소분이 원장 합의 절반이었고(JPA가 잠금 전 인스턴스를 돌려줘 행 락이 갱신 유실을 막지 못함), 재고 조정이 원장에만 기록돼 출고지시 149건 이후가 전부 거절됐습니다. 세 문제의 공통 원인은 재고 숫자가 원장과 잔고 컬럼 두 곳에 있고, 잔고 갱신이 트랜잭션 안의 행 락에 묶여 있다는 것이었습니다.

**[접근법]**

| 방안 | 장점 | 기각 사유 |
| :-: | :-: | :-: |
| 1. 상품 행 잠금 순서를 id 순으로 정렬 | 변경 작음 | 상품 행과 박스 행 사이 2자 순환은 남음. 갱신 유실·두 곳 재고는 그대로 |
| 2. 낙관적 락(버전 컬럼) 재시도 | 락 대기 없음 | 재시도가 부하를 키움. 두 곳 재고 문제 그대로 |
| **3. 원장 기반 재고 (채택)** | **포장 완료는 원장에 행만 넣고 상품 행을 잠그지 않음. 재고 진실이 한 곳** | **잔고 조회에 집계 구조가 필요. 집계 지연·정합성 검사를 따로 설계** |

**[사용이유]**
원장을 유일한 진실로 두고, 잔고는 5초마다 원장을 집계한 스냅샷에 아직 집계하지 않은 행을 더해 읽습니다. 집계가 늦어도 조회값은 정확합니다. 트랜잭션이 잡는 행 락은 박스 행 하나뿐이고, 60초마다 대조기가 스냅샷과 원장 전체 합을 비교해 어긋나면 다시 씁니다. 재고 조정은 멱등 키를 받는 API 한 곳으로 모았습니다.

**[결과]** 같은 부하(작업자 50명, 3분)에서

| 지표 | 전환 전 | 전환 후 |
| :-: | :-: | :-: |
| 포장 완료 실패율 | 40.4% | **0** |
| 완료 p95 | 10.07초 | **73ms** |
| 처리량 | 2.9건/s | **32.6건/s** |
| 데드락 | 356 | 0 |
| 스캔·상세 서버 p95 | 6.3 / 5.1초 | 41 / 31ms |

`[캡처] grafana-packing-after.png — 전환 후 3분: pending 0, 완료 p95 73ms`

**전환 뒤 검토와 실험에서 잡은 결함 3건.** 머지 전 코드 검토에서 집계 커서가 늦게 커밋된 원장 행을 건너뛰는 결함(id 순서와 커밋 순서 불일치)을 찾아 정착 윈도우 60초로 고쳤습니다. 계획서의 CTE 집계 SQL은 동시 실행 시 이중 반영돼 상관 서브쿼리로 바꿨습니다. 풀 실험 중 4시간 동안 처리량이 113건/s에서 66건/s로 떨어진 원인을 좇아, 5초마다 도는 잔고 집계 쿼리가 새 커서를 찾을 때 원장 전체를 훑는 것을 찾았습니다. `FILTER` 집계로 고쳐 원장 105만 행에서 3,393ms를 0.66ms로, 무부하 RDS CPU 26~30%를 5~7%로 되돌렸습니다.

## Problem 2. 커넥션 풀 크기와 획득 타임아웃을 부하 실험으로 정하기

**[문제배경]**
커넥션 풀 설정이 Spring Boot 기본값(`maximumPoolSize` 10, `connectionTimeout` 30초)이었습니다. 풀 10이 이 창고 규모에 맞는지 잰 적이 없고, 30초 상한은 작업자 화면이 10초에 포기한 요청을 서버가 20초 더 붙들게 둡니다. v3에서 락 대기 트랜잭션이 커넥션을 붙들자 락과 무관한 요청까지 획득 대기 최대 10.5초를 겪은 것이 그 구조입니다.

**[접근법]**
Oracle Real World Performance Group의 커넥션 풀 실험 방식을 따랐습니다. 부하를 고정하고 풀 크기만 바꾸며 처리량·커넥션 획득 시간·점유 시간·DB 대기 이벤트를 같은 표에 놓습니다.

1. **트래픽 산정.** 수작업 포장 스테이션 시간당 30~60건(업계 수치)을 상한으로 작업자 100명이 분당 1건, 요청당 커넥션 점유 22ms → Little's law로 평균 동시 커넥션 0.1개. 피크 3배와 배치·스케줄러를 더해도 6개면 충분하다는 계산.
2. **판정 규칙을 실험 전에 문서로 고정.** 최고 처리량의 98%를 내는 최소 풀, 획득 대기가 사라지는 최소 풀, DB 락·I/O 대기 비중이 5%p 넘게 늘기 시작하는 풀, 처리량 없이 p95가 20% 넘게 나빠지는 풀.
3. **세 가지 부하.** 피크 1·3배(작업자 100·300명 분당 1건), 포화(100명 연타), 락 주입(박스 재고 행 20초 잠금 후 타임아웃 30·3·1초).

**[사용이유]**
설정값은 공식(HikariCP 위키 `core×2 + spindle` = 4)이 아니라 이 시스템의 실측으로 정해야 했습니다. 트랜잭션을 연 세션 9.5개 중 7.0개가 `idle in transaction`(Spring 서버가 다음 SQL을 보내기를 기다리는 상태)이라, 커넥션이 DB CPU를 쓰지 않고 쥐어진 시간이 길어 공식보다 큰 풀이 맞았습니다.

**[결과]**

| 부하 | 결과 |
| :-: | :-: |
| 피크 1·3배 | 풀 5~40 처리량 동일, 대기 없음. 산정과 일치 |
| 포화 | 풀 5→10→20에서 78→125→137건/s. 30·40은 처리량 그대로, p95만 571ms→1.3초(박스 행 락 대기열) |
| 락 주입 | 30초: 락 무관 스캔 절반이 6~7초, 일부 10초 실패, Tomcat 스레드 200 포화. 3초: 3초에 500, 화면 멈춤 없음 |
| 결정 | 풀 10, `connectionTimeout` 3초. 포화 ABBA 재검증 실패 0, 처리량 차이 1% |

`[캡처] docs/evidence/pool-sizing/timeout/peak3x-p10-t30000-th200-r1/grafana.png — 타임아웃 30초, 락 20초 주입: pending 174, Tomcat busy 184, 획득 max 18초`

**실험이 가르쳐 준 것.** 사전 예측 하나("풀 5 이상이면 획득 p95 1ms 미만")는 틀렸고, 원인을 좇아 HikariCP의 500ms 이상 쉰 커넥션 생존 확인 왕복임을 확인했습니다. 4시간 동안 같은 조건 처리량이 절반으로 떨어져 "풀 30 붕괴"로 읽힐 뻔했으나, 조건마다 원장을 되돌리자 사라졌습니다. 원인은 RDS 크레딧이 아니라(잔고 0에서도 처리량 평탄) 원장 크기였고, 그 쿼리를 카드 1에서 고쳤습니다. 수집 도구가 같은 초 표본을 두 번 세어 세션 수를 부풀린 버그도 잡았습니다(커넥션 40개에 세션 49는 불가능한 값).

상세: 블로그 초안 G, `docs/evidence/pool-sizing/README.md`, 도구 `tools/loadtest/pool-sweep.sh`

## Problem 3. 박스 추천 — 부피 근사에서 실제 적재로, 무게를 목적함수에

**[문제배경]**
MVP 초안 규칙은 "6방향 회전, 3cm 마진, 최소 박스"뿐이었습니다. 부피 합으로 판정하면 유효 내치수 30×30×30 박스에 25×25×20 상품 두 개가 통과하지만 어떤 방향으로도 함께 들어가지 않습니다. 박스 A~F호는 부피가 커져도 세 변이 모두 커지지 않아 "최대 박스 하나만 검사"로는 초과 치수를 못 잡습니다. 무게는 계산에 없었고, 결과 발표에서 CJ 현업 심사위원이 이 부분을 질문했습니다. 택배 요금은 세 변 합 구간과 무게 구간 중 높은 쪽으로 정해지므로, 무게 없이는 요금이 한 구간 올라가는 편성이 최적해로 나옵니다.

**[접근법]**

| 방안 | 기각 사유 |
| :-: | :-: |
| 부피 합산 비교 | 들어가지 않는 박스를 추천. 현장에서 재포장 |
| 단일 상품 6방향 회전(초안) | 여러 상품 동시 적재를 판정 못 함 |
| 배송 단위 선분할 후 박스 판정 | 분할 방식이 고정돼 박스 수를 줄이는 편성을 못 찾음 |
| **extreme point 적재 + FFD 초기해 + 국소 탐색 (채택)** | 판정이 곧 실제 배치. 편성과 적재를 한 목적함수로 |

무게는 박스 한도 1개(효과 없음), 요금 구간을 물리 한도로 쓰기(2.5kg C호를 분할하는 오해)를 기각하고 **목적함수를 총 배송비로 교체**했습니다. 1순위 총 요금, 동점이면 박스 수, 그다음 부피. 무게 때문에 한 박스에 담기는데도 나누는 편이 싼 경우가 있어 국소 탐색은 배송 단위를 늘리는 이동도 후보에 넣습니다. 요금 구간표는 CJ대한통운 2024 표준운임을 시드로 넣었습니다.

**[사용이유]**
현업 카토나이제이션의 목적함수와 같습니다. 낱개 하나가 접수 한도(20kg)를 넘으면 `OVERWEIGHT_ITEM`으로 거부하고, 포장 완료 때 실측 무게가 예상과 어긋나면 `WEIGHT_MISMATCH`로 차단해 무게 오류가 출고까지 가지 않게 했습니다.

**[결과]**
편성 단위 테스트 21개에서 39개("부피 합은 통과하나 배치 불가", "무게로 요금 구간이 오르면 나눠 담는다" 포함). 합성 주문 벤치마크(SKU 500종, 단일 스레드):

| 주문 수 | 총 시간 | 주문당 p50 / p95 |
| :-: | :-: | :-: |
| 100 | 0.36초 | 1.8 / 12.8ms |
| 5,000 | 21.0초 | 2.3 / 13.8ms |

주문 50배에 주문당 시간 1.16배. 첫 벤치마크는 NPE로 멈췄습니다. 국소 탐색이 낱개를 옮길 때 받는 쪽만 검사하고 뺀 쪽은 검사하지 않아, 17개는 F호에 담기는데 16개는 어디에도 못 담긴다고 판정되는 주문이 나왔습니다. 접수 API였다면 500이었을 경로를 고치고 그 주문을 회귀 테스트로 고정했습니다.

## Problem 4. 촬영 응답 1초 — CPU 서빙 전환과 저장 경로 병목 제거

**[문제배경]**
추론 계약의 타임아웃은 GPU 개발 파드 전제로 8초였습니다. 간헐적 입고 등록에 GPU를 상시 점유하는 비용을 피해 CPU Lambda 컨테이너로 옮기자 두 문제가 생겼습니다. 콜드스타트 초기화가 최대 9.5초로 계약을 넘겼고, 8초는 작업자가 버튼을 누르고 기다리는 기준으로 쓸 수 없는 숫자였습니다. 응답 시간 목표를 Nielsen 1초 한계와 상용 치수 측정기(1~3초) 기준으로 p95 1초 SLO로 다시 정했습니다. 그런데 백엔드가 사진을 읽고 추론을 부르고 저장하는 구간은 잰 적이 없었습니다.

**[접근법]**
1. **런타임 전환.** 가중치를 빌드 시 ONNX로 변환하고 torch 출력과 대조(max diff 1e-4)하는 게이트를 둡니다.
2. **콜드스타트.** 시연 시간대만 Provisioned Concurrency 예약, 리셋과 배포 뒤 워밍 호출.
3. **구간 실측.** Lambda 이미지를 로컬 에뮬레이터로 띄워 같은 Invoke 경로로 5구간(사진 읽기 / 이벤트 조립 / Invoke / 파싱 / 저장)을 55회씩 측정. 저장 구간(세션 커밋 + S3 put 3회 동기)이 p95 144~227ms로 백엔드 경로의 절반.
4. **저장 경로.** Lambda 메모리 상향(쿼터 3,008MB 상한), 페이로드 축소(이득 10~80ms), 메시지 큐(시연 규모에 과함)를 기각하고 **사진 업로드를 커밋 뒤 비동기**로. 세션은 사진 키만 커밋하고 `AFTER_COMMIT` 리스너가 전용 executor에서 올립니다. 3회 재시도 후 실패는 `upload_status = FAILED`.

**[사용이유]**
응답 경로에서 업로드가 빠지면서 커넥션 점유도 함께 사라집니다. 추론 호출 자체도 트랜잭션 밖으로 빼서 콜드 호출 동안 커넥션을 쥐지 않게 했습니다.

**[결과]**

| 지표 | 전 | 후 |
| :-: | :-: | :-: |
| CPU 추론(사진 3장) | 1,070ms | **185ms** |
| 모델 로드 | 3.10초 | 0.22초 |
| 저장 구간 p95(MinIO) | 36ms | **12ms** |
| 백엔드 total p95 | 243ms | 192ms |
| 운영 클라이언트 E2E p95(실제 3뷰) | — | **611ms** |
| 시연 기간 Lambda 웜 246건 | — | p50 325 / p95 609ms, 8초 초과 0 |

**비동기화가 숨긴 실패.** v1 부하 테스트에서 작업자 100명까지 응답 p95 0.54초·실패 0이었지만 사진 1,155장이 PENDING으로 남았습니다. 업로드 큐(2,000)가 차면 거절이 로그 한 줄로 끝나고 재처리 경로가 없기 때문입니다. 프로세스 재시작 때도 큐가 사라집니다. 이 재처리 경로(Outbox)는 남은 과제입니다.

## Problem 5. 모델 교체 시 정확도 보증 — 배포 전 자동 평가 게이트

**[문제배경]**
학습 리포트의 MAE는 length 1.31cm, 서빙 코드로 검증셋을 다시 재니 2.06cm였습니다. 분할과 촬영 슬롯 고정 여부가 달라서 생긴 차이인데, 이 상태로는 모델을 교체할 때 좋아졌는지 나빠졌는지 판정할 기준이 없습니다. 속도를 위해 양자화 후보를 시험하려면 더욱 필요했습니다.

**[접근법]**
검증셋 2,024품목 고정셋을 비공개 S3에 두고, 서빙 이미지에서 꺼낸 모델을 같은 프로토콜로 평가합니다. 판정은 두 단계입니다. 직전 기준선 대비 비열화(MAE +0.2cm, ±3cm 정답률 −2%p 이내)와 절대 상한(MAE 3cm, 박스 추천 마진에서 가져온 잠정값). 통과한 후보만 `live` 별칭으로 승격하고 기준선을 갱신합니다.

**[사용이유]**
평균 MAE 하나로는 오차가 한쪽으로 치우친 후보를 못 잡습니다. 3축이 모두 ±3cm 안에 드는 비율을 함께 보게 했습니다.

**[결과]**

| 후보 | MAE L/W/H | 3축 ±3cm | 속도 | 판정 |
| :-: | :-: | :-: | :-: | :-: |
| FP32(현행) | 2.06 / 2.17 / 1.62 | 62.5% | 243ms | 기준선 |
| FP16 | 동일 | 62.5% | 243ms | 통과, 이득 없음 |
| INT8 정적 PTQ | 3.57 / 3.24 / 2.89 | **22.6%** | 164ms | **차단** |
| INT8 동적 | 11.45 / 8.22 / 7.72 | 6.7% | 1,828ms | 차단 |

INT8 정적 양자화는 1.48배 빠르고 MAE 악화는 1.5cm뿐이라 평균만 봤다면 통과했을 후보입니다. 3축 정답률이 62.5%에서 22.6%로 떨어져 게이트가 막았습니다. 재학습 없이 통과하는 속도 후보는 없었고, 남는 속도 레버는 vCPU 수라는 결론을 얻었습니다. 파이프라인 첫 실행(2026-09-16)은 8월 평가와 같은 값으로 통과해 live 버전 5로 승격됐습니다.

## 더 개선할 부분이 있다면

1. **배치 접수의 토트 배정.** 배송단위마다 유휴 토트 전체를 적재해 주문당 53ms(5,000주문 272초)이고, 동시 배치가 같은 토트를 골라 전체 롤백됩니다. `LIMIT 1 FOR UPDATE SKIP LOCKED`와 500주문 청크 커밋으로 바꿉니다. 사전 배정은 피킹 지시의 LPN 배정을 모사한 것이며, 실제 현장은 피커가 빈 토트를 스캔하는 시점에 묶습니다.
2. **업로드 큐 유실.** 큐 거절과 프로세스 재시작으로 PENDING이 남습니다. Outbox 테이블과 재처리 스케줄러, 큐 깊이 알람.
3. **박스 재고 행 락이 포화 처리량 상한.** 풀 20 이후 처리량이 오르지 않고 락 대기열만 늡니다. 락을 쥔 채 세는 라인별 건수 조회를 트랜잭션 밖으로 빼고, `lock_timeout`을 실험합니다.
4. **정착 60초 가정의 강제.** 원장 쓰기 트랜잭션이 60초 안에 끝난다는 가정을 `transaction_timeout`으로 강제하되, 앱 롤 전체에 걸면 272초 배치가 끊기므로 원장 쓰기 트랜잭션에만 적용하는 방법이 필요합니다.
5. **서버 2대 전환.** 집계 스케줄러 ShedLock, 게이지 계산 방식, ALB·롤링 배포. 필요한 이유는 성능이 아니라 무중단 배포입니다.
6. **타임아웃 3초의 여유 4ms.** 작업자 100명 포화에서 최장 획득 대기 2.996초. 작업자가 더 늘면 타임아웃이 날 수 있어, 3번을 해결한 뒤 다시 잽니다.
7. **실측하지 못한 것.** 수정 전 빌드에서 집계 커서 누락의 실제 빈도, 동시 작업자 100명 가정의 실제 값.
