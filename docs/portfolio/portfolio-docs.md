## 시스템 아키텍처

![그림 1. 시스템 아키텍처](images/01-architecture.png)

| 영역 | 구성 | 역할 |
| --- | --- | --- |
| 프론트엔드 | Next.js | 입고 촬영·치수 확정, 출고 포장, 대시보드 |
| API 서버 | Spring Boot, EC2 1대 | 입고·출고·주문·재고 처리, 박스 편성 |
| 저장소 | PostgreSQL(RDS), S3 | 업무 데이터, 촬영 사진 |
| 치수 추론 | AWS Lambda 컨테이너, ONNX Runtime | 사진 3장 → 가로·세로·높이 |
| 모델 파이프라인 | GitHub Actions | 모델 변환 → 고정셋 정확도 검증 → 통과 시 Lambda 배포 |
| 관측·부하 | Prometheus, Grafana, k6 | 지표 수집, 부하 발생 |

**아키텍처 설계 이유**

1. 치수 추론은 Lambda(CPU). 입고 시각이 불규칙해 GPU 상시 가동(월 약 380달러)은 유휴 비용이 크고, ONNX 변환으로 CPU 추론이 185ms라 Lambda로 충분했습니다. 콜드스타트(최대 9.5초)는 시연 시간대만 실행 환경 1개를 미리 띄워 막았습니다.
2. 재고는 수량을 갱신하지 않고 변동을 원장에 쌓습니다. 동시 포장에서 상품 락 데드락과 갱신 손실을 없애기 위한 결정입니다(개선 1).
3. 촬영 사진 업로드는 추론과 병렬로 돌리고 둘 다 끝나야 응답합니다. 응답이 곧 "사진 저장 완료"가 되어 유실이 없습니다(개선 3).
4. 모델은 고정 검증셋 정확도 게이트를 통과한 것만 배포합니다. 속도만 보고 정확도가 떨어진 모델이 나가는 일을 막습니다(문제 4).
5. API 서버는 1대. 가정한 포장 피크(300명)를 1대가 대기 없이 처리해 이중화는 무중단 배포가 필요해질 때로 미뤘습니다.

# 부하 테스트 및 개선 1 · 동시 포장 시 재고 갱신 데드락

**테스트 목적** — 창고 규모의 동시 작업에서 어디서 먼저 병목이 생기는지 찾기 위해 수행했습니다. 시연은 작업자 1명이었습니다.

**테스트 도구·환경** — k6 + Prometheus/Grafana. API 서버 EC2 2 vCPU, RDS 2 vCPU·1GB. 시나리오는 작업자 행동 단위(토트 스캔 → 주문 확인 → 포장 완료, 1건 뒤 1초 대기). 현장 속도(작업자당 분당 1~2건)의 20~55배 부하입니다.

**문제 배경**

포장 작업자 50명 동시 부하에서 포장 완료 요청의 **40.4%가 실패**했습니다(10명에서 12.1%). 포장 완료는 박스에 담긴 상품마다 락을 잡고 수량을 1씩 줄이는데, 박스마다 잠그는 순서가 달라 데드락이 났습니다. 같은 테스트에서 재고 감소분이 포장 건수의 절반만 반영되는 갱신 손실도 확인했습니다. 락은 잡았지만 갱신에 쓴 값이 락 이전에 읽어 둔 값이었습니다.

![개선 전 — 50명: 응답 p95 10초, 실패율 40%, 커넥션 대기 39](images/02-packing-before.png)

**해결 과정**

| 해결 방안 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| 원자적 갱신 + 락 순서 통일 | 단일 UPDATE로 갱신하고 상품 ID 순으로 잠금 | 데드락·갱신 손실 제거 | 상품 수만큼 락 유지, 변동 이력 없음 |
| 낙관적 락 | 버전 비교로 충돌 감지 후 재시도 | 락 없음 | 동시 요청이 많을수록 재시도 증가, 이력 없음 |
| **재고 원장(append-only ledger)** | 수량을 고치지 않고 "−1" 변동 행을 추가. 현재 수량은 5초 주기 스냅샷 + 미집계 행 합산 | 상품 락 자체가 없음. 모든 변동이 한 곳에 남아 불일치 추적 가능 | 집계 구조 필요, 원장 보관 정책 필요 |

**핵심 설계 결정**

- **수량 갱신 → 원장 추가**: 락을 잡을 대상이 사라져 데드락과 갱신 손실이 구조적으로 불가능해집니다.
- **집계 60초 지연 + 60초마다 전체 대조**: 원장 ID 순서와 커밋 순서가 어긋나 건너뛴 행은 대조 단계가 잡습니다. 그 사이 조회값이 틀릴 수 있는 창은 최대 60초입니다.
- **재고 부족 판정은 접수 단계에서만**: 포장대에 온 상품은 이미 꺼낸 실물이라 포장 완료에서는 판정하지 않습니다. 박스 자재 락만 남겼습니다.

**부하테스트 결과** (작업자 50명, 3분)

| 지표 | 전환 전 | 전환 후 |
| --- | --- | --- |
| 에러율 | **40.4%** | **0%** |
| 포장 완료 p95 | **10.07초**(프론트 타임아웃) | **73ms** |
| 처리량(포장 완료/초) | 2.9 | 32.6(넣은 부하를 대기 없이 처리) |
| 데드락 | 356건 | 0건 |
| 원장 합계 vs 포장 건수 | 절반만 반영 | 일치 |

![개선 후 — 50명: 응답 p95 73ms, 실패 0, 커넥션 대기 0](images/03-packing-after.png)

**결론**

같은 부하에서 에러율 **40.4% → 0%**, p95 **10.07초 → 73ms**, 처리량 **11배**. 재고 변동이 원장 한 곳에 남아 관리자 조정이 수량에 반영되지 않던 이중 기록 문제도 함께 사라졌습니다. 이후 실험에서 원장이 105만 행까지 쌓이자 집계 쿼리가 상품마다 원장을 풀 스캔해 처리량이 절반으로 떨어졌고, 인덱스 범위 스캔으로 고쳐 **3.39초 → 0.66ms**로 줄였습니다.

# 부하 테스트 및 개선 2 · 커넥션 풀 크기와 타임아웃을 실측으로 결정

**문제 배경**

개선 1 이전 테스트에서 락 대기 요청이 커넥션을 점유하자 락과 무관한 조회까지 최대 **10.5초**를 기다렸습니다. 커넥션 풀은 기본값(풀 10, 타임아웃 30초)이었고, 이 규모에 맞는지 잰 적이 없었습니다. 타임아웃 30초는 프론트엔드 타임아웃(10초)이 지난 요청도 서버에서 20초 더 기다리게 합니다.

**해결 과정**

| 해결 방안 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| HikariCP 권장 공식 | 코어 × 2 + 스핀들 = 4 | 계산 간단 | 커넥션 점유 = DB 실행 시간이라는 전제가 이 시스템과 다름 |
| 리틀의 법칙 | 요청률 × 점유 시간 = 평균 동시 커넥션 0.11개 → 6 | 부하 기반 | 평균이라 포화·락 대기를 반영 못 함 |
| **부하 고정 후 풀 크기·타임아웃만 바꿔 실측** | 판정 규칙·예측을 실험 전에 기록. 현장 부하(100·300명)·포화·락 주입 3종 | 실제 병목 위치 확인 | 조건당 3분 × 20회 이상 실행 |

실험 도구는 직접 만든 스윕 스크립트와 실시간 콘솔입니다. 조건마다 원장을 되돌리고 k6 → Prometheus → 판정을 자동으로 돌립니다.

![풀 스윕 실시간 콘솔 — 조건별 TPS·커넥션 획득 시간·DB 대기 이벤트](images/04-pool-sweep-console.png)

**부하테스트 결과**

| 부하 | 결과 |
| --- | --- |
| 현장 부하 100·300명 | 풀 5~40개 모두 처리량 같음, 커넥션 대기 없음. 타임아웃 1초·3초 모두 0건 |
| 포화(100명, 대기 0) | 풀 5·10·20에서 78·125·137 TPS, p95 577·445·571ms. 풀 30·40은 처리량 그대로, p95만 882ms·1.3초. DB 락 대기 비중 8→19→47% |
| 락 20초 주입 + 타임아웃 30초 | 락과 무관한 조회 절반이 6~7초, 일부 10초 타임아웃, Tomcat 스레드 200개 소진 |
| 락 20초 주입 + 타임아웃 3초 | 3초에 에러 응답, 화면 멈춤 없음 |
| 점유 시간 분해(포화, 풀 10) | DB 실행 26%, 트랜잭션 안 애플리케이션 구간 74% → 권장 공식이 맞지 않는 이유 |

![타임아웃 30초에서 락 20초 주입 — 커넥션 대기 174, 무관한 요청까지 20초 정체](images/05-lock-injection-timeout30s.png)

**결론**

풀은 **10 유지**, 타임아웃은 **30초 → 3초**. 풀 20은 포화 처리량이 10% 높지만 DB 락 대기 비중이 47%로 커지고 p95도 길어 10을 택했습니다. 포화 처리량의 상한은 박스 자재 락이라 풀을 늘려도 대기열만 길어집니다. 3초는 포화 재검증에서 커넥션 대기 최대 2.6초를 넘는 값으로 정했고, 재검증 처리량은 기본값과 1% 차이였습니다. 획득 시간 예측(1ms 미만)은 실측 1.6ms로 빗나갔는데, 원인은 유휴 커넥션 유효성 검사 왕복이었고 안정성을 위해 그대로 두었습니다.

# 부하 테스트 및 개선 3 · 촬영 사진 업로드 유실

**문제 배경**

촬영 API에 입고 작업자를 1→100명으로 올리자 응답은 전부 정상인데 **1,155장**이 S3에 올라가지 않았습니다. 사진 업로드를 커밋 뒤 비동기로 넘겼는데, 45명부터 업로드 큐(2,000)가 차면서 작업이 에러 없이 버려졌습니다. 작업자 화면은 성공인데 사진은 영구히 없는 상태였습니다.

**해결 과정**

| 해결 방안 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| 유실분 재업로드 스케줄러 | 미업로드 행을 주기적으로 다시 올림 | 구현 단순 | 응답 시점에 사진이 없는 상태는 그대로 |
| 클라이언트 presigned URL 직접 업로드 | 프론트가 S3에 직접 올림 | 서버 부하 없음 | 추론용 사진을 서버가 따로 받아야 해 경로가 둘, 프론트 변경 |
| 메시지 큐 + 워커 | 업로드를 브로커로 분리 | 유실 방지 | 브로커 운영 추가 |
| **추론·업로드 병렬 실행 후 응답** | 사진 3장 업로드(37ms)를 추론 호출(320ms) 안에 끝내고 둘 다 성공해야 응답 | 응답 = 저장 완료, 추가 인프라 없음 | 업로드 실패가 곧 응답 실패(작업자 재촬영) |

**핵심 설계 결정**

- **응답 조건에 업로드 포함**: 유실을 "나중에 복구"하지 않고 애초에 생기지 않게 했습니다.
- **스레드 풀 포화 시 거절 대신 요청 스레드가 직접 업로드**: 큐가 차도 사진은 빠지지 않고 응답만 느려집니다. 8초를 넘으면 에러로 끝냅니다.
- **S3 SDK 타임아웃 상한(시도 2초·호출 6초)**: 재현되지 않은 9.9초 업로드 지연 1건에 대비해 지연 상한을 두었습니다.

**부하테스트 결과** (작업자 60명, 3분, 시연 환경)

| 지표 | 커밋 뒤 비동기 업로드 | 병렬 업로드 후 응답 |
| --- | --- | --- |
| S3 미업로드 사진 | 부하 중 최대 **5,700장**, 종료 후 **27장** 잔존 | **0장** |
| 촬영 응답 p95 | 540ms | 540ms(업로드 스레드 6개) |
| 단일 요청 p95 | 467ms | 482ms |

![60명 3분 — 왼쪽(비동기): 미업로드 사진 누적 5,700장 / 오른쪽(병렬 후 응답): 0장](images/06-upload-A-vs-C6-dashboard.png)

![종료 120초 뒤 DB 확인 — 비동기 27장 PENDING 잔존, 병렬 후 응답 0장](images/07-upload-pending-psql.png)

**결론**

유실 **1,155장 → 0장**, 응답 p95는 **540ms로 동일**. 업로드 스레드 3개에서는 p95가 946ms까지 올랐는데, 큐가 차기 전에는 스레드를 늘리지 않는 풀 동작 때문이라 기본 스레드를 6개로 올렸습니다.

# 문제 4 · 치수 추론 서빙을 GPU 서버에서 Lambda로, 정확도 게이트로 배포

**문제 배경**

팀 초기 설계는 GPU 서버 상시 가동이었습니다. 시연처럼 시간이 정해져 있으면 그 시간만 켜면 되지만 운영 입고는 시각이 불규칙해 유휴 비용을 계속 냅니다. 또 모델을 바꿀 때 나아졌는지 판정할 기준이 없었고, 학습 리포트의 MAE(가로 1.31cm)와 서비스 코드로 잰 값(2.06cm)이 달랐습니다.

**해결 과정**

| 해결 방안 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| GPU 인스턴스 상시 가동 | g4dn.xlarge 24시간 | 추론 최단 | 월 약 380달러, 유휴 비용 |
| API 서버 안에서 CPU 추론 | Spring 서버에 모델 탑재 | 인프라 단순 | 2 vCPU에서 포장 요청과 CPU 경합, Python 전처리 재작성 |
| **Lambda 컨테이너(ONNX Runtime)** | PyTorch 모델을 ONNX로 변환해 실행, 호출한 만큼 과금 | 추론 1.07초에서 185ms로 단축, 동시 촬영만큼 확장 | 콜드스타트 최대 9.5초 |

**핵심 설계 결정**

- **시연 시간대만 실행 환경 1개 사전 예약(Provisioned Concurrency)**: 콜드스타트를 첫 호출에서 제거. 24시간 예약해도 월 약 36달러입니다.
- **고정 검증셋 2,024품목으로 배포 전 자동 검증**: 직전 모델 대비 MAE +0.2cm·±3cm 적중률 −2%p 안, 절대 상한 MAE 3cm. 통과한 모델만 Lambda 별칭에 연결됩니다.

![모델 파이프라인 — 빌드 → 고정셋 정확도 검증 → Lambda 갱신, 3단계 통과](images/08-model-gate-actions.png)

**결과**

| 항목 | 값 |
| --- | --- |
| 추론 시간(CPU) | **1.07초 → 185ms** |
| 월 비용 | GPU 상시 약 380달러 → Lambda 호출 100만 건 + 24시간 예약 **약 66달러** |
| 시연 기간 핸들러 p95 | 609ms(246건, 목표 1초) |
| 정확도 게이트 | INT8 양자화 후보: MAE 2.06 → 3.57cm, 적중률 62.5% → 22.6%로 **자동 차단** |

**결론**

속도만 보면 INT8(164ms)이 가장 빨랐지만 적중률이 40%p 떨어져 게이트가 막았습니다. 재학습 없이 통과하는 경량화 후보는 없었고, 기준 모델 그대로 배포했습니다.

# 문제 5 · 박스 편성을 부피 비교에서 3D 빈 패킹으로

**문제 배경**

초기 판정은 "상품 부피 합 < 박스 부피"였습니다. 30×30×30cm 박스에 25×25×20cm 상품 2개는 부피로는 통과하지만 어떤 방향으로도 함께 들어가지 않습니다. 발표 심사에서 현업 심사위원이 지적하기 전까지 무게도 계산에 없었습니다. 택배 요금은 크기·무게 구간 중 높은 쪽이라 무게를 빼면 요금이 틀립니다.

**해결 과정**

| 해결 방안 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| 부피 합산 비교 | 총부피만 비교 | 빠름 | 안 들어가는 박스 추천 → 현장 재포장 |
| 상품별 6방향 회전 검사 | 하나씩 들어가는지 확인 | 단일 상품 정확 | 여러 상품 조합은 판정 못 함 |
| **3D 빈 패킹 휴리스틱 + 국소 탐색** | 극점(extreme point) 배치, 초기 해 First Fit, 상품 이동으로 개선. 목적 함수는 총 배송비 | 판정이 곧 실제 배치, 분할과 적재를 한 기준으로 최적화 | NP-hard라 최적 보장 없음 |

**핵심 설계 결정**

- **목적 함수 = 총 배송비(CJ대한통운 2024 표준운임 5구간)**: 요금표가 바뀌어도 편성이 따라갑니다. 취급 한도(20kg·세 변 합 160cm) 초과는 후보에서 제외됩니다.
- **포장 완료 무게 검수**: 실측이 예상과 3%(최소 0.1kg) 넘게 다르면 완료를 막습니다. 담긴 상품이 빠졌거나 바뀐 경우를 잡습니다.

**결과**

| 검증 | 결과 |
| --- | --- |
| "부피는 통과하나 배치 불가" 테스트 | 부피 방식 실패, 3D 빈 패킹 통과 |
| 합성 주문 벤치마크(SKU 500종, 주문당 평균 16.5개) | 주문당 **p50 2.3ms, p95 13.8ms**, 5,000건 21초 |

![합성 주문 5,000건 벤치마크 — 주문당 p95 13.8ms](images/09-cartonization-bench.png)

**결론**

주문 접수 시점에 실시간 편성이 가능한 속도(주문당 p95 13.8ms)를 확인했습니다. 벤치마크 중 국소 탐색이 상품을 뺀 쪽 박스를 재판정하지 않아 예외가 나는 주문을 찾았고, 회귀 테스트로 고정했습니다. 부피 방식 대비 배송비 절감액은 아직 측정하지 않았습니다.

# 더 개선할 부분

1. **박스 자재 락**: 포화 처리량의 상한입니다. 상품처럼 원장으로 옮겨 완료 시점 판정과 락을 없애면 풀 20에서 처리량이 더 오를지 확인합니다.
2. **주문 일괄 접수**: 접수마다 유휴 토트 3만 건을 읽어 5,000건 배치가 60초를 넘고, 겹친 배치가 같은 토트를 골라 전체 롤백됩니다. 잠긴 행을 건너뛰고 1건만 가져오는 방식과 500건 단위 저장으로 바꿉니다.
3. **API 서버 이중화**: 지금은 1대가 죽으면 입고·출고가 함께 멈춥니다. 집계 스케줄러 분산 락과 로드밸런서가 필요합니다.
4. **24시간 콜드스타트**: 상시 예약(월 36달러)과 주기 웜업 호출을 비용·첫 응답 지연으로 비교해 정합니다.
5. **박스 편성 효과 측정**: 부피 방식 대비 추천 변경 비율과 배송비 차이, 소형 주문의 전수 탐색 대비 품질을 측정합니다.
