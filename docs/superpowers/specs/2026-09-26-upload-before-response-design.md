# 촬영 사진 업로드 — 응답 전 병렬 업로드 설계 (2026-09-26)

## 1. 배경

촬영 API(`POST /api/v1/inbound/measurements`)는 사진 3장을 읽고, Lambda 추론을 부르고, 세션을 저장한 뒤 응답한다. 사진의 S3 업로드는 세션 커밋 뒤 전용 스레드 풀에서 비동기로 한다(D-27, 2026-09-15). 응답 경로에서 업로드를 뺀 결과 저장 구간 p95가 36ms에서 12ms로 줄었다.

운영 실측(2026-09-16, 실제 3뷰 사진, 11종 × 5회 순차):

| 구간 | p50 | p95 |
| --- | ---: | ---: |
| 사진 읽기 `loadMs` | 80ms | 108ms |
| 추론 호출 `inferMs` | 318ms | 343ms |
| 저장 `saveMs` | 27ms | 34ms |
| 서버 total | 426ms | 574ms |
| 업로드(응답 밖) `uploadMs` | 109ms | 132ms |
| 클라이언트 E2E | 524ms | 611ms |

## 2. 문제

비동기 업로드는 메모리 안 대기 줄(코어 3 / 최대 6 / 큐 2,000)에 들어간다. 세 경우에 사진이 보관소에 남지 않는다.

| 경우 | 동작 | DB 상태 | 근거 |
| --- | --- | --- | --- |
| 대기 줄 포화 | 스레드 풀이 작업을 거절(기본 AbortPolicy), 로그 한 줄 | PENDING | 부하 테스트 실행 1·2: 작업자 45명(30 req/s)부터 적체, 1,155장 PENDING |
| 서버 재시작·종료 | 줄에 남은 작업은 30초까지만 기다리고 버려짐. 크래시면 즉시 소실 | PENDING | `ImageUploadExecutorConfig` `awaitTerminationSeconds 30` |
| 업로드 실패 | 3회 재시도 후 FAILED 표시 | FAILED | `MeasurementImageUploader` |

세 경우 모두 다시 올리는 경로가 없다. 촬영 응답은 성공이었으므로 작업자는 저장된 줄 알고, 나중에 검수 사진을 열면 없다. 입고 사진은 치수 확정의 증빙이라 유실은 재촬영으로만 복구된다. 현장 부하(입고 작업자 수 미확인, 작업자당 분당 1~2건)에서 대기 줄이 차는 일은 없지만, 재시작은 배포마다 일어난다.

## 3. 대안

| 안 | 방식 | 응답 시간(추정) | 유실 | 변경 범위 |
| --- | --- | --- | --- | --- |
| A. 현행 + Outbox 재처리 | 커밋 뒤 비동기 업로드는 그대로. PENDING·FAILED 행을 스케줄러가 주기적으로 다시 올림 | 지금과 같음(E2E p95 611ms) | 재처리 주기만큼 늦게 복구. 응답 시점엔 사진 없음 | 스케줄러 1개, 상태 전이 |
| B. S3 선업로드, Lambda가 S3에서 읽기 | 백엔드가 사진 3장을 먼저 올리고 키만 Lambda에 전달. Lambda가 S3 GET | 업로드 109ms + 추론 + Lambda 안 S3 GET 3회(미측정, 같은 리전 수십 ms) − base64 조립·전송분. p50 +50~100ms 추정 | 없음(추론 전에 S3에 있음) | Lambda 코드·이벤트 계약 변경, ai 저장소 게이트·배포 |
| **C. 병렬 업로드 후 응답 (채택)** | 사진을 읽은 직후 (a) 업로드 3장과 (b) 추론 호출을 동시에 시작. 둘 다 끝나면 세션 저장(STORED) 후 응답 | max(업로드, 추론) ≈ 추론. 지금과 거의 같음 | 없음(응답 전에 S3에 있음) | 백엔드만. Lambda 무변경 |

A는 유실을 나중에 메우는 것이고, 응답을 받은 작업자가 사진을 바로 열면 없는 상태는 그대로다. B는 Lambda 계약을 바꾸고 응답도 느려진다. C는 업로드(p50 109ms)가 추론(p50 318ms)보다 짧아 응답 시간을 거의 바꾸지 않으면서 "응답 = 사진이 있다"를 보장한다. 이 비교는 4절의 측정으로 확정한다.

## 4. C안 설계

### 흐름

```
measure(productId)
  images = load()                      -- 80ms
  token  = 세션 전 키 토큰 발급          -- UUID (세션 id는 저장 전이라 없음)
  uploads = executor.submit(put 3장)   -- 병렬, 각 장 독립 future
  result  = infer(images)              -- 318ms, 요청 스레드
  storedKeys = uploads.join(timeout)   -- 업로드 대기(추론이 더 길면 0ms)
  writer.save(result, storedKeys)      -- 트랜잭션. 사진 행은 STORED 로 바로 저장
  응답
```

### 결정

- **D-U1. 키는 세션 id가 아니라 사전 토큰으로 만든다.** 지금 키는 `keyFor(sessionId, cameraNo)`인데 세션 id는 저장 시점에 생긴다. 업로드가 저장보다 먼저이므로 키를 `measurements/{productId}/{uuid}/{cameraNo}.jpg`로 바꾼다. 세션 행에 키를 그대로 저장하므로 조회(1-6)는 변경 없음.
- **D-U2. 업로드 실패는 촬영 실패다.** 재시도(3회, 1초 간격) 뒤에도 실패하면 세션을 `MEASURE_FAILED`(사유 `IMAGE_STORE_FAILED`)로 저장하고 그렇게 응답한다. 추론 결과는 버린다. 증빙 없는 측정을 성공으로 내보내지 않기 위해서다. 작업자는 재촬영한다.
- **D-U3. 대기 줄이 차면 거절하지 않고 요청 스레드가 올린다.** `RejectedExecutionHandler`를 `CallerRunsPolicy`로 바꾼다. 포화 시 응답이 느려질 뿐 유실은 없다. 큐 용량은 2,000에서 200으로 줄인다(응답 전에 끝나야 하는 작업이라 긴 줄은 의미가 없다).
- **D-U4. 업로드 대기 상한은 추론 타임아웃과 같은 값이다.** 추론이 끝났는데 업로드가 안 끝난 경우를 위해 `join`에 상한(기본 8초, 추론 타임아웃과 동일)을 둔다. 넘으면 D-U2와 같이 처리하고 진행 중 업로드는 취소한다.
- **D-U5. DB 저장이 실패하면 S3에 고아 객체가 남는다.** 업로드가 먼저이므로 저장 롤백 시 객체 3개가 남는다. 세션 없는 키는 조회되지 않으므로 기능에 영향이 없고, 정리는 S3 수명주기 규칙(접두사 `measurements/`, 세션과 연결 안 된 객체 판별은 범위 밖)으로 미룬다. 지금 구조의 반대 경우(DB에 키가 있는데 객체가 없음)보다 낫다.
- **D-U6. 추론 실패 시 업로드는 그대로 둔다.** 추론이 `MEASURE_FAILED`면 사진은 이미 올라가 있다. 실패 세션에도 사진 키를 붙여 실패 원인 확인에 쓸 수 있게 한다.
- **D-U7. `MeasurementImageUploader`(AFTER_COMMIT 리스너)와 `MeasurementImagesPending` 이벤트, `upload_status` PENDING 전이는 제거한다.** `upload_status` 컬럼은 남기되 저장 시점에 STORED만 쓴다. FAILED는 D-U2로 세션 자체가 실패라 쓰이지 않는다.

### 기각한 안

- 업로드를 요청 스레드에서 순차로(동기, 트랜잭션 밖): 응답에 109ms가 그대로 더해진다. C가 같은 보장을 더 싸게 준다.
- 업로드 실패를 성공 응답 + FAILED 표시로 두기: 증빙 없는 측정을 성공으로 내보낸다. 기각.

### 미확정

- 부하 시 병렬 업로드가 요청 스레드 수만큼 동시 S3 put을 만들어 풀 크기(최대 6)가 병목이 되는 지점. 4절 부하 측정에서 본다. 필요하면 최대 스레드를 요청 처리 스레드 수에 맞춘다.
- 로컬 저장소(`LocalImageStore`) 경로도 같은 코드로 간다. 파일 쓰기라 병렬 이득은 없다.

## 5. 측정 계획 (A 현행 vs C)

같은 도구·같은 환경(EC2 백엔드 + RDS + 실제 S3 + Lambda `live`)에서 이미지만 바꿔 잰다. 조건마다 리셋.

| # | 측정 | 방법 | 판정 |
| --- | --- | --- | --- |
| M1 | 단일 클라이언트 응답 시간 | 11종 × 5회 순차, 서버 구간 로그 + 클라이언트 E2E (`tools/measure` 프로토콜) | C의 E2E p50·p95가 A 대비 +30ms 이내면 "응답 시간 유지" |
| M2 | 부하 응답 시간·유실 | k6 촬영 시나리오 작업자 10·30명, 각 3분. 응답 p95, 실패, 종료 후 `measurement_image` 상태별 건수, 업로드 스레드 풀 활성·큐 깊이(Micrometer) | A: PENDING > 0 여부. C: PENDING·FAILED 0, 응답 p95 |
| M3 | 재시작 유실 재현 | 작업자 10명 부하 중 `docker compose restart backend`. 종료 후 상태별 건수 | A: PENDING 잔존 건수. C: 0 (진행 중이던 요청은 실패 응답) |
| M4 | 포화 유실 재현 | 작업자 60명 3분(실행 2 재현) | A: 거절 로그·PENDING. C: 응답 p95 상승 폭과 유실 0 |

산출물: `docs/evidence/upload-before-response/` 아래 조건별 JSON·로그·Grafana 캡처, `README.md` 전후 표. 포폴 캡처는 M2(응답 p95 나란히)와 M3(PENDING 잔존 건수 나란히).

## 6. 범위 밖

- B안 구현. 응답 시간 추정만 3절에 남긴다.
- S3 고아 객체 정리 규칙.
- 사진 조회(1-6) 계약 변경.

## 7. 실측 결과와 선택 (2026-09-26)

5절 계획대로 EC2 백엔드 + RDS + 실제 S3 + Lambda `live` 에서 A(현행 이미지 cd6222eefbf2)와 C(backend `feat/upload-before-response` a73311e)를 쟀다. 증거·재현 방법은 `docs/evidence/upload-before-response/README.md`.

| # | 지표 | A | C | 판정 |
| --- | --- | --- | --- | --- |
| M1 | 단일 클라이언트 E2E p50 / p95 (110건씩, ABBA) | 437 / 467ms | 441 / 482ms | 충족(+4 / +15ms, 기준 +30ms). C upload.wait p95 0ms, 병렬 업로드 p50 37ms |
| M2 | 작업자 10명 응답 p95 · PENDING | 535ms · 0 | 536ms · 0 | 차이 없음 |
| M2 | 작업자 30명 응답 p95 · PENDING | 524ms · 0 | 544ms · 0 | 차이 없음 |
| M3 | 작업자 10명 중 재시작(SIGTERM) 60초 뒤 PENDING | 0 | 0 | A 도 유실 없음(정상 종료가 큐를 비움) |
| M3 보조 | 작업자 30명 중 SIGKILL 60초 뒤 PENDING | 0 | 0 | 1회 시행, 유실 재현 안 됨 |
| M4 | 작업자 60명 응답 p95 | 540ms | 946ms | C 가 +406ms. 업로드 풀이 코어 3에서 늘지 않아 병목 |
| M4 | 종료 직후 → 120초 뒤 PENDING | 2,116 → 18장(거절 6건) | 0 → 0 | C 만 유실 0 |
| M4 보조 | C 에서 코어만 6 (backend `exp/upload-c-core6`) | - | p95 540ms, 유실 0 | A 와 같은 응답 시간 |

2절의 세 유실 경우 중 이번 측정에서 A 에 재현된 것은 대기 줄 포화(M4)뿐이다. 재시작은 정상 종료가 진행 중 업로드를 마쳐 유실이 없었다. C 는 모든 조건에서 유실이 0이었다. 응답 시간은 작업자 30명까지 A 와 같았다. 60명에서는 코어 3 설정이 병목이었고, 코어 6에서는 A 와 같았다.

4절 미확정 항목("풀 크기가 병목이 되는 지점")의 답도 나왔다. `ThreadPoolExecutor` 는 큐가 가득 차야 코어 위로 스레드를 늘린다. 큐 200 을 채우기 전에는 최대 6이 쓰이지 않고, CallerRuns 도 발동하지 않는다(M4 C 큐 최대 75, CallerRuns 0).

### 선택 (사용자 결정)

- C 채택·병합 여부: 미정(사용자 결정). 병합한다면 업로드 풀 코어를 3 에서 6 이상으로 올릴지 함께 정한다.
- 큐 200·CallerRuns: 이번 부하에서는 한 번도 작동하지 않았다. 유지할지, 코어 = 최대로 두고 큐를 줄일지 미정(사용자 결정).
- S3 지연 꼬리: A 30명 조건에서 업로드 작업 하나가 9.9초 걸렸다(원인 미확정, SDK 안에서 쓰인 시간). 대기 상한 8초와 `IMAGE_STORE_FAILED` 는 유지하고, S3 클라이언트에 시도 상한 2초·호출 상한 6초·커넥션 128 을 명시했다(backend 0bed710). 로컬 재현에서 10초 멈춤이 2.1초로 줄었고, EC2 재측정(작업자 30명)에서 성능 변화와 촬영 실패는 없었다(`docs/evidence/upload-before-response/README.md` 후속 절). 설정 값은 사용자 결정.
