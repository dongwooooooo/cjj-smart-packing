# 박스 추천에 무게를 넣기까지 — 부피 근사에서 3D 배치와 배송비 목적함수로

CJ Campus AI SW 과정에서 풀필먼트 검수·포장 판단 시스템을 3주 동안 만들었습니다. 결과 발표에서 CJ 현업 심사위원이 남긴 질문은 하나였습니다. "무게는 고려했나요?" 그때의 박스 추천은 치수만 봤고, 무게는 어디에도 없었습니다. 이 글에서는 출고지시 배치의 박스 추천을 부피 근사가 아닌 3D 배치로 판정하게 된 과정부터, 발표 뒤에 무게를 목적함수에 넣고 5,000주문 배치로 편성 시간을 잰 결과까지를 다룹니다.

## 출고지시 배치에서 박스 추천이 하는 일

시스템은 입고와 출고 두 지점만 다룹니다. 입고 작업자는 카메라 3대로 상품을 촬영해 치수를 저장하고, 출고 시에는 저장된 치수로 주문을 배송 단위로 나눠 박스를 고릅니다. 박스 추천은 출고지시 접수 API가 배치 한 건을 받을 때 실행되고, 편성 결과가 그대로 배송 단위 레코드와 토트가 됩니다. 포장 작업자 화면의 "추천 박스"와 "완충재 권유"가 여기서 나옵니다.

```
POST /admin/orders/import
  ├─ 접수·검증        요청 결함은 배치 전체 400, 주문별 문제는 거부 목록
  ├─ 블록화           마진·완충재·무게를 반영한 낱개 블록
  ├─ 배치 판정        "이 블록들이 이 박스에 들어가는가"
  ├─ 편성 최적화      배송 단위 분할과 박스 확정
  └─ 라인 배정·토트 할당·저장   한 트랜잭션
```

원본 MVP 문서에는 박스 규칙이 "6방향 회전 검사, 3cm 마진, 수용 가능한 최소 박스" 한 줄뿐이었습니다. 완충재를 어떻게 반영할지, 한 박스에 안 들어가면 어떻게 나눌지, 적층불가 상품을 어떻게 다룰지가 없어서 그대로는 개발을 시작할 수 없었습니다(결정 이력 D-11). 이 규칙을 채우는 것이 첫 번째 일이었습니다.

## 부피 합산이 틀리는 세 지점

가장 단순한 판정은 상품 부피 합이 박스 부피보다 작으면 통과시키는 것입니다. 이 방식은 세 곳에서 틀립니다.

첫째, 부피로는 들어가는데 실제로는 안 들어가는 조합이 있습니다. 유효 내치수 30×30×30cm 박스에 25×25×20cm 상품 두 개를 넣으면 부피는 25,000 대 27,000으로 통과하지만, 어떤 방향으로 놓아도 두 개가 함께 들어가지 않습니다. 작업자는 현장에서 재포장을 하게 됩니다.

둘째, 박스 라인업은 부피 순서와 치수 순서가 다릅니다. 우체국 소포 규격을 준용한 박스 A~F호는 부피가 커진다고 세 변이 모두 커지지 않습니다. 2호는 1호보다 부피가 크지만 한 변이 더 짧습니다. "가장 큰 박스 하나만 검사해서 안 들어가면 초과 치수"라는 판정은 성립하지 않고, 박스마다 따로 봐야 합니다.

셋째, 편성과 적재를 분리하면 편성이 최적화 대상에서 빠집니다. 주문을 배송 단위로 먼저 나누고 각 단위의 박스를 고르는 순서라면, 나누는 방식이 박스 개수를 결정하는데도 그 방식 자체는 고정됩니다.

## 배치 기반 판정의 선택

네 가지 방식을 놓고 비교했습니다.

| 방식 | 장점 | 기각 사유 |
| --- | --- | --- |
| 부피 합산 비교 | 구현 단순, 즉시 계산 | 위 25×25×20 사례처럼 들어가지 않는 박스를 추천 |
| 단일 상품 6방향 회전 검사(초안 규칙) | 낱개 통과 여부는 정확 | 여러 상품의 동시 적재를 판정하지 못함. 분할·완충재 규칙 없음 |
| 배송 단위 선분할 후 박스 판정 | 단계가 명확 | 분할 방식이 고정돼 박스 개수를 줄이는 편성을 찾지 못함 |
| extreme point 배치 + FFD 초기해 + 국소 탐색 | 판정이 곧 실제 배치라 무효 추천이 없음. 편성과 적재를 한 목적함수로 최적화 | 휴리스틱이라 실제로는 들어가는 조합을 못 찾는 경우가 이론상 남음 |

extreme point 방식을 택했습니다. 박스 안에 놓인 블록들의 모서리가 만드는 후보점마다 블록을 축 평행 6방향으로 놓아 보고, 경계 안에 들어가면서 기존 블록과 겹치지 않는 첫 자리를 채택합니다. 블록을 놓을 때마다 그 블록의 세 모서리가 새 후보점이 됩니다.

```java
List<Point> candidates = new ArrayList<>(List.of(new Point(0, 0, 0)));
for (Block block : blocks) {
    Placement placement = tryPlace(block, candidates, placed, w, l, h);
    if (placement == null) {
        return false;                                   // 1. 한 블록이라도 못 놓으면 이 박스는 불가
    }
    placed.add(placement);
    candidates.remove(new Point(placement.x(), placement.y(), placement.z()));
    candidates.add(new Point(placement.x() + placement.w(), placement.y(), placement.z()));
    candidates.add(new Point(placement.x(), placement.y() + placement.l(), placement.z()));
    candidates.add(new Point(placement.x(), placement.y(), placement.z() + placement.h()));  // 2. 새 후보점 3개
}
```

판정 결과가 실제 배치이므로 "부피는 되는데 안 들어가는" 추천이 나오지 않습니다. 남는 오류는 반대 방향입니다. 휴리스틱이 배치를 못 찾으면 박스가 한 단계 커질 뿐, 안 들어가는 박스를 추천하지는 않습니다.

편성은 두 단계입니다. 주문 전체를 박스 하나에 담는 시도를 먼저 하고, 실패하면 FFD(부피 내림차순으로 수용 가능한 첫 단위에 배정)로 초기해를 만든 뒤 단위 사이에서 낱개를 옮겨 보며 목적함수가 좋아지는 변경만 채택합니다. 탐색 순서를 고정해 같은 입력에는 같은 편성이 나옵니다. 같은 SKU를 격자로 합치는 슈퍼블록과 투입 순서를 바꿔 재시도하는 다양화는 넣지 않았습니다. 단일 고정 순서가 실패하는 배치 가능 조합을 테스트로 만들지 못했고, 뒤에 나오는 실측에서도 도입 근거가 나오지 않았습니다.

이 판정과 편성은 Spring과 DB 의존이 없는 순수 로직으로 분리해 TDD로 작성했습니다. "부피 합은 남아도 배치가 불가능한 블록들은 거부한다", "부피가 큰 박스가 치수로 탈락해도 다음 박스를 검사한다", "같은 입력이면 같은 편성이 나온다"가 단위 테스트 이름 그대로 들어 있습니다.

## 무게를 넣는 세 가지 방법

발표 때까지의 목적함수는 박스 개수 최소, 동점이면 총 부피 최소였습니다. 무게가 빠진 이유는 단순합니다. 초안 규칙에 없었고, 시연에는 저울이 없어 무게를 사전 등록값으로 대체했기 때문입니다.

택배 요금은 세 변의 합 구간과 무게 구간 중 높은 쪽으로 정해집니다. CJ대한통운 2024 표준운임(동일권역)은 다섯 구간이고, 세 변 합 80/100/120/140/160cm와 무게 2/5/10/15/20kg이 각각 5,000원부터 9,000원까지 대응합니다([파스토 2024 택배사 요금 비교](https://guide-kr.fassto.ai/d4204e29-29fd-4e91-9b64-3784764a4fc2) 기준. CJ 공식 페이지는 접속 실패로 대조하지 못했습니다). 무게를 빼고 박스 개수만 세면, 부피는 남는데 무게가 구간을 한 단계 올리는 편성이 최적해로 나옵니다. 박스를 덜 쓰고 돈을 더 내는 편성입니다.

무게를 어디에 넣을지 세 가지를 비교했습니다.

| 방식 | 결과 | 기각 사유 |
| --- | --- | --- |
| A. 박스마다 한도 1개(택배사 전체 상한 20kg) | 구현량 최소 | 상한에 걸리는 주문이 거의 없어 편성 결과가 바뀌지 않음 |
| B. 박스 한도 = 세 변 합이 속한 요금 구간의 무게 상한 | 무게가 분할에 개입 | 요금 구간을 물리 한도로 오해한 모델. 2.5kg짜리 C호 상자는 그대로 배송되는데도 분할함 |
| C. 목적함수를 총 배송비로 교체 | 분할과 상위 구간 중 어느 쪽이 싼지를 계산이 판정 | 요금 구간표 기준정보와 국소 탐색 목적함수 교체. 구현 범위 최대 |

C를 택했습니다. 요금이 이미 치수와 무게를 한 수치로 합쳐 주므로, 무게에 가중치를 두는 절충식은 만들 근거가 없었습니다. 목적함수는 총 배송비, 동점이면 박스 개수, 그다음 총 부피입니다.

```java
private record PlanCost(long fareKrw, int units, long volumeMm3) implements Comparable<PlanCost> {
    @Override
    public int compareTo(PlanCost other) {
        return Comparator.comparingLong(PlanCost::fareKrw)     // 1. 총 배송비
                .thenComparingInt(PlanCost::units)              // 2. 박스 개수
                .thenComparingLong(PlanCost::volumeMm3)         // 3. 총 부피
                .compare(this, other);
    }
}
```

목적함수를 바꾸자 국소 탐색의 이동 후보도 바뀌어야 했습니다. 무게로 구간이 올라간 단위는 둘로 쪼개는 쪽이 쌀 수 있는데, 기존 단위 사이의 이동만으로는 단위 수가 늘지 않아 그 편성에 닿지 못합니다. 그래서 "새 배송 단위로 옮기는" 이동을 후보에 넣었습니다. 채택 조건은 목적함수뿐이라 쪼개는 쪽이 비싸면 그대로 기각됩니다. "무게로 요금 구간이 올라가면 한 박스에 들어가도 나눠 담는다"와 "요금표가 평평하면 한 박스로 둔다"가 이 동작을 고정하는 테스트입니다.

함께 넣은 것이 세 가지 더 있습니다. 세 변 합·최장변·총무게의 접수 한도(160cm / 100cm / 20kg)를 넘는 단위는 만들 수 없고, 낱개 하나가 한도를 넘으면 `OVERWEIGHT_ITEM`으로 그 주문만 거부합니다. 세 변 합 판정은 박스 외치수(내치수 + 판두께)로 합니다. 포장 완료 시에는 실측 무게를 받아 입고 때 저장한 무게로 계산한 예상 총무게와 대조하고, 허용 오차(0.1kg 또는 3% 중 큰 값)를 벗어나면 `WEIGHT_MISMATCH`로 막습니다. 입고에서 한 번 잰 값이 출고 검수까지 쓰입니다.

## 벤치마크가 먼저 찾은 결함

무게 축을 넣은 뒤 편성 시간을 재려고 벤치마크를 돌렸습니다. 시연 상품 11종의 치수를 ±20% 흔들어 SKU 500종을 만들고, 주문마다 1~10줄, 줄마다 1~5개를 배정했습니다(주문당 평균 낱개 16.5개, 난수 씨앗 고정). 첫 실행은 결과 대신 NPE로 끝났습니다.

```
CartonizationBenchmark > 배치_크기별_편성_시간() FAILED
    java.lang.NullPointerException at CartonizationBenchmark.java:151
```

원인은 국소 탐색의 이동 검사에 있었습니다. 낱개를 옮길 때 받는 쪽 단위만 수용 가능한지 확인하고, 낱개를 뺀 쪽은 당연히 담긴다고 가정했습니다. 배치 판정이 휴리스틱이라 이 가정은 성립하지 않습니다. 블록이 하나 줄면 놓는 순서와 남는 공간의 모양이 달라져, 17개는 F호에 담기는데 그중 하나를 뺀 16개는 어느 박스에도 담기지 않는다고 판정된 주문이 나왔습니다. 박스를 정하지 못한 단위가 편성 후보로 남았고, 요금 계산에서 NPE가 났습니다. 접수 API로 들어온 요청이었다면 500 응답이 됐을 경로입니다.

```java
List<PackItem> source = new ArrayList<>(units.get(from));
source.remove(i);
if (!source.isEmpty() && minBox(source, ascending, rates) == null) {
    // 낱개를 빼면 오히려 담을 박스가 사라질 수 있다. 박스를 정하지 못하는 편성은 후보가 될 수 없다.
    return null;
}
```

뺀 쪽도 수용 가능한지 검사하도록 고치고, 그 주문을 "낱개를 빼면 담을 박스가 사라지는 이동은 기각한다"는 회귀 테스트로 고정했습니다. 이 검사 누락은 8월 23일 첫 구현부터 있었습니다. 무게 작업 중에 발견했지만 무게와는 무관한 결함입니다.

## 5,000주문까지의 편성 시간

수정 뒤 같은 입력으로 다시 쟀습니다. 단일 스레드, 편성 함수 호출만 측정, DB와 직렬화 없음, Apple M2 Pro입니다.

| 주문 수 | 총 시간 | 주문당 p50 | p95 | 최대 | 분할 주문 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 0.36초 | 1.8ms | 12.8ms | 16.9ms | 15.0% |
| 1,000 | 4.0초 | 2.4ms | 12.9ms | 31.2ms | 21.6% |
| 5,000 | 21.0초 | 2.3ms | 13.8ms | 96.6ms | 20.0% |

주문 수가 50배가 돼도 주문당 p50·p95는 변하지 않았습니다. 배치 크기에 따른 초선형 증가는 없습니다. 시간 상위 구간을 만드는 요인은 배송 단위 수가 아니라 낱개 수였습니다. 5,000건 중 가장 오래 걸린 10건은 모두 낱개 31개 이상이고, 그중 6건은 배송 단위 1개로 끝난 주문입니다. 한 박스에 담기는 주문에서도 국소 탐색이 낱개마다 새 단위 후보를 만들어 보기 때문입니다. 이 결과로 슈퍼블록과 시도 다양화는 보류를 유지했습니다. 최적화할 병목이 아직 없습니다.

## 남은 것

근거가 없어 잠정으로 둔 값은 전부 설정이나 기준정보 컬럼으로 빼 두었습니다. 값이 확인되면 코드를 고치지 않습니다.

| 값 | 현재 | 확인할 것 |
| --- | --- | --- |
| 요금 구간표 | 5구간 5,000~9,000원, 동일권역 | CJ대한통운 2026 최신표 대조. 권역별·계약 단가는 없음 |
| 판두께 | 0.5cm | 실제 골판지 실측 |
| 박스 자체 무게 | 0.0kg | 박스 A~F호 실물 계량 |
| 무게 검수 허용 오차 | max(0.1kg, 예상 × 3%) | 저울 오차와 완충재 무게 |

적재 순서(무거운 상품을 아래에) 규칙은 넣지 않았습니다. 상품별 내하중 데이터가 없어 규칙을 만들어도 검증할 수 없습니다. 상품 무게가 비어 있으면 편성은 0kg으로 보고 출고 검수는 건너뜁니다. 요금이 실제보다 낮게 잡히는 방향입니다.

박스 판정은 부피 합산에서 extreme point 배치로 바꿔 무효 추천을 없앴고, 목적함수는 박스 개수에서 총 배송비로 바꿔 무게가 편성에 개입하게 했습니다. 편성 단위 테스트는 21개에서 38개가 됐고, 5,000주문 배치는 21초, 주문당 p95 13.8ms입니다. 코드는 [cjj-smart-packing-backend](https://github.com/dongwooooooo/cjj-smart-packing-backend)의 `orders/packing` 패키지에 있습니다.
